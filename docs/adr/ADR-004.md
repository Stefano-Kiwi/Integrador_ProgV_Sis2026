# ADR-004 — Control de concurrencia y prevención de sobreventa en las reservas de canchas

**Estado:** Aceptado  
**Fecha de registro:** 19 de noviembre de 2026  
**Proyecto:** FitZone Sports — Trabajo Integrador Final  
**Equipo:** 12  
**Unidad temática:** Arquitectura de Software — Concurrencia y consistencia transaccional  
**Requisitos relacionados:** RN-02, RF-10, RF-11 y RNF-03  
**Decisión relacionada:** ADR-002 — Adopción de PostgreSQL como base de datos relacional

---

## 1. Contexto

FitZone Sports permite a los socios y clientes externos consultar la disponibilidad de canchas deportivas y reservar turnos en cualquiera de las sedes de la cadena.

Cada cancha dispone de una grilla horaria que muestra los turnos libres, ocupados o no disponibles por mantenimiento.

Las reservas relacionan una cancha, un usuario, una fecha y un horario determinado.

Uno de los principales problemas de este tipo de sistemas aparece cuando **dos o más usuarios intentan reservar el mismo recurso de manera simultánea**.

En un sistema utilizado por múltiples personas, las solicitudes pueden llegar al backend con diferencias de apenas milisegundos.

Por ejemplo, dos usuarios pueden consultar una misma cancha a las 20:00 y observar que el turno se encuentra disponible.

Si ambos intentan confirmar la reserva al mismo tiempo, el sistema debe impedir que se registren dos reservas activas sobre el mismo espacio.

### 1.1 Problema identificado

Una implementación sencilla podría seguir este procedimiento:

1. Recibir una solicitud de reserva.
2. Consultar si existe una reserva activa para la cancha, fecha y horario.
3. Si no existe, crear la nueva reserva.
4. Devolver una respuesta exitosa.

En condiciones normales, este procedimiento puede funcionar correctamente.

Sin embargo, presenta una condición de carrera conocida como *race condition*.

Supongamos dos solicitudes simultáneas:

| Instante | Usuario A | Usuario B |
|---|---|---|
| T1 | Consulta disponibilidad | — |
| T2 | — | Consulta disponibilidad |
| T3 | Recibe «Libre» | — |
| T4 | — | Recibe «Libre» |
| T5 | Intenta crear reserva | — |
| T6 | — | Intenta crear reserva |
| T7 | Reserva creada | Reserva potencialmente duplicada |

Si solamente se valida la disponibilidad antes de insertar, ambas solicitudes podrían superar la comprobación inicial.

Por lo tanto, **la consulta previa no constituye una garantía suficiente de exclusividad**.

### 1.2 Regla de negocio RN-02

La regla RN-02 establece que una cancha no puede tener dos reservas activas para la misma fecha y franja horaria.

El sistema debe garantizar que:

- Dos solicitudes simultáneas no produzcan una doble reserva.
- Solamente una operación pueda ocupar un turno libre.
- Los intentos restantes reciban una respuesta de conflicto.
- Las reservas canceladas permitan volver a utilizar el horario.
- La garantía funcione incluso con varias solicitudes HTTP concurrentes.
- El resultado no dependa exclusivamente del estado almacenado en memoria del servidor.

La decisión debía ser compatible con el backend NestJS, Prisma ORM y PostgreSQL utilizados por el proyecto.

### 1.3 Objetivos de la decisión

Se establecieron los siguientes objetivos:

1. Garantizar la integridad de las reservas.
2. Evitar la sobreventa de turnos.
3. Mantener una respuesta HTTP clara para el usuario.
4. Reducir la complejidad del control de concurrencia.
5. Permitir que múltiples solicitudes sean atendidas por el backend.
6. Conservar la posibilidad de cancelar reservas y liberar horarios.
7. Facilitar pruebas automatizadas de concurrencia.
8. Mantener compatibilidad con la arquitectura de monolito modular.

## 2. Decisión

Se decidió implementar una estrategia basada en **validación previa de disponibilidad, inserción transaccional y restricción de unicidad a nivel de PostgreSQL**.

La solución utiliza un **índice único parcial** sobre la tabla `reserva_cancha`, definido para las reservas cuyo estado sea distinto de `CANCELADA`.

Esto permite asegurar que exista como máximo una reserva no cancelada para cada combinación de:

- Identificador de cancha.
- Fecha.
- Hora de inicio.

El índice implementado es:

```sql
CREATE UNIQUE INDEX "ux_reserva_cancha_slot"
ON "reserva_cancha"(
    "cancha_id",
    "fecha",
    "hora_inicio"
)
WHERE "estado" <> 'CANCELADA';
```

La decisión se fundamenta en que **la base de datos debe ser responsable de garantizar la unicidad**, ya que dispone de mecanismos de coordinación adecuados para múltiples transacciones concurrentes.

### 2.1 Estrategia seleccionada

La estrategia combina tres mecanismos:

**Validación previa en el servicio:** permite detectar rápidamente un turno ocupado y devolver un mensaje comprensible.

**Operación de creación mediante Prisma:** registra la reserva dentro de una transacción.

**Restricción única en PostgreSQL:** constituye la garantía definitiva contra reservas duplicadas.

Estos mecanismos tienen responsabilidades distintas.

La validación inicial mejora la experiencia del usuario.

La transacción administra la operación de escritura.

El índice único parcial impide que dos operaciones incompatibles se confirmen simultáneamente.

### 2.2 Naturaleza del mecanismo

La solución seleccionada **no utiliza un bloqueo pesimista explícito**, como `SELECT FOR UPDATE`, para bloquear anticipadamente el recurso.

Tampoco implementa un bloqueo optimista clásico basado en una columna de versión y una comprobación de que dicha versión no haya cambiado.

Se utiliza una tercera aproximación: **concurrencia controlada mediante restricciones de integridad de la base de datos**.

PostgreSQL coordina internamente las inserciones que compiten por la misma clave única.

Cuando dos transacciones intentan registrar la misma combinación de cancha, fecha y horario, solamente una puede cumplir la restricción de unicidad.

La otra operación debe esperar o fallar según el estado de la transacción concurrente y, si la primera confirma la reserva, termina recibiendo un error de unicidad.

De esta manera, la garantía no depende de que todas las solicitudes pasen secuencialmente por un único proceso del backend.

## 3. Alternativas consideradas

Se evaluaron cuatro alternativas para resolver la concurrencia en las reservas.

### 3.1 Alternativa A — Validación previa sin bloqueo

Consiste en consultar si el turno está disponible y crear la reserva cuando no se encuentra un registro activo.

**Ventajas:**

- Implementación sencilla.
- Bajo costo de desarrollo.
- Consultas fáciles de comprender.
- No requiere mecanismos especiales de coordinación.
- Ofrece una respuesta rápida en situaciones sin concurrencia.

**Desventajas:**

- No elimina las condiciones de carrera.
- Dos solicitudes pueden superar la validación inicial.
- Puede permitir reservas duplicadas si no existe otra restricción.
- Su comportamiento depende del orden en que se ejecutan las operaciones.
- No constituye una garantía suficiente de integridad.

**Motivo de descarte:**

No satisface RN-02 por sí sola.

Se decidió conservar la validación previa únicamente como mejora de experiencia, complementándola con una restricción definitiva en la base de datos.

### 3.2 Alternativa B — Bloqueo pesimista

El bloqueo pesimista consiste en bloquear un registro o recurso durante una transacción para impedir que otras operaciones incompatibles lo modifiquen simultáneamente.

En PostgreSQL puede implementarse mediante mecanismos como:

```sql
SELECT *
FROM cancha
WHERE id = 10
FOR UPDATE;
```

El ejemplo muestra cómo bloquear la fila de una cancha dentro de una transacción.

Para proteger la reserva habría que definir un protocolo consistente: bloquear un recurso existente, comprobar la disponibilidad y registrar la reserva dentro de la misma transacción.

**Ventajas:**

- Permite controlar explícitamente la ejecución concurrente.
- Resulta útil cuando varias modificaciones deben realizarse de manera coordinada.
- Puede simplificar determinados procedimientos que necesitan exclusividad.
- Evita que operaciones que respeten el mismo protocolo modifiquen simultáneamente un recurso bloqueado.

**Desventajas:**

- Puede generar esperas entre solicitudes.
- Mantener bloqueos durante mucho tiempo reduce el rendimiento.
- Requiere administrar correctamente los límites de las transacciones.
- Existe riesgo de interbloqueos si se adquieren recursos en órdenes incompatibles.
- Es más complejo cuando se necesitan múltiples bloqueos.
- Todos los caminos de escritura deben respetar el mismo protocolo.

**Motivo de descarte:**

Para una reserva representada por una combinación fija de cancha, fecha y horario, se consideró innecesario introducir un bloqueo pesimista explícito.

PostgreSQL podía garantizar la exclusividad directamente mediante una restricción de unicidad.

### 3.3 Alternativa C — Bloqueo optimista con versión

El bloqueo optimista permite ejecutar operaciones sin bloquear inicialmente los registros.

Antes de confirmar una modificación, se verifica que la información no haya cambiado desde su lectura.

Una implementación posible utilizaría un campo de versión:

```text
cancha:
    id
    nombre
    version
```

Cada operación comprobaría la versión leída anteriormente.

Si la versión hubiera cambiado, la operación tendría que reintentarse o rechazarse.

**Ventajas:**

- Reduce el uso de bloqueos explícitos.
- Puede ofrecer buen rendimiento cuando los conflictos son poco frecuentes.
- Resulta útil para controlar actualizaciones concurrentes de una misma entidad.
- Permite detectar modificaciones realizadas entre una lectura y una escritura.

**Desventajas:**

- Requiere agregar y mantener información de versión.
- Las operaciones deben comprobar correctamente la versión esperada.
- Los conflictos requieren una política de reintento o rechazo.
- La ausencia inicial de una reserva hace más complejo identificar un registro concreto que deba versionarse.
- Una actualización incorrectamente implementada podría permitir inconsistencias.

**Motivo de descarte:**

El principal problema de FitZone Sports no consiste en modificar simultáneamente una reserva existente, sino en **crear dos reservas para un mismo turno que inicialmente se encuentra libre**.

Una restricción única sobre la combinación que identifica el turno resulta más directa que administrar versiones de registros.

### 3.4 Alternativa D — Restricción única parcial en PostgreSQL (seleccionada)

Consiste en declarar directamente en la base de datos que no pueden existir dos reservas activas para el mismo turno.

**Ventajas:**

- La regla se aplica independientemente del número de solicitudes concurrentes.
- No necesita administrar bloqueos pesimistas desde la aplicación.
- No requiere columnas adicionales de versión.
- Funciona cuando varias instancias del backend utilizan la misma base de datos.
- La regla queda definida en un lugar central.
- Permite aprovechar las capacidades nativas de PostgreSQL.
- El índice también puede ayudar a determinadas consultas de disponibilidad.
- Las reservas canceladas no bloquean permanentemente los turnos.

**Desventajas:**

- Depende de una característica específica de PostgreSQL.
- Es necesario administrar la restricción mediante migraciones SQL.
- El backend debe interpretar los errores de unicidad.
- No evita que dos usuarios observen inicialmente un turno como disponible.
- La restricción garantiza la integridad del dato, pero no reemplaza otras reglas de negocio.
- Un cambio hacia horarios de duración variable podría requerir modificar el mecanismo.

**Evaluación:**

Se seleccionó esta alternativa porque permite implementar una regla de integridad clara, verificable y adecuada al modelo de reservas utilizado por FitZone Sports.

## 4. Comparación de alternativas

| Criterio | Validación previa | Bloqueo pesimista | Bloqueo optimista | Índice único parcial |
|---|---|---|---|---|
| Garantiza exclusividad por sí solo | No | Sí, con protocolo correcto | Sí, con diseño correcto | **Sí** |
| Requiere bloqueo explícito en la aplicación | No | Sí | No | No |
| Requiere columna de versión | No | No | Habitualmente sí | No |
| Complejidad de implementación | Baja | Media-alta | Media | **Baja-media** |
| Manejo de conflictos | Insuficiente | Esperas o errores | Reintentos o rechazo | Error de unicidad |
| Escalado con varias instancias de API | Inseguro sin coordinación | Posible | Posible | **Sí, con BD compartida** |
| Adecuación a RN-02 | Baja | Alta | Media-alta | **Alta** |

La comparación es cualitativa y considera el modelo de turnos horarios fijos utilizado en el proyecto.

**Resultado:** se seleccionó la restricción única parcial en PostgreSQL como mecanismo principal de integridad, conservando la validación previa para mejorar los mensajes del sistema.

## 5. Implementación de la decisión

### 5.1 Modelo de datos

La entidad `reserva_cancha` contiene los campos necesarios para identificar un turno.

En `backend/prisma/schema.prisma` aparecen, entre otros:

```prisma
model reserva_cancha {
  id          Int                   @id @default(autoincrement())
  cancha_id   Int
  usuario_id  Int
  fecha       DateTime              @db.Date
  hora_inicio Int                   @db.SmallInt
  estado      estado_reserva_cancha @default(PENDIENTE_PAGO)

  // Otros campos monetarios y relaciones.
}
```

El fragmento es una versión abreviada del modelo real.

La combinación de `cancha_id`, `fecha` y `hora_inicio` identifica la franja que se desea ocupar.

El campo `estado` permite diferenciar reservas vigentes de reservas canceladas.

### 5.2 Estados de una reserva

El sistema define los siguientes estados:

| Estado | Descripción |
|---|---|
| `PENDIENTE_PAGO` | Turno reservado a la espera del pago |
| `CONFIRMADA` | Reserva cuyo pago fue confirmado |
| `CUMPLIDA` | Reserva correspondiente a un turno realizado |
| `CANCELADA` | Reserva anulada |

El índice parcial considera ocupados los turnos asociados con todos los estados distintos de `CANCELADA`.

Esto significa que una reserva pendiente de pago también bloquea el horario.

Por lo tanto, el sistema no permite que dos usuarios mantengan simultáneamente reservas pendientes de pago para el mismo turno.

### 5.3 Migración SQL

La restricción se encuentra en:

`backend/prisma/migrations/20261118000000_indices_parciales_y_disponibilidad/migration.sql`

El código utilizado es:

```sql
-- RN-02: un único turno activo
-- por cancha, fecha y horario.

CREATE UNIQUE INDEX "ux_reserva_cancha_slot"
    ON "reserva_cancha"(
        "cancha_id",
        "fecha",
        "hora_inicio"
    )
    WHERE "estado" <> 'CANCELADA';
```

Este índice no está expresado como una restricción única convencional en el modelo Prisma.

Se conserva mediante una migración SQL específica.

La razón es que la versión de Prisma utilizada en el proyecto no representa directamente este índice parcial mediante la declaración habitual del esquema.

### 5.4 Consulta previa de disponibilidad

El repositorio dispone del método:

```typescript
findReservaByTurno(
  canchaId: number,
  fecha: Date,
  horaInicio: number,
): Promise<reserva_cancha | null> {
  return this.prisma.reserva_cancha.findFirst({
    where: {
      cancha_id: canchaId,
      fecha,
      hora_inicio: horaInicio,
      estado: { not: 'CANCELADA' },
    },
  });
}
```

Este método permite verificar si el turno está ocupado antes de intentar la inserción.

Si encuentra una reserva activa, el servicio devuelve una excepción de conflicto.

Sin embargo, esta consulta no constituye la protección definitiva.

Dos solicitudes concurrentes pueden ejecutarla antes de que alguna de ellas registre el nuevo turno.

Por lo tanto, su finalidad principal es anticipar conflictos comunes y ofrecer un mensaje claro.

### 5.5 Creación de la reserva

El método `createReserva` del repositorio utiliza Prisma para insertar el registro.

Fragmento representativo del código:

```typescript
return this.prisma.$transaction((tx) =>
  tx.reserva_cancha.create({
    data: {
      cancha_id: data.cancha_id,
      usuario_id: data.usuario_id,
      fecha: data.fecha,
      hora_inicio: data.hora_inicio,
      precio_base: data.precio_base,
      descuento: data.descuento ?? 0,
      recargo: data.recargo ?? 0,
      monto_total: data.monto_total,
      estado: 'PENDIENTE_PAGO',
    },
  }),
);
```

La operación utiliza una transacción Prisma.

No obstante, es importante aclarar que la consulta previa de disponibilidad no está incluida dentro de esa misma transacción en el código analizado.

Por esa razón, la garantía de no sobreventa **no depende del aislamiento de la consulta previa**, sino de la restricción única aplicada al momento de insertar.

### 5.6 Tratamiento del conflicto

El servicio `CanchasService` captura el error de Prisma cuando PostgreSQL rechaza la inserción por una restricción de unicidad.

El mecanismo utilizado es:

```typescript
catch (error) {
  if (
    error instanceof Prisma.PrismaClientKnownRequestError &&
    error.code === 'P2002'
  ) {
    throw new ConflictException(
      'El turno seleccionado ya se encuentra reservado',
    );
  }

  throw error;
}
```

Prisma utiliza el código `P2002` para informar una violación de unicidad.

NestJS transforma `ConflictException` en una respuesta HTTP `409 Conflict`.

Esto permite diferenciar una reserva exitosa de un intento rechazado porque el recurso ya fue ocupado.

### 5.7 Secuencia completa

El flujo es el siguiente:

```text
            USUARIO
               |
               v
       POST /canchas/reserva
               |
               v
        CanchasController
               |
               v
         CanchasService
               |
               v
     Verificar cancha habilitada
               |
               v
      Consultar turno existente
               |
        +------+------+
        |             |
      Ocupado        Libre
        |             |
        v             v
    HTTP 409      Calcular precio
                      |

                      |

```

El resultado se comunica al frontend.

Una reserva creada exitosamente queda inicialmente en estado `PENDIENTE_PAGO`.

El pago se procesa mediante el módulo correspondiente.

## 6. Ejemplo de concurrencia real

Para representar el problema se considera que dos usuarios intentan reservar la misma cancha.

**Recurso solicitado:**

- Cancha: 5.
- Fecha: 15 de junio de 2027.
- Hora de inicio: 20:00.
- Estado inicial: turno libre.

### 6.1 Desarrollo simultáneo

| Paso | Usuario A | Usuario B |
|---|---|---|
| 1 | Consulta turno | Consulta turno |
| 2 | Recibe disponible | Recibe disponible |
| 3 | Solicita reserva | Solicita reserva |
| 4 | Intenta insertar | Intenta insertar |
| 5 | PostgreSQL acepta una inserción | PostgreSQL detecta conflicto con la clave única |
| 6 | Recibe `201 Created` | Recibe `409 Conflict` |

La identidad del usuario que obtiene el turno depende de cuál inserción consigue confirmarse primero.

No se garantiza que gane necesariamente quien hizo clic primero, sino que **solamente puede existir una reserva no cancelada para esa clave**.

### 6.2 Resultado esperado en la base de datos

La tabla `reserva_cancha` debe contener una única reserva activa para esa combinación.

Ejemplo:

| cancha_id | fecha | hora_inicio | estado |
|---|---|---|---|
| 5 | 2027-06-15 | 20 | PENDIENTE_PAGO |

No puede coexistir otro registro con la misma combinación y un estado distinto de `CANCELADA`.

### 6.3 Interpretación

La estrategia no impide que los dos usuarios observen inicialmente la franja como disponible.

Eso es una consecuencia normal de trabajar con consultas concurrentes.

Lo que garantiza el sistema es que **la base de datos no confirme dos reservas incompatibles**.

Esta distinción resulta fundamental para comprender la decisión arquitectónica.

## 7. Cancelación y liberación del turno

Las reservas pueden cancelarse conforme a las reglas de negocio del sistema.

Cuando una reserva pasa al estado `CANCELADA`, deja de cumplir el predicado del índice único parcial.

Como consecuencia, el horario vuelve a poder utilizarse para una nueva reserva.

Por ejemplo:

| Reserva | Cancha | Fecha | Hora | Estado |
|---|---|---|---|---|
| 101 | 5 | 2027-06-15 | 20 | CANCELADA |
| 102 | 5 | 2027-06-15 | 20 | PENDIENTE_PAGO |

Esta situación es válida porque la primera reserva ya fue cancelada.

El historial de la reserva anterior puede conservarse sin impedir la contratación del turno.

### 7.1 Política de cancelación

En el código actual:

- Una reserva `PENDIENTE_PAGO` puede cancelarse.
- Una reserva `CONFIRMADA` también puede cancelarse.
- Una reserva `CUMPLIDA` no puede cancelarse.
- Una reserva `CANCELADA` no puede volver a cancelarse.
- Las reservas pagadas pueden tener una penalidad si la cancelación ocurre con menos de 24 horas de anticipación.

Estas reglas están definidas en:

`backend/src/canchas/reserva-reglas.ts`

### 7.2 Consideración sobre reservas pendientes de pago

El índice bloquea el turno desde el momento en que la reserva queda `PENDIENTE_PAGO`.

Esto evita que otro usuario lo reserve mientras se espera la confirmación del pago.

Sin embargo, introduce una consecuencia: **si el usuario abandona el pago, el turno continuará ocupado hasta que la reserva se cancele o exista otro mecanismo que lo libere**.

En el código revisado no se identificó un mecanismo automático de expiración de reservas pendientes de pago.

La implementación de un vencimiento de estas reservas constituye una mejora futura posible.

## 8. Relación con las transacciones ACID

La elección de PostgreSQL se encuentra relacionada con la necesidad de mantener la consistencia de las operaciones.

El motor proporciona transacciones con propiedades ACID:

**Atomicidad:** las modificaciones incluidas en una transacción se confirman o revierten como una unidad.

**Consistencia:** las operaciones deben respetar las restricciones declaradas en la base de datos.

**Aislamiento:** las transacciones concurrentes interactúan según las reglas del motor y su nivel de aislamiento.

**Durabilidad:** los cambios confirmados se conservan mediante los mecanismos de persistencia de PostgreSQL.

### 8.1 Consistencia de las reservas

En FitZone Sports, la propiedad más importante para esta decisión es que las restricciones de integridad permanezcan vigentes incluso ante solicitudes concurrentes.

La base de datos no permite confirmar una operación que viole el índice `ux_reserva_cancha_slot`.

### 8.2 Transacción y restricción única

La transacción administra la creación de la reserva.

La restricción única controla que el registro sea compatible con los datos ya existentes o en proceso de confirmación.

Ambas herramientas son complementarias.

No debe afirmarse que utilizar `$transaction` por sí solo resuelve la sobreventa.

La garantía específica de RN-02 está implementada en PostgreSQL mediante el índice único parcial.

### 8.3 Independencia de instancias del backend

Si en el futuro se utilizaran varias instancias de la API NestJS conectadas a la misma base de datos, la restricción seguiría aplicándose.

Esto representa una ventaja frente a soluciones que utilizan un bloqueo únicamente en memoria.

Por ejemplo, dos procesos Node.js distintos no comparten necesariamente los mismos objetos ni sus mecanismos locales de sincronización.

En cambio, ambos deben cumplir las restricciones definidas en PostgreSQL.

## 9. Relación con el rendimiento — RNF-03

La aplicación también necesita mostrar rápidamente la disponibilidad de las canchas.

Para ello, el modelo contiene un índice compuesto:

```sql
CREATE INDEX "ix_reserva_cancha_disponibilidad"
ON "reserva_cancha"(
    "cancha_id",
    "fecha",
    "hora_inicio"
);
```

Este índice está orientado a consultas que filtran reservas por cancha, fecha y horario.

El índice único parcial `ux_reserva_cancha_slot` también puede utilizarse para determinadas consultas de reservas no canceladas.

### 9.1 Ventajas

- Permite localizar reservas asociadas con un recurso específico.
- Facilita el cálculo de ocupación de franjas horarias.
- Reduce la necesidad de recorrer registros no relacionados cuando el optimizador selecciona un acceso indexado.
- Contribuye a mantener tiempos de consulta adecuados.

### 9.2 Evidencia documentada

En `docs/rnf/RNF-03.md`, el equipo registró un análisis de ejecución de PostgreSQL 18.

El resultado documentado informa:

```text
Index Scan using ux_reserva_cancha_slot
Execution Time: 0.068 ms
```

Este resultado muestra que la consulta analizada utilizó el índice parcial.

El valor corresponde a una medición concreta y no representa una garantía universal de rendimiento.

Es importante distinguir dos funciones del índice:

**Integridad:** impedir reservas duplicadas.

**Optimización:** ofrecer una estructura de acceso que PostgreSQL puede aprovechar en consultas compatibles.

Ambas propiedades resultan útiles, pero la corrección de RN-02 no depende de alcanzar un tiempo de ejecución determinado.

## 11. Consecuencias de la decisión

### 11.1 Consecuencias positivas

**Prevención efectiva de sobreventa**

La base de datos impide que dos reservas no canceladas compartan la misma cancha, fecha y horario.

**Integridad centralizada**

La regla no depende de una validación duplicada en cada componente del sistema.

**Compatibilidad con concurrencia real**

Las solicitudes simultáneas deben cumplir la misma restricción.

**Escalabilidad del backend**

Se pueden incorporar distintas instancias de NestJS conectadas a la misma base de datos sin perder la garantía de unicidad.

**Simplicidad de implementación**

No es necesario administrar manualmente bloqueos pesimistas para cada solicitud.

**Respuesta clara para el usuario**

El sistema traduce el conflicto de unicidad a una respuesta HTTP `409 Conflict`.

**Liberación de horarios**

Las reservas canceladas no impiden registrar nuevas reservas sobre el mismo turno.

**Pruebas reproducibles**

El escenario puede evaluarse mediante solicitudes simultáneas sobre PostgreSQL real.

### 11.2 Consecuencias negativas

**Dependencia de PostgreSQL**

La implementación utiliza índices únicos parciales y necesita conservar las migraciones SQL correspondientes.

**Conflictos inevitables bajo concurrencia**

Cuando varios usuarios intentan reservar el mismo turno, solamente uno puede obtenerlo. Los demás deben recibir una respuesta de rechazo.

**Disponibilidad inicialmente desactualizada**

Un usuario puede visualizar un turno como libre y recibir después un conflicto si otro usuario lo reservó.

**Necesidad de interpretar errores**

El backend debe traducir correctamente las violaciones de unicidad a respuestas HTTP adecuadas.

**Restricción limitada al modelo horario definido**

La clave considera cancha, fecha y hora de inicio.

Si en el futuro se permitieran reservas de duraciones variables o franjas parcialmente superpuestas, podría ser necesario cambiar la estrategia.

**Bloqueo de turnos pendientes de pago**

Las reservas `PENDIENTE_PAGO` ocupan la franja, incluso cuando el pago todavía no fue confirmado.

**Costo de mantenimiento de índices**

Los índices ocupan espacio y requieren mantenimiento durante inserciones, actualizaciones y eliminaciones.

## 12. Limitaciones y riesgos

### 12.1 Cambios en la duración de los turnos

Actualmente, el servicio de disponibilidad organiza la grilla mediante franjas de una hora.

Si se incorporaran reservas de 90 minutos o duraciones variables, la unicidad sobre la hora de inicio podría no ser suficiente para detectar todos los solapamientos.

En ese caso podrían evaluarse restricciones de exclusión de PostgreSQL sobre intervalos horarios o un modelo explícito de intervalos ocupados.

### 12.2 Vencimiento de reservas pendientes

La política actual bloquea el turno desde que se crea la reserva.

Una mejora futura sería establecer un vencimiento para los pagos pendientes y liberar automáticamente los turnos abandonados.

Dicha modificación necesitaría reglas de transición de estados y pruebas concurrentes propias.

### 12.3 Cancelaciones simultáneas

La cancelación de una reserva debe mantener las reglas de transición de estados.

Es recomendable verificar que dos solicitudes simultáneas de cancelación no generen efectos duplicados, especialmente si la operación se relaciona con reembolsos o penalidades.

### 12.4 Autorización de las operaciones

La garantía de concurrencia no reemplaza las verificaciones de permisos.

El backend también debe comprobar que el usuario autenticado está autorizado para realizar la reserva y operar sobre los recursos correspondientes.

### 12.5 Mantenimiento de las migraciones

La restricción única parcial debe existir realmente en la base de datos del entorno donde se ejecuta la aplicación.

Si una instalación utiliza solamente el esquema Prisma y omite la migración SQL, podría no disponer de la misma garantía.

Por lo tanto, la aplicación de migraciones forma parte del procedimiento obligatorio de despliegue.

## 15. Evolución futura de la decisión

La solución actual resulta adecuada para el modelo de reservas de una hora y una única cancha por turno.

Si el sistema evolucionara, se podrían considerar las siguientes mejoras:

1. **Vencimiento automático de reservas sin pagar:** liberar turnos cuando se supera un plazo configurable.
2. **Reservas de duración variable:** incorporar restricciones sobre intervalos de tiempo para evitar solapamientos parciales.
3. **Reintentos controlados:** ofrecer alternativas cuando un usuario pierde una reserva por concurrencia.
4. **Monitoreo de conflictos:** registrar métricas de errores `409` y analizar los períodos de mayor demanda.
5. **Mayor cobertura de pruebas:** incorporar escenarios con cancelaciones, pagos y solicitudes concurrentes combinadas.
6. **Control de idempotencia:** evitar que el reenvío accidental de una solicitud genere efectos adicionales.
7. **Optimización del flujo de pago:** coordinar de manera explícita los estados de reserva con las operaciones del módulo Pagos.

Estas posibilidades no se consideran implementadas por esta decisión.

Si alguna extensión modificara de forma sustancial el mecanismo de concurrencia, debería documentarse mediante un nuevo ADR.

## 16. Conclusión

Para cumplir la regla de negocio RN-02, FitZone Sports adoptó una estrategia de **control de concurrencia mediante un índice único parcial de PostgreSQL**, complementada con validaciones previas de disponibilidad y operaciones transaccionales a través de Prisma ORM.

Esta decisión se tomó porque las validaciones realizadas únicamente en el backend no constituyen una garantía suficiente frente a solicitudes simultáneas.

Durante la evaluación se consideraron el bloqueo pesimista, el bloqueo optimista con control de versiones y la validación previa sin protección adicional.

El bloqueo pesimista podía resolver el problema mediante una coordinación explícita, pero incorporaba una complejidad innecesaria para el modelo de turnos utilizado.

El bloqueo optimista también era viable con un diseño adecuado, aunque requería administrar versiones y conflictos sobre recursos que inicialmente podían no existir como reservas.

La restricción única parcial resultó una alternativa más directa: expresa la regla de negocio en la base de datos y permite que PostgreSQL impida confirmar reservas incompatibles.

Además, el mecanismo no requiere que todas las solicitudes sean procesadas por una única instancia de NestJS.

Las reservas canceladas permiten reutilizar el turno, mientras que las reservas pendientes de pago, confirmadas o cumplidas permanecen sujetas a la restricción.

La implementación dispone de una prueba automatizada que contempla doce solicitudes simultáneas y espera una única reserva exitosa y once respuestas de conflicto.

**La decisión garantiza la integridad estructural del turno siempre que la migración SQL se encuentre aplicada correctamente, sin depender de bloqueos explícitos en memoria ni de la secuencia temporal de las solicitudes HTTP.**

Por lo tanto, se decidió mantener este mecanismo como la solución principal de prevención de sobreventa para el sistema actual.

**Decisión final: utilizar validación previa para mejorar la respuesta al usuario y un índice único parcial de PostgreSQL como garantía definitiva de exclusividad en las reservas de canchas.**
