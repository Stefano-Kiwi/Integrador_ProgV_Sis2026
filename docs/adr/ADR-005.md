# ADR-005 — Adopción de NestJS, inyección de dependencias y Prisma ORM para el backend

**Estado:** Aceptado  
**Fecha de registro:** 19 de noviembre de 2026  
**Proyecto:** FitZone Sports — Trabajo Integrador Final  
**Equipo:** 12  
**Unidad temática:** Unidad II — Frameworks, inversión de control y persistencia  
**Decisiones relacionadas:** ADR-001 — Monolito modular; ADR-002 — PostgreSQL  
**Requisitos relacionados:** RF-01 a RF-14, RN-01, RN-02 y RN-03

---

## 1. Contexto

FitZone Sports es una plataforma de gestión integral para una cadena de gimnasios y complejos deportivos distribuidos en múltiples sedes.

El backend debe procesar solicitudes provenientes del portal de socios y de la consola administrativa, aplicando reglas de negocio relacionadas con autenticación, membresías, control de acceso, clases grupales, canchas deportivas y pagos simulados.

La arquitectura seleccionada en el ADR-001 es un monolito modular, en el que las funcionalidades se organizan en módulos diferenciados que se ejecutan dentro de una única aplicación.

Para implementar esta arquitectura era necesario seleccionar un framework backend que proporcionara mecanismos adecuados para organizar controladores, servicios, repositorios y dependencias.

El sistema también requería comunicarse con la base de datos PostgreSQL seleccionada en el ADR-002, administrar relaciones entre entidades, ejecutar transacciones y mantener un modelo tipado compatible con TypeScript.

### 1.1 Problema identificado

Una implementación sin convenciones arquitectónicas claras puede producir distintos problemas:

- Controladores HTTP con demasiadas responsabilidades.
- Repetición de consultas a la base de datos.
- Acoplamiento excesivo entre funcionalidades.
- Dificultad para sustituir dependencias durante las pruebas.
- Inconsistencias en la validación de solicitudes.
- Duplicación de reglas de autenticación y autorización.
- Dependencias difíciles de mantener.
- Cambios en el modelo de datos que afectan numerosos archivos.
- Problemas de integración entre integrantes del equipo.

Estos riesgos resultan especialmente importantes en FitZone Sports porque varios módulos dependen de información compartida.

Por ejemplo, la reserva de una cancha requiere consultar el estado de la instalación, comprobar la disponibilidad, identificar la condición del usuario y calcular el precio correspondiente.

Asimismo, la reserva de clases involucra el estado de la membresía, el cupo disponible y el mecanismo de lista de espera.

Si estas responsabilidades se concentraran en los controladores o se implementaran mediante consultas dispersas, la aplicación sería más difícil de mantener y probar.

### 1.2 Necesidades técnicas

Se establecieron las siguientes necesidades:

1. Organizar el backend en módulos funcionales.
2. Utilizar TypeScript para definir contratos tipados.
3. Separar las responsabilidades de HTTP, negocio y persistencia.
4. Implementar inyección de dependencias.
5. Reutilizar servicios entre componentes.
6. Facilitar pruebas unitarias mediante mocks.
7. Validar automáticamente los datos recibidos.
8. Documentar la API REST.
9. Mantener compatibilidad con PostgreSQL.
10. Administrar migraciones del modelo de datos.
11. Soportar transacciones y restricciones de concurrencia.
12. Facilitar la evolución del sistema sin introducir una complejidad excesiva.

La decisión debía considerar tanto el framework de aplicación como la tecnología de acceso a datos.

## 2. Decisión

Se decidió utilizar **NestJS sobre Node.js y TypeScript como framework backend**, aprovechando su contenedor de inversión de control para administrar dependencias.

Para la persistencia se seleccionó **Prisma ORM**, conectado con PostgreSQL.

La arquitectura resultante separa las responsabilidades mediante:

- **Controllers:** recepción y respuesta de solicitudes HTTP.
- **Services:** implementación de reglas de negocio.
- **Repositories:** consultas y operaciones de persistencia.
- **Modules:** agrupación de componentes funcionales.
- **Providers:** servicios administrados mediante inyección de dependencias.
- **DTO:** definición y validación de datos de entrada.
- **Guards:** autenticación y autorización de operaciones.
- **PrismaService:** administración del cliente de base de datos.

Esta estructura permite organizar el backend de acuerdo con las necesidades del dominio y mantener una separación entre las capas de aplicación y persistencia.

### 2.1 Tecnologías seleccionadas

| Componente | Tecnología | Función |
|---|---|---|
| Entorno de ejecución | Node.js | Ejecutar la aplicación backend |
| Lenguaje | TypeScript | Proporcionar tipado y contratos de código |
| Framework | NestJS | Organizar módulos, controladores y servicios |
| Servidor HTTP | Adaptador Express de NestJS | Procesar solicitudes REST |
| Contenedor IoC | NestJS Dependency Injection | Resolver dependencias |
| Persistencia | Prisma ORM | Consultar y modificar datos |
| Base de datos | PostgreSQL | Almacenar información transaccional |
| Validación | class-validator / class-transformer | Validar solicitudes |
| Autenticación | JWT | Identificar usuarios |
| Documentación | Swagger / OpenAPI | Exponer el contrato HTTP |
| Pruebas | Vitest / Supertest | Verificar reglas y endpoints |

En el `package.json` revisado, el proyecto declara NestJS 12 y Prisma 5.22 como líneas de versión de referencia, mediante rangos de dependencias.

### 2.2 Principio de organización

La comunicación interna sigue principalmente el esquema:

```text
Solicitud HTTP
      |
      v
Controller
      |
      v
Service
      |
      v
Repository
      |
      v
PrismaService
      |
      v
PostgreSQL
```

Los controladores delegan las reglas de negocio a los servicios.

Los servicios utilizan repositorios para acceder a los datos.

Los repositorios utilizan Prisma para interactuar con PostgreSQL.

Este diseño permite reducir la repetición de código y definir responsabilidades más claras.

## 3. Alternativas consideradas para el framework backend

Se evaluaron diferentes alternativas tecnológicas para implementar la API.

### 3.1 Alternativa A — NestJS con TypeScript (seleccionada)

NestJS es un framework de Node.js que proporciona una estructura modular y mecanismos de inyección de dependencias.

Utiliza decoradores, módulos, controladores y proveedores para organizar las aplicaciones.

**Ventajas:**

- Organización modular integrada.
- Soporte directo de TypeScript.
- Contenedor de inyección de dependencias.
- Separación natural entre controladores y servicios.
- Mecanismos de autenticación mediante Guards.
- Validación de datos mediante Pipes y DTO.
- Integración con Swagger / OpenAPI.
- Herramientas para pruebas unitarias e integración.
- Compatibilidad con PostgreSQL y Prisma ORM.
- Convenciones que facilitan el trabajo de varios desarrolladores.

**Desventajas:**

- Requiere aprender conceptos como módulos, proveedores, decoradores y ciclo de vida.
- Introduce mayor estructura inicial que un framework minimalista.
- Una configuración incorrecta de las dependencias puede impedir iniciar la aplicación.
- La abstracción del framework puede dificultar la depuración de determinados errores.
- Su uso de metadatos y decoradores requiere configuraciones apropiadas de TypeScript.

**Evaluación:**

Se consideró la alternativa más apropiada porque FitZone Sports cuenta con múltiples módulos funcionales y necesita mantener reglas de negocio separadas de la comunicación HTTP.

El contenedor de inyección de dependencias también facilita incorporar patrones de diseño y reemplazar dependencias durante las pruebas.

### 3.2 Alternativa B — Express.js sin framework estructural adicional

Express es una biblioteca minimalista para implementar servidores y APIs HTTP sobre Node.js.

Permite definir rutas, middlewares y manejadores de solicitudes.

**Ventajas:**

- Configuración sencilla.
- Menor estructura inicial.
- Amplia documentación.
- Flexibilidad para organizar el proyecto.
- Buen rendimiento para aplicaciones HTTP.
- Integración con múltiples bibliotecas.

**Desventajas para FitZone Sports:**

- No impone una organización modular estándar.
- No incorpora por defecto un contenedor de inyección de dependencias.
- La estructura de controladores y servicios debe definirse manualmente.
- La validación y autorización requieren seleccionar e integrar soluciones adicionales.
- El equipo debe establecer y mantener sus propias convenciones arquitectónicas.

**Motivo de descarte:**

Express era técnicamente viable, pero requería construir manualmente parte de la organización que NestJS ya proporciona.

La reducción de código inicial no compensaba la necesidad de mantener varios módulos funcionales con reglas de negocio relacionadas.

**Aclaración:** la elección de NestJS no implica abandonar Express como tecnología HTTP. El proyecto utiliza `@nestjs/platform-express` como adaptador subyacente. La comparación se refiere a utilizar Express directamente, sin la estructura adicional proporcionada por NestJS.

### 3.3 Alternativa C — Fastify como framework principal

Fastify es un framework HTTP para Node.js orientado a una implementación eficiente de servidores y APIs.

**Ventajas:**

- Buen desempeño en procesamiento HTTP.
- Soporte para validación mediante esquemas.
- Arquitectura basada en plugins.
- Bajo costo de procesamiento en numerosos escenarios.
- Compatibilidad con TypeScript.

**Desventajas para este proyecto:**

- La organización de los módulos de negocio requiere decisiones adicionales.
- El sistema de plugins no equivale directamente a la estructura modular e IoC seleccionada.
- El equipo tendría que establecer convenciones propias para servicios, repositorios y dependencias.
- La migración del diseño existente introduciría trabajo adicional.

**Motivo de descarte:**

El objetivo prioritario no era maximizar de manera aislada el rendimiento del servidor HTTP, sino organizar un backend con múltiples reglas de negocio.

Se consideró que NestJS ofrecía una estructura más adecuada para ese propósito.

Fastify también puede funcionar como adaptador HTTP de NestJS, por lo que esta alternativa no representa necesariamente una arquitectura incompatible.

### 3.4 Alternativa D — Spring Boot

Spring Boot es una plataforma del ecosistema Java que permite construir aplicaciones backend con controladores, servicios, repositorios e inyección de dependencias.

**Ventajas:**

- Arquitectura madura.
- Contenedor de inversión de control consolidado.
- Herramientas para seguridad y persistencia.
- Organización adecuada para aplicaciones empresariales.
- Amplio soporte de pruebas y transacciones.

**Desventajas para FitZone Sports:**

- Requería incorporar Java y su ecosistema al proyecto.
- Aumentaba la diversidad tecnológica entre frontend y backend.
- Exigía adaptar la organización y las herramientas previstas.
- Podía incrementar la curva de aprendizaje del equipo.
- No aportaba una ventaja proporcional para el alcance académico seleccionado.

**Motivo de descarte:**

Se priorizó mantener TypeScript tanto en el frontend como en el backend.

NestJS ofrecía mecanismos arquitectónicos similares para los objetivos del proyecto sin incorporar un segundo lenguaje principal.

## 5. Inversión de control e inyección de dependencias

Uno de los motivos principales para seleccionar NestJS fue su contenedor de **inversión de control (IoC)**.

### 5.1 Problema que resuelve

En una implementación sin inyección de dependencias, un servicio podría crear directamente sus dependencias:

```typescript
class CanchasService {
  private repository = new CanchasRepository();
}
```

Este ejemplo es conceptual; no corresponde al código implementado.

El inconveniente de este enfoque es que `CanchasService` queda encargado de construir y administrar el repositorio.

Esto dificulta reemplazarlo durante una prueba y aumenta el acoplamiento entre componentes.

### 5.2 Solución con inyección de dependencias

NestJS permite declarar las dependencias mediante el constructor de una clase.

En FitZone Sports, `CanchasService` utiliza:

```typescript
@Injectable()
export class CanchasService {
  constructor(
    private readonly canchasRepository: CanchasRepository,
    private readonly pricingService: PricingService,
  ) {}
}
```

El servicio declara qué necesita, pero no construye manualmente esas dependencias.

NestJS se encarga de resolverlas mediante su contenedor.

### 5.3 Inversión del control de creación

El framework administra el ciclo de creación de los proveedores registrados.

De esta manera:

1. El módulo registra las clases disponibles.
2. NestJS identifica sus dependencias.
3. El contenedor obtiene o crea las instancias correspondientes.
4. Las instancias se inyectan en los componentes que las requieren.
5. Los servicios pueden utilizarlas sin conocer cómo fueron construidas.

Esta inversión de control simplifica el mantenimiento y permite que las dependencias sean sustituidas en contextos de prueba.

### 5.4 Registro de proveedores

El módulo Canchas registra sus componentes mediante:

```typescript
@Module({
  controllers: [CanchasController],
  providers: [
    CanchasRepository,
    CanchasService,
    PricingService,
    // Otros proveedores de estrategias de precio.
  ],
  exports: [CanchasService],
})
export class CanchasModule {}
```

Este fragmento resume la estructura del archivo real.

La implementación completa también registra las estrategias tarifarias y un proveedor creado mediante `useFactory`.

El módulo establece qué componentes pueden ser resueltos por el contenedor y cuáles se exportan para su utilización desde otros módulos.

### 5.5 Ventajas de la inversión de control

**Menor responsabilidad de creación**

Los servicios no tienen que instanciar manualmente todos los objetos que utilizan.

**Facilidad de prueba**

Las dependencias pueden sustituirse por objetos simulados.

**Configuración centralizada**

Cada módulo declara los componentes disponibles.

**Reutilización**

Un proveedor puede utilizarse en varios componentes conforme a la configuración de los módulos.

**Separación de responsabilidades**

El servicio se concentra en las reglas de negocio y no en la construcción de su infraestructura.

### 5.6 Limitaciones

La inyección de dependencias no elimina automáticamente todo el acoplamiento.

En la implementación actual, varios servicios dependen de clases concretas de repositorio y no de interfaces o tokens de abstracción independientes.

Esto significa que el sistema aprovecha las ventajas del contenedor, pero todavía conserva dependencias concretas entre algunas capas.

Una evolución futura podría introducir interfaces y tokens específicos donde resulte conveniente.

## 7. Selección de Prisma ORM

Además del framework backend, fue necesario elegir una tecnología para acceder a PostgreSQL.

Se decidió utilizar **Prisma ORM**, manteniendo consultas organizadas en clases Repository.

### 7.1 Problema que resuelve

La aplicación necesita realizar operaciones como:

- Consultar usuarios por identificador.
- Obtener membresías activas.
- Listar clases y reservas.
- Registrar pagos.
- Consultar disponibilidad.
- Crear reservas.
- Ejecutar transacciones.
- Recuperar información relacionada entre tablas.

Implementar cada consulta directamente en los servicios podría generar duplicación y aumentar el acoplamiento entre negocio y persistencia.

Prisma proporciona un cliente de acceso a datos basado en modelos declarados.

### 7.2 Esquema Prisma

El modelo se encuentra en:

`backend/prisma/schema.prisma`

La configuración principal es:

```prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}
```

La conexión se obtiene mediante una variable de entorno, evitando definir directamente la dirección y las credenciales dentro del esquema.

Los modelos representan las entidades y relaciones del dominio.

### 7.3 Cliente tipado

Prisma permite generar un cliente TypeScript compatible con el modelo de datos.

Por ejemplo, una consulta como:

```typescript
return this.prisma.cancha.findUnique({
  where: { id },
  include: {
    sede: true,
    tipo_cancha: true,
  },
});
```

permite recuperar una cancha con información relacionada.

Este fragmento representa la operación empleada en `CanchasRepository`.

El cliente generado proporciona tipos que ayudan a detectar errores en los nombres de propiedades y estructuras de consulta.

### 7.4 Integración con NestJS

El proyecto utiliza una clase denominada `PrismaService`:

```typescript
@Injectable()
export class PrismaService
  extends PrismaClient
  implements OnModuleInit, OnModuleDestroy
{
  async onModuleInit() {
    await this.$connect();
  }

  async onModuleDestroy() {
    await this.$disconnect();
  }
}
```

Esta implementación conecta Prisma con el ciclo de vida de NestJS.

Al inicializarse el módulo, se establece la conexión con la base de datos.

Cuando corresponde destruir el módulo, se solicita la desconexión.

### 7.5 PrismaModule

El archivo `backend/src/prisma/prisma.module.ts` contiene:

```typescript
@Global()
@Module({
  providers: [PrismaService],
  exports: [PrismaService],
})
export class PrismaModule {}
```

El decorador `@Global()` permite que el proveedor exportado esté disponible para los módulos de la aplicación sin necesidad de importar explícitamente `PrismaModule` en cada uno.

Esto simplifica la utilización de Prisma en distintos repositorios.

Como contrapartida, introduce una dependencia de infraestructura compartida, por lo que debe utilizarse con disciplina para no dispersar reglas de negocio entre módulos.

## 8. Alternativas consideradas para el acceso a datos

Se evaluaron distintas alternativas para implementar la capa de persistencia.

### 8.1 Alternativa A — Prisma ORM (seleccionada)

**Ventajas:**

- Cliente generado con tipos TypeScript.
- Modelos declarativos.
- Integración con PostgreSQL.
- Operaciones CRUD expresivas.
- Administración de migraciones.
- Consultas con relaciones entre entidades.
- Soporte de transacciones.
- Buena integración con repositorios de NestJS.

**Desventajas:**

- Requiere generar el cliente después de ciertos cambios.
- Algunos mecanismos específicos de PostgreSQL requieren SQL manual.
- El cliente generado está acoplado al esquema.
- Las actualizaciones del ORM pueden requerir ajustes.
- Las consultas complejas necesitan comprender las abstracciones y limitaciones de Prisma.

**Evaluación:**

Se consideró una solución adecuada por su tipado y su compatibilidad con el modelo relacional utilizado.

### 8.2 Alternativa B — TypeORM

TypeORM es un ORM que permite definir entidades y relaciones mediante clases y decoradores, con integración habitual en aplicaciones NestJS.

**Ventajas:**

- Integración con NestJS.
- Entidades orientadas a objetos.
- Soporte de relaciones.
- Consultas mediante repositorios y QueryBuilder.
- Migraciones y transacciones.

**Desventajas para este proyecto:**

- Requiere definir y mantener la correspondencia entre entidades y tablas.
- Las consultas complejas también necesitan conocimiento del ORM.
- Introduciría una alternativa de persistencia distinta de la adoptada por el equipo.
- Las restricciones avanzadas de PostgreSQL seguirían necesitando atención específica.

**Motivo de descarte:**

Se priorizó el cliente generado y el modelo declarativo de Prisma, por considerarlos convenientes para mantener los contratos del proyecto en TypeScript.

### 8.3 Alternativa C — Sequelize

Sequelize es un ORM para Node.js que permite trabajar con motores relacionales mediante modelos y consultas de alto nivel.

**Ventajas:**

- Experiencia consolidada en aplicaciones Node.js.
- Soporte de asociaciones entre modelos.
- Operaciones CRUD y transacciones.
- Compatibilidad con PostgreSQL.

**Desventajas para este proyecto:**

- Requería adoptar otro sistema de definición de modelos.
- El equipo tendría que integrar su tipado y convenciones con la estructura de NestJS.
- No ofrecía una ventaja decisiva frente a Prisma para las necesidades identificadas.

**Motivo de descarte:**

Se consideró que Prisma resultaba más conveniente para generar tipos a partir del esquema y mantener un proceso de migraciones centralizado.

### 8.4 Alternativa D — Consultas SQL directas

Consiste en utilizar un cliente PostgreSQL desde Node.js para construir y ejecutar sentencias SQL manualmente.

**Ventajas:**

- Control directo sobre las consultas.
- Acceso a todas las características de PostgreSQL.
- Menor dependencia de abstracciones ORM.
- Posibilidad de optimizar manualmente operaciones concretas.

**Desventajas:**

- Mayor cantidad de código repetitivo.
- Necesidad de mapear manualmente muchos resultados.
- Mayor responsabilidad al parametrizar consultas.
- Más esfuerzo de mantenimiento cuando cambia el esquema.
- Tipado de resultados y contratos que debe administrarse manualmente.
- Mayor esfuerzo inicial para operaciones CRUD convencionales.

**Motivo de descarte:**

El sistema posee numerosas entidades relacionadas y requiere desarrollar funcionalidades de manera progresiva.

Se consideró que utilizar Prisma para las operaciones habituales y SQL específico para las restricciones avanzadas ofrecía un equilibrio más adecuado.

## 10. Aplicación del patrón Repository

El proyecto utiliza el patrón Repository para organizar el acceso a datos.

### 10.1 Objetivo del patrón

El patrón Repository busca separar las operaciones de persistencia de las reglas de negocio.

Por ejemplo, `CanchasService` debe decidir si una reserva puede realizarse, pero no necesita implementar directamente todos los detalles de las consultas SQL.

### 10.2 Implementación

El archivo:

`backend/src/canchas/canchas.repository.ts`

contiene la clase `CanchasRepository`.

Su constructor recibe `PrismaService`:

```typescript
@Injectable()
export class CanchasRepository {
  constructor(
    private readonly prisma: PrismaService,
  ) {}
}
```

De esta forma, el repositorio delega las operaciones a Prisma.

### 10.3 Ejemplo de consulta

El repositorio utiliza:

```typescript
findById(id: number) {
  return this.prisma.cancha.findUnique({
    where: { id },
    include: CANCHA_INCLUDE,
  });
}
```

El servicio correspondiente utiliza ese método sin necesidad de conocer todos los detalles de la consulta.

### 10.4 Ejemplo de reserva

El módulo también contiene un método que crea una reserva dentro de una transacción:

```typescript
return this.prisma.$transaction((tx) =>
  tx.reserva_cancha.create({
    data: {
      cancha_id: data.cancha_id,
      usuario_id: data.usuario_id,
      fecha: data.fecha,
      hora_inicio: data.hora_inicio,
      precio_base: data.precio_base,
      descuento: data.descuento ?? 0,
      recargo: data.recargo ?? 0,
      monto_total: data.monto_total,
      estado: 'PENDIENTE_PAGO',
    },
  }),
);
```

El servicio utiliza esta operación como parte de la regla de reserva.

La protección definitiva contra la sobreventa corresponde al índice único parcial de PostgreSQL, explicado en el ADR-004.

### 10.5 Ventajas

- Centralización de consultas.
- Menor duplicación.
- Servicios de negocio más legibles.
- Posibilidad de sustituir repositorios durante las pruebas.
- Organización consistente entre módulos.
- Mayor facilidad para localizar cambios de persistencia.

### 10.6 Limitación de la implementación

El uso del patrón Repository no significa que los servicios sean completamente independientes de Prisma.

Algunos componentes utilizan tipos, resultados o errores específicos del ORM.

Por ejemplo, los servicios interpretan errores conocidos de Prisma para devolver respuestas HTTP apropiadas.

Esto constituye una dependencia tecnológica que debe considerarse durante futuras refactorizaciones.

## 11. Validación, seguridad y documentación de la API

La elección de NestJS permitió utilizar mecanismos integrados para validar y proteger las solicitudes.

### 11.1 Validación mediante DTO

Los DTO definen la información esperada por los endpoints.

Se utilizan decoradores de `class-validator` para expresar restricciones sobre los datos recibidos.

El archivo `backend/src/main.ts` registra un `ValidationPipe` global:

```typescript
app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,
    forbidNonWhitelisted: true,
    transform: true,
  }),
);
```

Esta configuración permite:

- Aplicar las validaciones declaradas.
- Rechazar propiedades no permitidas.
- Transformar determinados datos cuando corresponde.
- Reducir la cantidad de comprobaciones repetidas en los controladores.

La validación de entrada es complementaria de las reglas de negocio y de las restricciones de base de datos.

### 11.2 Autenticación mediante Guards

NestJS permite incorporar Guards para decidir si una solicitud puede continuar.

FitZone Sports utiliza:

- `JwtAuthGuard`.
- `RolesGuard`.

Ambos se registran globalmente en `AppModule` mediante `APP_GUARD`.

El primero comprueba la autenticación JWT y el segundo aplica restricciones basadas en roles declarados.

Los decoradores `@Roles()` y `@Public()` permiten identificar comportamientos de autorización sobre los endpoints correspondientes.

### 11.3 Autorización contextual

El control por roles debe complementarse con reglas específicas de negocio.

Por ejemplo, disponer de rol Gerente no implica automáticamente poder administrar recursos de cualquier sede.

Los servicios necesitan verificar que las operaciones correspondan a la sucursal autorizada.

Esta separación distingue:

**Autenticación:** quién realiza la solicitud.

**Autorización:** qué operaciones tiene permitido realizar.

**Autorización sobre recursos:** sobre qué sedes, usuarios o entidades puede operar.

### 11.4 Documentación OpenAPI

El proyecto utiliza `@nestjs/swagger`.

El archivo:

`backend/src/swagger/swagger.setup.ts`

configura la documentación de la API.

La interfaz Swagger se publica en:

```text
/api
```

El proyecto también configura la exportación del documento OpenAPI en formato JSON y YAML.

Esto permite que los desarrolladores del frontend consulten los contratos de los endpoints y reduzcan discrepancias de integración.

La utilización de NestJS y Prisma favorece la organización de distintos patrones y mecanismos arquitectónicos.

### 12.1 Repository

Los repositorios encapsulan las operaciones de persistencia.

Ejemplos:

- `UsersRepository`.
- `CanchasRepository`.
- `ClasesRepository`.

La inyección de dependencias no reemplaza a los patrones anteriores.

Es un mecanismo arquitectónico que facilita construir y conectar los componentes que implementan esos patrones.

Por lo tanto, la combinación seleccionada permite organizar las funcionalidades de acuerdo con sus necesidades sin concentrar toda la lógica en una única clase.

## 13. Estrategia de pruebas y mantenibilidad

La selección de NestJS y Prisma también se relaciona con la posibilidad de probar las reglas de negocio.

### 13.1 Pruebas unitarias

Los servicios pueden probarse reemplazando sus dependencias por mocks.

Por ejemplo, para evaluar una regla del módulo Canchas no siempre es necesario consultar una base PostgreSQL.

En una prueba unitaria se pueden simular las respuestas del repositorio y comprobar la reacción del servicio.

### 13.2 Pruebas de integración

NestJS proporciona herramientas para construir instancias de prueba de la aplicación.

El proyecto utiliza `@nestjs/testing` y Supertest para verificar endpoints.

Las pruebas de integración pueden comprobar la interacción entre controladores, servicios, repositorios y PostgreSQL.

### 13.3 Pruebas de concurrencia

Las operaciones sensibles a condiciones de carrera se prueban utilizando una base PostgreSQL real.

Esto permite evaluar restricciones y transacciones que no podrían verificarse completamente mediante mocks.

### 13.4 Cobertura

La configuración de Vitest establece umbrales mínimos del 70 % sobre el conjunto de archivos incluidos en la medición.

Los indicadores contemplados son:

- Sentencias.
- Ramas.
- Funciones.
- Líneas.

La decisión formal sobre la estrategia de pruebas se documenta en el ADR-008.

### 13.5 Estado de verificación

El repositorio contiene pruebas unitarias y de integración.

Sin embargo, la presencia de esas pruebas no acredita automáticamente que la última versión haya superado todas las verificaciones.

Antes de la entrega definitiva debe comprobarse el resultado de los comandos de lint, build y tests sobre el commit final.

## 14. Consecuencias de la decisión

### 14.1 Consecuencias positivas

**Organización consistente**

NestJS proporciona una estructura uniforme para módulos, controladores y servicios.

**Menor acoplamiento de creación**

El contenedor IoC administra proveedores y facilita la inyección de dependencias.

**Facilidad de mantenimiento**

La separación de responsabilidades permite localizar errores y modificar componentes con menor impacto.

**Tipado de datos**

Prisma y TypeScript proporcionan contratos que facilitan detectar determinados errores durante el desarrollo.

**Integración con PostgreSQL**

El sistema puede utilizar operaciones CRUD tipadas, transacciones y migraciones.

**Pruebas automatizadas**

Los servicios pueden evaluarse mediante mocks, mientras que los flujos completos pueden comprobarse con PostgreSQL real.

**Documentación de endpoints**

Swagger facilita consultar las operaciones HTTP y sus contratos.

**Reutilización**

Los servicios registrados pueden ser utilizados por otros componentes conforme a la configuración modular.

**Extensibilidad**

Los patrones Strategy, Observer y Repository se integran con la estructura de NestJS.

### 14.2 Consecuencias negativas

**Curva de aprendizaje**

El equipo debe comprender módulos, decoradores, proveedores, Guards y el ciclo de vida de NestJS.

**Complejidad inicial**

Para funcionalidades simples, la separación en controlador, servicio, repositorio y módulo puede requerir más archivos que una solución minimalista.

**Dependencia del framework**

La aplicación utiliza mecanismos específicos de NestJS que deberían adaptarse si se reemplazara el framework.

**Dependencia de Prisma**

Las consultas y migraciones se encuentran vinculadas a la tecnología seleccionada.

**Migraciones especiales**

Los índices únicos parciales necesitan mantenerse mediante SQL específico de PostgreSQL.

**Riesgo de dependencias circulares**

Una organización incorrecta de los módulos puede introducir relaciones circulares o problemas de resolución de proveedores.

**Dependencias globales**

Los módulos globales simplifican el acceso a proveedores compartidos, pero pueden hacer menos explícitas determinadas dependencias.

**Necesidad de disciplina**

La existencia de capas no garantiza que el equipo mantenga correctamente la separación de responsabilidades.

## 15. Riesgos y medidas de mitigación

### 15.1 Acoplamiento entre módulos

**Riesgo:** que los módulos comiencen a depender directamente de numerosas clases internas de otros módulos.

**Mitigación:** exportar únicamente los servicios necesarios y mantener responsabilidades bien delimitadas.

### 15.2 Consultas Prisma dispersas

**Riesgo:** que distintos servicios ejecuten consultas directamente y dupliquen lógica de persistencia.

**Mitigación:** concentrar las operaciones habituales dentro de los repositorios.

### 15.3 Cambios en el esquema

**Riesgo:** que una modificación del modelo de datos afecte consultas existentes.

**Mitigación:** utilizar migraciones versionadas, generar el cliente Prisma y ejecutar pruebas después de los cambios.

### 15.4 Dependencias circulares

**Riesgo:** que dos módulos necesiten inyectarse mutuamente y dificulten su inicialización.

**Mitigación:** revisar sus responsabilidades y extraer servicios compartidos cuando corresponda, evitando dependencias innecesarias.

### 15.5 Problemas de seguridad

**Riesgo:** que un controlador protegido por JWT no aplique correctamente las restricciones de rol o de sede.

**Mitigación:** combinar Guards, verificaciones de recursos y pruebas de autorización.

### 15.6 Incompatibilidad de contratos

**Riesgo:** que el frontend y el backend utilicen nombres de campos o estructuras diferentes.

**Mitigación:** mantener actualizados los DTO y el contrato OpenAPI, además de probar los recorridos integrados.

### 15.7 Desactualización de dependencias

**Riesgo:** que nuevas versiones del framework o del ORM introduzcan cambios incompatibles.

**Mitigación:** conservar lockfiles, revisar las actualizaciones y ejecutar las pruebas antes de incorporar nuevas versiones.

## 18. Evolución futura de la decisión

La arquitectura seleccionada permite continuar desarrollando funcionalidades dentro del monolito modular.

Si el sistema creciera significativamente, podrían evaluarse las siguientes mejoras:

1. **Introducir interfaces de repositorio:** reducir la dependencia de servicios respecto de implementaciones concretas.
2. **Optimizar consultas Prisma:** identificar operaciones que necesiten índices o SQL específico.
3. **Separar proveedores compartidos:** evitar dependencias globales innecesarias.
4. **Mejorar los contratos entre módulos:** limitar las responsabilidades que cada módulo expone.
5. **Ampliar la cobertura de pruebas:** verificar casos límite, errores de autorización y concurrencia.
6. **Generar tipos a partir de OpenAPI:** reducir discrepancias entre frontend y backend.
7. **Evaluar nuevas estrategias de persistencia:** solamente cuando exista una necesidad respaldada por mediciones.
8. **Monitorear el rendimiento de la API:** identificar problemas antes de modificar la arquitectura.

Estas mejoras se consideran posibilidades de evolución y no funcionalidades implementadas por este ADR.

Si una modificación futura sustituyera NestJS o Prisma, se debería registrar una nueva decisión arquitectónica, conservando el presente documento como evidencia histórica.

## 19. Conclusión

Se decidió utilizar **NestJS con TypeScript como framework backend y Prisma ORM como tecnología principal de persistencia**, sobre una base de datos PostgreSQL.

La elección de NestJS responde a la necesidad de desarrollar una aplicación modular con responsabilidades claramente diferenciadas.

Su contenedor de inversión de control permite administrar dependencias, reutilizar proveedores y construir componentes que pueden probarse mediante sustitución de sus colaboradores.

Prisma aporta un cliente tipado, herramientas de modelado y mecanismos para administrar consultas y migraciones.

La incorporación del patrón Repository permite concentrar las operaciones de persistencia y separar parcialmente los detalles de acceso a datos de las reglas de negocio.

Frente a Express directo y Fastify directo, NestJS ofrece una estructura arquitectónica más completa para las necesidades del proyecto.

Spring Boot constituye una alternativa técnicamente válida, pero se priorizó mantener TypeScript en toda la solución.

En cuanto a la persistencia, TypeORM, Sequelize y SQL directo también podrían resolver las necesidades de FitZone Sports, aunque Prisma fue seleccionado por su modelo declarativo y la generación de tipos.

La decisión presenta compromisos, como la dependencia de tecnologías concretas, la necesidad de mantener migraciones SQL especiales y una mayor estructura inicial.

Sin embargo, se considera que sus beneficios son apropiados para el alcance del Trabajo Integrador Final.

**Decisión final: mantener NestJS como framework backend, utilizar su contenedor de inyección de dependencias para organizar los componentes e implementar la persistencia con Prisma ORM y PostgreSQL, conservando la separación entre controladores, servicios y repositorios.**
