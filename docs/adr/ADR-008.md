## 1. Contexto

FitZone Sports es una plataforma de gestión integral destinada a una cadena de gimnasios y complejos deportivos con múltiples sedes.

El sistema permite administrar usuarios, membresías, clases grupales, reservas de canchas, pagos simulados y accesos mediante códigos QR dinámicos.

Estas funcionalidades deben respetar reglas de negocio que afectan directamente la consistencia de los datos y las operaciones de los usuarios.

Por ejemplo, una reserva de cancha debe considerar la disponibilidad del horario y evitar que dos personas reserven simultáneamente el mismo recurso.

El control de acceso debe impedir que un socio mantenga ingresos abiertos en distintas sedes al mismo tiempo.

La gestión de clases debe respetar la capacidad máxima, los estados de las reservas y la promoción de usuarios desde listas de espera.

Asimismo, el cálculo de tarifas debe aplicar correctamente descuentos y recargos según las condiciones definidas para cada usuario y franja horaria.

Estos escenarios muestran que no alcanza con comprobar visualmente que una pantalla funciona: es necesario verificar también las reglas internas y las interacciones entre los módulos.

### 1.1 Problema identificado

Durante el desarrollo, el equipo necesitaba incorporar nuevas funcionalidades y modificar otras existentes sin introducir errores en los recorridos previamente implementados.

La ausencia de una estrategia de pruebas podía generar distintos problemas:

- Errores en el cálculo de precios.
- Reservas duplicadas ante solicitudes simultáneas.
- Ingresos incompatibles con las reglas de membresía.
- Fallos de autenticación y autorización.
- Pérdida de consistencia durante la cancelación de clases.
- Errores en la promoción de usuarios en lista de espera.
- Problemas de integración entre controladores y servicios.
- Diferencias entre los datos enviados por React y los esperados por NestJS.
- Fallos en las migraciones de PostgreSQL.
- Errores de compilación incorporados durante una integración.
- Regresiones provocadas por modificaciones en componentes compartidos.

Además, el equipo debía demostrar ante la cátedra que las funcionalidades críticas habían sido verificadas mediante procedimientos reproducibles.

### 1.2 Restricciones del proyecto

La estrategia de pruebas debía cumplir las siguientes condiciones:

1. Ser compatible con NestJS y TypeScript.
2. Permitir probar reglas de negocio de manera aislada.
3. Facilitar la sustitución de dependencias mediante mocks.
4. Verificar los endpoints HTTP.
5. Ejecutar pruebas de concurrencia contra PostgreSQL real.
6. Permitir medir cobertura de código.
7. Automatizar las verificaciones mediante GitHub Actions.
8. Funcionar en el entorno de desarrollo del equipo.
9. Evitar una infraestructura de pruebas excesivamente compleja.
10. Mantener tiempos de ejecución razonables para la integración continua.

La decisión debía equilibrar confiabilidad, facilidad de mantenimiento y costo de desarrollo.

## 2. Alternativas consideradas

Se analizaron diferentes estrategias y herramientas para verificar la calidad del sistema.

### 2.1 Alternativa A — Pruebas manuales exclusivamente

Consiste en comprobar las funcionalidades utilizando la interfaz o realizando solicitudes individuales a la API.

**Ventajas:**

- No requiere desarrollar una suite automatizada.
- Permite verificar la experiencia del usuario.
- Es útil para revisar formularios, navegación y diseño responsive.
- Facilita detectar problemas visuales.
- Puede utilizarse durante las primeras etapas del desarrollo.

**Desventajas:**

- Requiere repetir manualmente los mismos pasos.
- Los resultados pueden variar entre evaluadores.
- Es difícil reproducir condiciones de carrera.
- No proporciona métricas de cobertura.
- Los errores pueden pasar inadvertidos.
- El costo de repetición aumenta a medida que crece el sistema.
- No permite verificar automáticamente cada cambio publicado en GitHub.

**Motivo de descarte:**

Se consideró insuficiente como estrategia principal para una aplicación con reglas transaccionales y múltiples módulos.

Las pruebas manuales conservan utilidad como complemento, pero no sustituyen la automatización.

### 2.2 Alternativa B — Solo pruebas unitarias

Consiste en comprobar clases, funciones y servicios de manera aislada.

**Ventajas:**

- Generalmente se ejecutan rápidamente.
- Permiten localizar defectos en reglas concretas.
- Facilitan probar situaciones excepcionales.
- Pueden utilizar mocks en lugar de dependencias externas.
- Ayudan a mantener y refactorizar servicios.

**Desventajas:**

- No comprueban por sí solas la configuración completa de NestJS.
- Los mocks pueden representar comportamientos diferentes de los reales.
- No garantizan que las rutas HTTP funcionen correctamente.
- No verifican directamente las restricciones de PostgreSQL.
- No permiten demostrar condiciones reales de concurrencia.
- Pueden pasar aunque existan errores de integración entre componentes.

**Motivo de descarte como estrategia única:**

No resultaba suficiente para comprobar los recorridos completos de FitZone Sports.

Se decidió mantenerlas como base de la estrategia, complementándolas con pruebas de integración y concurrencia.

### 2.3 Alternativa C — Solo pruebas end-to-end

Consiste en comprobar funcionalidades completas mediante solicitudes que atraviesan varias capas del sistema.

**Ventajas:**

- Permiten verificar recorridos reales.
- Comprueban la comunicación entre controladores, servicios y persistencia.
- Pueden detectar problemas que no aparecen en pruebas unitarias.
- Ofrecen evidencia de integración funcional.

**Desventajas:**

- Requieren preparar más infraestructura.
- Son más costosas de mantener.
- Pueden depender de datos específicos.
- Su diagnóstico puede ser más complejo.
- Generalmente son más lentas que las pruebas unitarias.
- No permiten cubrir fácilmente todas las combinaciones posibles de las reglas de negocio.

**Motivo de descarte como estrategia única:**

Se consideró conveniente mantener una mayor cantidad de pruebas de bajo nivel y reservar las pruebas integradas para recorridos y restricciones críticas.

### 2.4 Alternativa D — Estrategia combinada mediante pirámide de pruebas (seleccionada)

Consiste en utilizar diferentes niveles de pruebas según la responsabilidad que se necesita verificar.

La estrategia adoptada incluye:

- Pruebas unitarias para reglas de negocio.
- Pruebas de integración de endpoints.
- Pruebas específicas de concurrencia con PostgreSQL real.
- Verificaciones estáticas y compilación.
- Pruebas manuales complementarias para recorridos visuales.

**Ventajas:**

- Combina rapidez y profundidad.
- Permite localizar defectos en servicios concretos.
- Comprueba recorridos funcionales completos.
- Verifica restricciones reales de base de datos.
- Facilita detectar regresiones.
- Puede ejecutarse automáticamente en GitHub.
- Produce métricas de cobertura y resultados reproducibles.
- Permite mantener un equilibrio entre costo y confiabilidad.

**Desventajas:**

- Requiere mantener distintos tipos de pruebas.
- Es necesario configurar un entorno PostgreSQL para los tests integrados.
- Los cambios de contratos pueden afectar varios tests.
- La cobertura no garantiza ausencia de defectos.
- Pueden existir áreas sin pruebas automatizadas.
- El mantenimiento de los datos de prueba requiere disciplina.

**Evaluación:**

Se seleccionó esta estrategia por ofrecer una combinación adecuada de verificaciones unitarias, funcionales y transaccionales.

## 3. Comparación de alternativas

| Criterio | Solo manual | Solo unitarias | Solo E2E | Estrategia combinada |
|---|---|---|---|---|
| Rapidez para verificar reglas aisladas | Baja | Alta | Media-baja | **Alta** |
| Verificación de endpoints reales | Parcial | No necesariamente | Sí | **Sí** |
| Concurrencia con PostgreSQL | Difícil | No con mocks | Sí | **Sí** |
| Medición de cobertura | No | Sí | Posible | **Sí** |
| Reproducibilidad | Variable | Alta | Alta con entorno preparado | **Alta** |
| Automatización en CI | Baja | Alta | Alta | **Alta** |
| Detección de problemas visuales | Sí | No necesariamente | Depende de herramientas | Manual complementaria |
| Complejidad inicial | Baja | Media | Alta | Media-alta |
| Adecuación al proyecto | Baja | Media | Media | **Alta** |

Los valores corresponden a una evaluación cualitativa para las necesidades de FitZone Sports.

**Resultado:** se eligió una estrategia combinada organizada alrededor de la pirámide de pruebas, con mayor cantidad de verificaciones unitarias y una cantidad menor de pruebas integradas para recorridos críticos.

## 4. Decisión

Se decidió adoptar una **estrategia de pruebas automatizadas basada en la pirámide de pruebas**, utilizando **Vitest** para las pruebas unitarias, **Supertest** para las pruebas HTTP de integración y **PostgreSQL real** para comprobar concurrencia e integridad transaccional.

Además, se estableció un **umbral mínimo de cobertura del 70 %** para sentencias, ramas, funciones y líneas del código incluido en la medición.

Las verificaciones se integraron en GitHub Actions para ejecutarse automáticamente al publicar cambios en las ramas principales o abrir solicitudes de integración.

La elección responde a los siguientes criterios:

1. Verificar rápidamente las reglas del negocio.
2. Detectar regresiones.
3. Aislar servicios mediante mocks.
4. Comprobar la integración real entre módulos.
5. Validar condiciones de carrera en PostgreSQL.
6. Medir la ejecución de código mediante cobertura.
7. Automatizar controles de calidad.
8. Reducir el riesgo de integrar versiones que no compilan.

La estrategia no busca reemplazar completamente las pruebas manuales, sino concentrar la automatización en los comportamientos que pueden expresarse mediante resultados esperados reproducibles.

## 5. Pirámide de pruebas adoptada

La pirámide de pruebas organiza los distintos niveles de verificación según su alcance, velocidad y costo de mantenimiento.

En términos generales, se busca contar con numerosas pruebas unitarias y una cantidad menor de pruebas integradas.

### 5.1 Representación conceptual

```text id="zydd0p"
                  /\
                 /  \
                / UI \
               /Manual\
              /--------\
             /          \
            / Integración\
           / y concurrencia\
          /----------------\
         /                  \
        /  Pruebas unitarias \
       /______________________\
```

La base contiene las pruebas de reglas y componentes aislados.

El nivel intermedio verifica recorridos completos y restricciones transaccionales.

El nivel superior representa comprobaciones de experiencia de usuario que complementan la suite automatizada.

### 5.2 Base — Pruebas unitarias

Se utilizan para verificar funciones y servicios en situaciones controladas.

Por ejemplo:

- Cálculo de tarifas.
- Estados de membresías.
- Validaciones de reservas.
- Reglas de acceso.
- Autenticación.
- Promoción de listas de espera.
- Manejo de pagos simulados.
- Restricciones de roles.

Estas pruebas utilizan frecuentemente dependencias simuladas.

### 5.3 Nivel intermedio — Integración

Se verifica que varios componentes funcionen correctamente al interactuar.

Los tests E2E del backend utilizan una aplicación NestJS y solicitudes HTTP mediante Supertest.

Además, utilizan PostgreSQL para consultar y modificar registros reales.

### 5.4 Nivel intermedio — Concurrencia

La concurrencia requiere un tratamiento especial.

El proyecto incorpora pruebas que envían múltiples solicitudes simultáneas para comprobar reglas de integridad.

Estas pruebas no pueden sustituirse adecuadamente por mocks que simulan respuestas secuenciales.

### 5.5 Nivel superior — Validación de experiencia de usuario

Las funcionalidades del frontend requieren revisar aspectos como:

- Navegación.
- Diseño responsive.
- Formularios.
- Visualización de errores.
- Accesibilidad.
- Lectura de códigos QR.
- Interacciones administrativas.

En el commit de referencia no se identificó una suite automatizada de pruebas de componentes React ni pruebas de navegador con Playwright o Cypress.

Por lo tanto, estas verificaciones constituyen un área de pruebas manuales y de futura automatización.

**La pirámide implementada tiene su mayor desarrollo en el backend.**

## 6. Herramientas seleccionadas

### 6.1 Vitest

Vitest es la herramienta elegida para ejecutar la suite automatizada.

Se integra con TypeScript y permite utilizar funciones como:

```typescript id="qymc7t"
describe()
it()
expect()
vi.fn()
```

Estas funciones facilitan definir escenarios, comprobar resultados y crear objetos simulados.

Vitest se configura mediante:

- `backend/vitest.config.ts`
- `backend/vitest.config.e2e.ts`

### 6.2 Supertest

Supertest permite enviar solicitudes HTTP a la aplicación NestJS durante las pruebas.

Se utiliza para comprobar:

- Códigos de respuesta.
- Autenticación.
- Datos devueltos por endpoints.
- Creación de reservas.
- Pagos.
- Comprobantes.
- Ingresos.
- Errores de concurrencia.

### 6.3 NestJS Testing

El paquete `@nestjs/testing` permite construir instancias de módulos de prueba.

Esto facilita levantar una aplicación representativa del backend y recuperar sus proveedores.

### 6.4 PostgreSQL

Para los tests de integración y concurrencia se utiliza una instancia real de PostgreSQL.

Esto permite verificar comportamientos que dependen de:

- Transacciones.
- Restricciones de integridad.
- Índices únicos parciales.
- Relaciones entre entidades.
- Migraciones.

### 6.5 Prisma ORM

Prisma se utiliza para preparar, consultar y limpiar datos de prueba.

También permite comprobar los efectos reales de determinadas operaciones sobre PostgreSQL.

### 6.6 V8 Coverage

Vitest utiliza el proveedor `v8` para producir métricas de cobertura.

Los reportes configurados son:

- Texto.
- LCOV.
- Resumen JSON.

### 6.7 Oxlint y compiladores

El proyecto incorpora controles complementarios:

- Oxlint para análisis estático.
- Nest CLI para compilar el backend.
- TypeScript para verificar tipos.
- Vite para construir el frontend.

Estas herramientas no reemplazan a los tests, pero ayudan a detectar problemas antes de ejecutar la aplicación.

## 7. Alternativas consideradas para las herramientas de prueba

Además de seleccionar la pirámide, se compararon herramientas concretas.

### 7.1 Vitest frente a Jest

**Vitest — Seleccionado**

Ventajas:

- Integración con el ecosistema TypeScript.
- Ejecución de suites automatizadas.
- Herramientas para mocks.
- Soporte de cobertura.
- Configuración adecuada para el proyecto.
- Posibilidad de ejecutar pruebas específicas.

Desventajas:

- Requiere configurar apropiadamente las transformaciones y los imports.
- Las migraciones entre versiones pueden necesitar ajustes.
- Los entornos de integración deben prepararse por separado.

**Jest — Alternativa considerada**

Ventajas:

- Amplia adopción en proyectos NestJS.
- Documentación y ejemplos abundantes.
- Sistema de mocks consolidado.
- Soporte de cobertura y herramientas de prueba.

Desventajas para el proyecto:

- Requería mantener una configuración diferente de la tecnología seleccionada.
- No proporcionaba una ventaja decisiva que justificara reemplazar Vitest.

**Motivo de selección:**

Se consideró que Vitest ofrecía las funcionalidades necesarias y era compatible con la organización elegida para las pruebas TypeScript del backend.

### 7.2 Supertest frente a pruebas HTTP manuales

Se seleccionó Supertest para automatizar solicitudes HTTP durante las pruebas de integración.

Las herramientas manuales, como Postman o un navegador, continúan siendo útiles para exploración y depuración.

Sin embargo, Supertest permite registrar las expectativas como código y ejecutarlas repetidamente.

### 7.3 PostgreSQL real frente a base de datos simulada

**PostgreSQL real — Seleccionado para integración**

Permite comprobar índices, restricciones, transacciones y condiciones de carrera.

**Base simulada — Utilizada indirectamente en unitarias mediante mocks**

Permite aislar las reglas del servicio y ejecutar pruebas rápidamente.

La decisión final no excluye ninguno de los enfoques: utiliza mocks donde resultan adecuados y PostgreSQL real cuando se necesita comprobar el comportamiento efectivo de la persistencia.

## 9. Pruebas de Strategy

El módulo de Canchas aplica el patrón Strategy para calcular precios.

Las pruebas permiten verificar las reglas de manera aislada y comprobar su composición.

### 9.1 Escenarios comprobados

Entre los casos implementados se encuentran:

- Cliente externo en horario normal.
- Socio activo en horario normal.
- Cliente externo en horario pico.
- Socio activo en horario pico.
- Socio sin membresía activa.
- Incorporación de una estrategia adicional.
- Prevención de montos finales negativos.

### 9.2 Ejemplo de prueba

El archivo:

`backend/src/canchas/pricing/pricing.service.spec.ts`

incluye una prueba representativa:

```typescript id="cf9sgg"
it('socio activo en horario pico: combina descuento y recargo', () => {
  const resultado = crearService().calcular(
    ctx({
      esSocioActivo: true,
      horaInicio: 20,
    }),
  );

  expect(resultado).toMatchObject({
    precio_base: 10000,
    descuento: 1500,
    recargo: 2000,
    monto_total: 10500,
  });
});
```

La prueba comprueba que se apliquen conjuntamente el descuento del 15 % y el recargo pico del 20 %.

### 9.3 Extensibilidad

También existe un caso que incorpora una estrategia adicional llamada `RecargoFeriado` dentro de la propia prueba.

Esto permite comprobar que el servicio puede aceptar una nueva estrategia sin modificar su implementación principal.

### 9.4 Beneficio

Las pruebas del patrón Strategy permiten incorporar reglas comerciales y detectar regresiones en los cálculos existentes.

## 10. Pruebas de Observer

El módulo Clases utiliza Observer para reaccionar ante la liberación de un cupo.

El comportamiento principal consiste en promover a un usuario desde la lista de espera.

### 10.1 Componentes evaluados

Las pruebas se relacionan con:

- `CupoLiberadoSubject`.
- `ListaEsperaObserver`.
- `ClasesService`.
- Repositorios y colaboradores simulados.

### 10.2 Escenario

Un usuario cancela una reserva confirmada.

El sistema libera un cupo y notifica a los observadores correspondientes.

El observador consulta la lista de espera y promueve al primer usuario elegible.

### 10.3 Regla FIFO

El orden esperado sigue la política:

**First In, First Out.**

Se prioriza la solicitud más antigua de la lista de espera.

### 10.4 Beneficio

Las pruebas permiten verificar que el mecanismo Observer actúe conforme a la regla prevista y que los cambios en el módulo Clases no rompan la promoción automática.

## 11. Pruebas de integración

Las pruebas de integración comprueban recorridos que atraviesan distintas capas y módulos.

El archivo principal es:

`backend/test/flujos.e2e-spec.ts`

Utiliza:

- NestJS Testing.
- Supertest.
- Prisma.
- PostgreSQL.

Se implementaron tres recorridos integrados principales.

### 11.1 Flujo 1 — Reserva de cancha, pago y comprobante

El recorrido evalúa:

1. Autenticación del usuario.
2. Solicitud de reserva de cancha.
3. Registro de la reserva.
4. Cálculo y consulta del monto.
5. Simulación de pago.
6. Confirmación del resultado.
7. Descarga del comprobante PDF.

El test comprueba que el pago termine en estado:

```text id="dy4uuo"
APROBADO
```

También verifica que el token de pasarela responda al formato esperado.

La descarga del comprobante debe producir una respuesta con tipo de contenido PDF.

El archivo se comprueba mediante su cabecera:

```text id="muqhfn"
%PDF-1.4
```

### 11.2 Flujo 2 — Clase y lista de espera

Este recorrido evalúa:

1. Reserva de un socio.
2. Inscripción de otro usuario cuando no hay cupos.
3. Incorporación a la lista de espera.
4. Cancelación de la primera reserva.
5. Liberación del cupo.
6. Promoción automática del usuario pendiente.

Se espera que la reserva inicial esté `CONFIRMADA`.

El segundo usuario debe ingresar en estado `EN_ESPERA`.

Después de la cancelación, se comprueba la promoción mediante Observer.

### 11.3 Flujo 3 — Acceso QR

Este recorrido evalúa:

1. Generación del QR dinámico.
2. Validación de ingreso.
3. Registro del acceso.
4. Consulta del aforo.
5. Registro de egreso.

La prueba verifica que el QR informe una validez de 60 segundos.

También comprueba que el ingreso resulte autorizado y que finalmente se registre el egreso.

### 11.4 Valor de las pruebas integradas

Estos casos permiten verificar que las funcionalidades no solamente se comporten correctamente de manera aislada, sino que también puedan completar operaciones reales entre módulos.

## 12. Pruebas de concurrencia

El sistema incorpora pruebas específicas de concurrencia en:

`backend/test/concurrencia.e2e-spec.ts`

Estas pruebas son especialmente importantes porque verifican reglas que no pueden demostrarse completamente mediante respuestas simuladas.

### 12.1 RN-02 — Prevención de sobreventa

La prueba envía doce solicitudes simultáneas para reservar el mismo turno.

Se utiliza:

```typescript id="p1phuh"
const N = 12;

const respuestas = await Promise.all(
  Array.from({ length: N }, () =>
    request(app.getHttpServer())
      .post('/canchas/reserva')
      .set('Authorization', `Bearer ${tokenSocio}`)
      .send(payload),
  ),
);
```

### 12.2 Criterio de aceptación

El resultado esperado es:

| Resultado HTTP | Cantidad |
|---|---:|
| `201 Created` | 1 |
| `409 Conflict` | 11 |
| Total | 12 |

Las aserciones principales son:

```typescript id="t8yq49"
expect(creadas).toHaveLength(1);
expect(conflictos).toHaveLength(N - 1);
```

Este escenario demuestra que las operaciones concurrentes no deberían confirmar reservas incompatibles.

### 12.3 RN-01 — Accesos simultáneos

La segunda prueba intenta registrar al mismo usuario en dos sedes distintas al mismo tiempo.

El resultado esperado es:

- Un ingreso autorizado.
- Un ingreso rechazado mediante `409 Conflict`.

### 12.4 PostgreSQL real

Las pruebas se ejecutan sobre una base de datos PostgreSQL.

De esta manera se verifica la intervención de los índices únicos parciales definidos en las migraciones.

### 12.5 Importancia de la decisión

Una prueba con mocks puede representar el comportamiento esperado del repositorio, pero no demostrar cómo responde PostgreSQL cuando varias transacciones compiten por la misma restricción.

Por eso se decidió conservar pruebas específicas sobre el motor real.

### 13.2 Cobertura de sentencias

**Statements** representa el porcentaje de sentencias instrumentadas que fueron ejecutadas por las pruebas.

### 13.3 Cobertura de ramas

**Branches** representa el porcentaje de alternativas instrumentadas de decisión que fueron ejecutadas.

### 13.4 Cobertura de funciones

**Functions** indica qué proporción de las funciones incluidas en la medición fue ejecutada.

### 13.5 Cobertura de líneas

**Lines** expresa el porcentaje de líneas instrumentadas ejecutadas durante las pruebas.

### 13.6 Interpretación del umbral

El pipeline exige que cada uno de los cuatro indicadores alcance al menos el 70 %.

No resulta suficiente superar el promedio general si alguno de los indicadores queda por debajo del mínimo.

### 13.7 Alcance de la medición

La configuración excluye distintos tipos de archivos.

Por ejemplo:

- Controladores.
- Repositorios.
- Módulos NestJS.
- DTO.
- Decoradores.
- Configuración de rutas.
- Archivos relacionados con Prisma.
- Archivos de documentación Swagger.

Esto permite concentrar la medición en un subconjunto de código de aplicación, especialmente en reglas y servicios.

Sin embargo, significa que **el resultado no representa la cobertura total de todo el backend**.

Tampoco mide la cobertura del frontend React.

Por lo tanto, debe informarse siempre el porcentaje junto con su alcance real.

## 18. Interpretación de fallos

Las herramientas pueden detectar diferentes categorías de problemas.

### 18.1 Error de compilación

Se produce cuando el código no puede construirse correctamente.

Por ejemplo:

- Un import inexistente.
- Un tipo incompatible.
- Una propiedad no declarada.
- Una llamada a un método que no existe.

### 18.2 Error de prueba unitaria

Ocurre cuando el comportamiento real de una función o servicio no coincide con el resultado esperado.

Puede indicar una modificación incorrecta de la lógica de negocio o una prueba desactualizada.

### 18.3 Error de integración

Puede deberse a:

- Ruta HTTP incorrecta.
- DTO incompatible.
- Error de autenticación.
- Respuesta diferente de la esperada.
- Falta de datos de prueba.
- Problema en una relación de base de datos.

### 18.4 Error de concurrencia

Se produce cuando el comportamiento ante solicitudes simultáneas no coincide con la regla esperada.

Por ejemplo, si dos reservas sobre el mismo turno obtuvieran éxito, se incumpliría RN-02.

### 18.5 Cobertura insuficiente

Se produce cuando uno de los indicadores queda por debajo del umbral configurado.

La solución debe buscarse incorporando pruebas relevantes, no ejecutando código artificialmente sin verificar resultados.

### 18.6 Error de entorno

Las pruebas integradas pueden fallar por:

- PostgreSQL inaccesible.
- Variables de entorno incorrectas.
- Migraciones ausentes.
- Datos de prueba incompletos.
- Dependencias no instaladas.

Es necesario diferenciar estos problemas de los defectos reales de las reglas de negocio.

## 20. Consecuencias de la decisión

### 20.1 Consecuencias positivas

**Detección temprana de errores**

Los tests permiten identificar defectos antes de que afecten otros módulos.

**Reducción de regresiones**

Una funcionalidad previamente verificada puede comprobarse nuevamente después de incorporar cambios.

**Mayor confianza en la integración**

Supertest permite verificar recorridos que atraviesan controladores, servicios y persistencia.

**Verificación de concurrencia real**

PostgreSQL participa en los escenarios donde deben cumplirse restricciones de integridad.

**Mantenimiento facilitado**

Las pruebas permiten modificar y refactorizar servicios con mayor seguridad.

**Cobertura cuantificable**

Los indicadores de V8 ayudan a identificar áreas insuficientemente ejercitadas.

**Automatización**

GitHub Actions ejecuta controles sin depender de que cada integrante recuerde hacerlo manualmente.

**Evidencia verificable**

Los resultados quedan asociados con una ejecución, una fecha y un commit concreto.

**Reproducibilidad**

Los comandos permiten repetir las verificaciones en otros entornos preparados correctamente.

**Apoyo a la documentación**

Los tests ayudan a demostrar las reglas y decisiones explicadas en los ADR.

### 20.2 Consecuencias negativas

**Tiempo de desarrollo**

Es necesario escribir y mantener código de prueba.

**Costo de mantenimiento**

Cuando cambia una regla o contrato, los tests asociados pueden necesitar modificaciones.

**Dependencia de datos de prueba**

Los recorridos E2E requieren una base con registros apropiados.

**Infraestructura de integración**

Las pruebas de concurrencia necesitan PostgreSQL real.

**Ejecución adicional en CI**

Cada cambio genera una ejecución que consume tiempo y recursos.

**Cobertura imperfecta**

Un porcentaje elevado no demuestra que todas las reglas hayan sido verificadas.

**Riesgo de mocks inadecuados**

Las pruebas unitarias pueden aprobar aunque el comportamiento real de la persistencia sea diferente.

**Limitaciones del frontend**

La estrategia actual no incluye una suite automatizada de componentes o navegador.

**Necesidad de interpretar resultados**

Un test fallido puede representar un defecto real, una configuración incorrecta o una expectativa desactualizada.

### 20.3 Deuda técnica asumida

La decisión deja pendientes las siguientes mejoras:

- Automatizar pruebas de componentes React.
- Incorporar pruebas de navegador.
- Ampliar pruebas de autorización entre sedes.
- Evaluar cobertura sobre controladores y repositorios.
- Fortalecer las pruebas de almacenamiento y sincronización offline.
- Incorporar pruebas de rendimiento bajo carga.
- Reducir la dependencia de determinados datos semilla.
- Mejorar las pruebas de fallas parciales y recuperación.
- Incorporar comprobaciones de accesibilidad.
- Ampliar la protección automatizada frente a errores de seguridad.

Estas mejoras representan oportunidades de evolución y no se declaran implementadas.

## 24. Conclusión

Se decidió adoptar una **estrategia de pruebas automatizadas basada en la pirámide de pruebas**, combinando verificaciones unitarias, pruebas de integración y escenarios específicos de concurrencia.

Se seleccionó Vitest por su compatibilidad con TypeScript y sus herramientas de ejecución, mocks y cobertura.

Para comprobar los recorridos HTTP se incorporó Supertest junto con las herramientas de pruebas de NestJS.

Las reglas críticas de concurrencia se verifican utilizando PostgreSQL real, porque sus restricciones de integridad no pueden validarse completamente mediante dependencias simuladas.

La estrategia también establece un umbral mínimo de cobertura del 70 % para sentencias, ramas, funciones y líneas del conjunto de código incluido en la medición.

La ejecución del commit `4cf36214838b255337fbdeb7d47b42db1d6d70a7`, realizada el 19 de noviembre de 2026, registró 112 pruebas unitarias y cinco pruebas E2E aprobadas.

Los cuatro indicadores de cobertura superaron el mínimo establecido.

Asimismo, los tres trabajos del pipeline de GitHub Actions finalizaron exitosamente.

La decisión ofrece ventajas relevantes: permite detectar errores, reducir regresiones, verificar reglas de concurrencia, automatizar controles y conservar evidencia reproducible.

Como contrapartida, requiere mantener los tests, preparar entornos de integración y reconocer que la cobertura no demuestra ausencia absoluta de defectos.

La principal deuda técnica identificada consiste en ampliar las pruebas automatizadas del frontend, fortalecer determinados escenarios de seguridad y aumentar el alcance de las verificaciones de integración.

Por lo tanto, se considera que la estrategia adoptada ofrece un equilibrio adecuado entre **calidad, automatización, costo de mantenimiento y capacidad de verificación** para el Trabajo Integrador Final.

**Decisión final: mantener Vitest como herramienta principal de pruebas, utilizar Supertest y PostgreSQL real para integración y concurrencia, aplicar un umbral mínimo de cobertura del 70 % y ejecutar las verificaciones mediante GitHub Actions como parte del proceso de integración del proyecto.**
