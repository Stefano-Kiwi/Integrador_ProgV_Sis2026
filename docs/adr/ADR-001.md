# ADR-001 — Adopción de una arquitectura de monolito modular

**Estado:** Aceptado  
**Fecha de registro:** 19 de noviembre de 2026  
**Proyecto:** FitZone Sports — Trabajo Integrador Final  
**Equipo:** 12  
**Unidad temática:** Unidad I — Arquitectura de Software  
**Requisitos relacionados:** RN-02 y RNF-04

---

## 1. Contexto

FitZone Sports es una plataforma de gestión integral destinada a una cadena de gimnasios y complejos deportivos con múltiples sedes.

El sistema debe administrar usuarios, membresías, ingresos mediante códigos QR, clases grupales, reservas de canchas deportivas y pagos simulados.

Estos módulos presentan relaciones directas entre sí. Por ejemplo, para reservar una cancha es necesario identificar al usuario, determinar su condición de socio, consultar la disponibilidad, calcular el precio correspondiente y registrar la reserva.

Asimismo, determinadas operaciones requieren mantener consistencia entre distintos datos del sistema. Un caso fundamental es la **regla de negocio RN-02**, que establece que no pueden confirmarse dos reservas activas para una misma cancha, fecha y horario.

Por otra parte, el requisito no funcional **RNF-04** contempla la incorporación de nuevas sedes y el crecimiento de la cantidad de usuarios y operaciones.

Durante la definición de la arquitectura fue necesario seleccionar un estilo que permitiera:

- Separar las responsabilidades de los distintos módulos funcionales.
- Mantener la integridad y consistencia de las operaciones.
- Facilitar el trabajo paralelo entre los integrantes.
- Reducir la complejidad de configuración y despliegue.
- Permitir la incorporación de nuevas funcionalidades.
- Favorecer las pruebas automatizadas y el mantenimiento del código.
- Brindar una base que pueda evolucionar ante futuros requerimientos.

Debido al alcance académico del proyecto, al tamaño del equipo y a la integración entre las reglas de negocio, se consideró necesario equilibrar la modularidad con la simplicidad operativa.

## 2. Decisión

Se decidió implementar FitZone Sports utilizando una arquitectura de **monolito modular**, desarrollada con NestJS sobre Node.js y TypeScript.

En este enfoque, el backend funciona como una única aplicación ejecutable, pero organiza su código en módulos que representan las principales áreas funcionales del negocio.

Los módulos implementados incluyen:

| Módulo | Responsabilidad |
|---|---|
| Usuarios | Registro, perfiles y administración de usuarios |
| Autenticación | Inicio de sesión, JWT y autorización por roles |
| Sedes | Administración de sucursales deportivas |
| Planes y membresías | Contratación, renovación y estados de membresías |
| Acceso | Generación y validación de QR, ingresos, egresos y aforo |
| Clases | Programación de clases, reservas y listas de espera |
| Canchas | Instalaciones, disponibilidad, reservas y tarifas dinámicas |
| Pagos | Pagos simulados y comprobantes PDF |
| Prisma | Acceso centralizado a PostgreSQL |

Cada módulo utiliza componentes de NestJS para organizar sus responsabilidades:

**Controladores:** reciben las solicitudes HTTP y exponen los endpoints correspondientes.

**Servicios:** contienen las reglas de negocio y coordinan las operaciones funcionales.

**Repositorios:** encapsulan las consultas y modificaciones de datos mediante Prisma ORM.

**Módulos NestJS:** registran controladores, proveedores y dependencias, permitiendo organizar la aplicación mediante inyección de dependencias.

La persistencia se centraliza en una base de datos PostgreSQL compartida por los módulos.

El frontend se desarrolla como una aplicación React con TypeScript, separada del backend y comunicada mediante una API REST.

Esta decisión permite mantener una separación clara entre presentación, lógica de negocio y persistencia, sin asumir los costos de coordinación de múltiples servicios independientes.

### 2.1 Organización arquitectónica

La arquitectura puede resumirse de la siguiente manera:

```text
                       USUARIOS
                          |
                          v
               FRONTEND REACT
            Portal Socio / Admin
                          |
                       HTTP/JSON
                          |
                          v
                 API NESTJS
                Monolito Modular
                          |
          +---------------+---------------+
          |               |               |
       Usuarios         Acceso           Clases
          |               |               |
        Sedes           Canchas          Pagos
          |               |               |
          +---------------+---------------+
                          |
                    Prisma ORM
                          |
                          v
                     PostgreSQL
```

Este esquema representa una vista conceptual de los módulos; las conexiones entre ellos no indican necesariamente dependencias directas de código.

La aplicación utiliza un módulo raíz, `AppModule`, encargado de registrar los módulos funcionales.

### 2.2 Separación de responsabilidades

La modularidad se mantiene mediante la organización por funcionalidades, evitando concentrar toda la lógica del negocio en un único archivo o controlador.

Por ejemplo:

- `CanchasController` recibe operaciones relacionadas con canchas.
- `CanchasService` aplica reglas de disponibilidad, reservas y precios.
- `CanchasRepository` realiza las operaciones de persistencia.

Esta separación también se utiliza en módulos como Clases, Usuarios y Acceso.

La arquitectura incorpora los patrones de diseño Strategy, Observer y Repository para resolver necesidades específicas.

La aplicación de estos patrones permite mejorar la extensibilidad sin modificar el estilo arquitectónico general.

## 3. Alternativas consideradas

Se analizaron cuatro alternativas para organizar el backend: monolito modular, microservicios, arquitectura orientada a servicios (SOA) y arquitectura serverless.

### 3.1 Alternativa A — Monolito modular (seleccionada)

Consiste en construir una única aplicación backend dividida en módulos funcionales con responsabilidades diferenciadas.

**Ventajas:**

- Simplifica el desarrollo y las pruebas de integración.
- Permite compartir mecanismos de autenticación, autorización y persistencia.
- Facilita el uso de transacciones sobre una misma base PostgreSQL.
- Reduce la complejidad de configuración y despliegue.
- Evita introducir comunicación distribuida entre módulos internos.
- Permite aprovechar la inyección de dependencias de NestJS.
- Resulta adecuada para el tamaño y la experiencia del equipo.
- Reduce los costos de infraestructura durante el desarrollo académico.

**Desventajas:**

- Los módulos comparten un mismo proceso y ciclo de despliegue.
- Un error grave en un componente puede afectar a toda la aplicación.
- El escalado de la aplicación normalmente implica replicar el backend completo.
- La base de datos compartida puede generar acoplamiento entre módulos.
- Una modularidad mal aplicada puede producir dependencias circulares o código difícil de mantener.

**Evaluación:**

Se consideró la opción más adecuada para FitZone Sports porque permite conservar las ventajas de una arquitectura organizada sin introducir complejidad distribuida innecesaria.

### 3.2 Alternativa B — Microservicios

Consiste en dividir el sistema en múltiples servicios independientes, por ejemplo:

- Servicio de usuarios y autenticación.
- Servicio de membresías.
- Servicio de acceso.
- Servicio de clases.
- Servicio de canchas.
- Servicio de pagos.

Cada servicio podría tener su propio despliegue y, según la arquitectura adoptada, su propia base de datos.

**Ventajas:**

- Permite desplegar componentes de manera independiente.
- Facilita escalar únicamente los servicios con mayor demanda.
- Favorece el aislamiento de determinados fallos.
- Permite que diferentes equipos evolucionen servicios sin coordinar todos los despliegues.

**Desventajas:**

- Requiere administrar comunicación entre servicios.
- Incrementa la complejidad del despliegue y monitoreo.
- Puede necesitar mensajería, descubrimiento de servicios y mecanismos de tolerancia a fallos.
- Las operaciones distribuidas requieren estrategias adicionales para conservar la consistencia de los datos.
- Aumenta la complejidad de las pruebas de integración.
- Introduce costos de infraestructura y mantenimiento superiores.

**Motivo de descarte:**

Para el tamaño actual del equipo y el alcance del proyecto, la independencia de despliegue no justificaba el esfuerzo adicional.

Además, las operaciones relacionadas con reservas, membresías y pagos presentan dependencias que se resuelven de manera más sencilla dentro de una misma aplicación y base de datos.

Se consideró que adoptar microservicios desde el comienzo habría aumentado el riesgo de retrasos y errores de integración sin aportar beneficios proporcionales.

### 3.3 Alternativa C — Arquitectura orientada a servicios (SOA)

SOA organiza las funcionalidades como servicios reutilizables que se comunican mediante contratos definidos y mecanismos de integración.

**Ventajas:**

- Favorece la interoperabilidad.
- Permite reutilizar funcionalidades entre distintos sistemas.
- Resulta apropiada para organizaciones con múltiples aplicaciones empresariales.
- Facilita integrar sistemas construidos con diferentes tecnologías.

**Desventajas:**

- Puede requerir infraestructura adicional de integración.
- Introduce complejidad de contratos, mensajería y gobierno de servicios.
- Puede incrementar la latencia de operaciones que atraviesan múltiples servicios.
- Su administración resulta más costosa para un sistema de alcance acotado.

**Motivo de descarte:**

FitZone Sports no necesitaba integrar múltiples sistemas empresariales independientes.

El alcance principal consistía en construir una plataforma unificada, por lo que los beneficios de SOA no justificaban su complejidad adicional.

### 3.4 Alternativa D — Arquitectura serverless

Consiste en ejecutar las funcionalidades del backend mediante funciones administradas por un proveedor de infraestructura, generalmente activadas por eventos o solicitudes HTTP.

**Ventajas:**

- Escalado administrado por la plataforma.
- Menor necesidad de administrar servidores directamente.
- Posibilidad de pagar según consumo.
- Adecuada para procesos independientes y determinadas cargas variables.

**Desventajas:**

- Puede presentar latencia de inicio en determinadas configuraciones.
- Requiere adaptar los componentes al modelo de ejecución del proveedor.
- Puede incrementar la dependencia de servicios específicos de la plataforma.
- Las conexiones y transacciones con bases relacionales necesitan especial consideración.
- El procesamiento de operaciones prolongadas o coordinadas puede resultar más complejo.
- Dificulta reproducir un entorno idéntico sin infraestructura o emuladores adicionales.

**Motivo de descarte:**

El proyecto requería una API REST integrada, operaciones transaccionales y un entorno de demostración reproducible mediante Docker.

Se priorizó una solución que pudiera ejecutarse localmente y que no dependiera del despliegue en una plataforma cloud específica.

## 4. Comparación de alternativas

| Criterio | Monolito modular | Microservicios | SOA | Serverless |
|---|---|---|---|---|
| Complejidad inicial | Baja-media | Alta | Alta | Media |
| Despliegue local | Sencillo | Complejo | Complejo | Variable |
| Consistencia transaccional | Sencilla con BD compartida | Requiere coordinación | Requiere coordinación | Depende del diseño |
| Escalado independiente | Limitado | Alto | Posible | Alto por función |
| Mantenimiento de infraestructura | Bajo-medio | Alto | Alto | Parcialmente administrado |
| Adecuación al equipo | Alta | Media-baja | Baja | Media |
| Adecuación al TIF | **Alta** | Media-baja | Baja | Media |

Los valores de esta tabla son una evaluación cualitativa del equipo para el alcance de FitZone Sports, no resultados de una medición de rendimiento.

A partir de esta comparación, se seleccionó el **monolito modular** por ofrecer el equilibrio más favorable entre simplicidad, consistencia, modularidad y mantenibilidad.

## 5. Consecuencias

### 5.1 Consecuencias positivas

**Organización del desarrollo**

Los módulos permiten dividir el trabajo entre los integrantes sin que todos deban intervenir permanentemente sobre los mismos archivos.

**Mantenimiento**

La separación entre controladores, servicios y repositorios facilita localizar problemas y modificar funcionalidades concretas.

**Integridad transaccional**

La utilización de PostgreSQL y Prisma dentro de una misma aplicación simplifica el control de operaciones que afectan varias entidades.

En el módulo de Canchas, la base de datos utiliza restricciones de unicidad para evitar reservas activas duplicadas, conforme a RN-02.

**Pruebas automatizadas**

Los servicios pueden probarse de manera aislada mediante dobles de prueba.

También pueden ejecutarse pruebas de integración sobre una aplicación NestJS completa y una instancia real de PostgreSQL.

**Reutilización de componentes**

La inyección de dependencias y los patrones de diseño permiten incorporar nuevas funcionalidades sin duplicar reglas comunes.

**Despliegue simplificado**

Al existir un único backend, no se necesita configurar una plataforma de comunicación entre múltiples microservicios.

### 5.2 Consecuencias negativas

**Despliegue conjunto**

Una modificación del módulo de Clases puede requerir reconstruir y desplegar el backend completo, incluso si los demás módulos no cambiaron.

**Escalabilidad menos granular**

Ante un aumento importante de demanda en Canchas, la estrategia inicial de escalado consiste en replicar instancias de la API completa, no únicamente ese módulo.

**Riesgo de acoplamiento**

El uso de una base de datos y un proceso compartidos facilita que los módulos desarrollen dependencias innecesarias.

Es necesario conservar la separación de responsabilidades para evitar que el sistema evolucione hacia un monolito difícil de mantener.

**Impacto compartido de fallos**

Un error que comprometa el proceso principal del servidor puede afectar simultáneamente distintas funcionalidades.

**Disciplina arquitectónica**

La modularidad requiere revisiones de código, pruebas y convenciones claras. La estructura de carpetas por sí sola no garantiza un bajo acoplamiento.

## 6. Relación con los requisitos del proyecto

### RN-02 — Prevención de sobreventa de canchas

La arquitectura elegida permite coordinar consultas y reservas dentro de un mismo backend y utilizar PostgreSQL como garantía final de integridad.

La regla de no sobreventa se respalda mediante un índice único parcial sobre cancha, fecha y horario para reservas no canceladas.

Esta garantía depende de PostgreSQL y del diseño de persistencia; no es una propiedad automática del monolito modular.

### RNF-04 — Escalabilidad y alta de nuevas sedes

La información de las sedes se administra mediante registros persistidos en la base de datos.

El módulo Sedes permite registrar nuevas sucursales mediante la API sin necesitar crear un servicio de software independiente por cada sede.

La incorporación de una sede no requiere cambiar la estructura de módulos del backend.

Respecto del crecimiento de la carga, el diseño permite considerar el escalado mediante múltiples instancias de la API y una base de datos compartida.

La capacidad real de escalado horizontal deberá demostrarse mediante pruebas e infraestructura adecuadas; la elección arquitectónica por sí sola no certifica un nivel de rendimiento.

## 8. Evolución futura de la decisión

La elección del monolito modular no impide que el sistema evolucione hacia una arquitectura distribuida.

Si FitZone Sports necesitara escalar considerablemente, incorporar equipos independientes o desplegar determinadas funcionalidades por separado, podría evaluarse la extracción de módulos específicos.

Una posible candidata sería la gestión de pagos o una funcionalidad de notificaciones externas, siempre que se definieran contratos y mecanismos de consistencia adecuados.

Antes de realizar esa separación, sería necesario:

1. Medir la carga y los cuellos de botella reales.
2. Identificar las dependencias entre módulos.
3. Definir contratos de comunicación.
4. Establecer cómo se conservaría la consistencia de los datos.
5. Evaluar el costo adicional de despliegue y monitoreo.
6. Registrar una nueva decisión arquitectónica mediante otro ADR.

En caso de reemplazar esta decisión, el ADR-001 debería conservarse como parte del historial y cambiar su estado a **«Reemplazado por ADR-XXX»**.

---

## 9. Conclusión

Se adoptó una arquitectura de **monolito modular con NestJS** porque responde adecuadamente a las necesidades actuales de FitZone Sports y al alcance del Trabajo Integrador Final.

Esta decisión permitió organizar las funcionalidades en módulos diferenciados, centralizar las reglas de negocio, compartir los mecanismos de autenticación y persistencia, y simplificar el desarrollo y las pruebas.

La alternativa de microservicios ofrecía mayores posibilidades de escalado y despliegue independiente, pero incorporaba una complejidad de coordinación e infraestructura que no se consideró necesaria para el proyecto.

SOA y serverless también presentaban ventajas en contextos específicos, pero no ofrecían un beneficio suficiente frente a los requisitos de integración, consistencia y reproducción local.

El monolito modular representa, por lo tanto, una solución equilibrada entre **simplicidad operativa, modularidad, mantenibilidad y capacidad de evolución**.

**Decisión final: mantener la arquitectura de monolito modular durante el desarrollo y la entrega de FitZone Sports.**
