**Estado:** Aceptado  
**Fecha de registro:** 19 de noviembre de 2026  
**Proyecto:** FitZone Sports — Trabajo Integrador Final  
**Equipo:** 12  
**Unidad temática:** Unidad IV — Frameworks frontend, componentes y estado de aplicación  
**Decisiones relacionadas:** ADR-001 — Monolito modular; ADR-005 — Framework backend y persistencia  
**Requisitos relacionados:** RF-01 a RF-14, RF-03, RF-04, RF-10, RF-11 y RNF-01

## 1. Contexto

FitZone Sports es una plataforma de gestión deportiva destinada a una cadena de gimnasios y complejos deportivos con múltiples sedes.

La aplicación necesita ofrecer interfaces para diferentes tipos de usuarios, incluyendo socios, clientes externos, instructores, gerentes y administradores.

Cada perfil dispone de necesidades específicas.

Los socios necesitan consultar su membresía, obtener su código QR de acceso, visualizar clases disponibles, reservar canchas, efectuar pagos simulados y administrar sus datos personales.

Por otra parte, el personal administrativo necesita gestionar usuarios, sedes, clases, canchas, membresías, pagos y operaciones de control de acceso.

Estas funcionalidades requieren una interfaz que permita presentar información dinámica, reaccionar ante las acciones del usuario y comunicarse con el backend mediante solicitudes HTTP.

Durante el diseño del frontend fue necesario seleccionar una tecnología que permitiera mantener una estructura organizada, reutilizar componentes y administrar información compartida entre distintas pantallas.

### 1.1 Problema identificado

Una aplicación con numerosas pantallas puede presentar problemas importantes cuando se desarrolla sin una arquitectura frontend definida.

Entre ellos se encuentran:

- Repetición de botones, formularios y elementos visuales.
- Inconsistencias entre distintas pantallas.
- Dificultad para mantener el estado de autenticación.
- Uso excesivo de variables compartidas o manipulación directa del DOM.
- Duplicación de consultas al backend.
- Dependencias difíciles de identificar entre componentes.
- Problemas al mantener sincronizada la sede seleccionada.
- Complejidad al adaptar las interfaces a dispositivos móviles.
- Falta de claridad sobre qué usuario puede acceder a cada pantalla.
- Dificultad para actualizar la interfaz cuando cambian los datos.

Estos riesgos resultan especialmente relevantes para FitZone Sports porque la aplicación incluye un portal público, un portal para socios autenticados y una consola administrativa.

### 1.2 Necesidades técnicas

Se establecieron las siguientes necesidades:

1. Desarrollar interfaces dinámicas y responsivas.
2. Reutilizar componentes visuales entre distintas pantallas.
3. Mantener una separación clara entre presentación y comunicación HTTP.
4. Facilitar la navegación sin recargar completamente la página.
5. Administrar la autenticación del usuario.
6. Mantener información global como la sede seleccionada.
7. Conocer el estado de conectividad de la aplicación.
8. Mostrar estados de carga, éxito y error.
9. Permitir la construcción progresiva de los módulos.
10. Mantener compatibilidad con la API REST de NestJS.
11. Utilizar TypeScript para mejorar la consistencia de los contratos.
12. Reducir la incorporación de dependencias que no fueran necesarias para el alcance del proyecto.

La decisión debía considerar tanto el framework frontend como la organización de los componentes y el mecanismo de estado global.

## 2. Decisión

Se decidió utilizar **React con TypeScript** para desarrollar la interfaz web de FitZone Sports, utilizando **Vite** como herramienta de desarrollo y compilación.

La aplicación se implementa como una **Single Page Application (SPA)**, en la que la navegación y la actualización de las vistas se administran desde el navegador.

Para organizar los elementos visuales se adoptó una **librería propia de componentes reutilizables**, inspirada en Atomic Design.

Para gestionar la información compartida se seleccionó **React Context API junto con `useReducer`**, complementados por estados locales mediante `useState`.

La navegación entre pantallas se implementa utilizando React Router.

### 2.1 Tecnologías seleccionadas

| Componente | Tecnología | Función |
|---|---|---|
| Biblioteca de interfaces | React | Construcción de vistas mediante componentes |
| Lenguaje | TypeScript | Tipado de datos, componentes y servicios |
| Herramienta de desarrollo | Vite | Servidor de desarrollo y compilación |
| Navegación | React Router | Gestión de rutas y layouts |
| Estado global | Context API | Distribución del estado compartido |
| Actualización de estado | `useReducer` | Centralización de transiciones |
| Estado local | `useState` | Manejo de información específica de cada vista |
| Efectos | `useEffect` | Sincronización con servicios y eventos |
| Comunicación HTTP | Fetch API | Solicitudes hacia NestJS |
| Biblioteca de componentes | Componentes propios | Reutilización de elementos visuales |
| Estilos | CSS e inline styles | Diseño visual y adaptación responsive |

En el `package.json` del frontend se declaran React 19, React Router 7, Vite 8 y TypeScript 6 mediante sus respectivos rangos de versiones.

### 2.2 Principio arquitectónico

La estructura seleccionada separa la interfaz en tres responsabilidades principales:

**Presentación:** componentes React que muestran información y reciben acciones del usuario.

**Estado de aplicación:** información compartida, como la sesión y la sede seleccionada.

**Comunicación con el backend:** servicios TypeScript encargados de realizar solicitudes HTTP.

El flujo conceptual es:

```text id="fda36m"
                  USUARIO
                     |
                     v
             COMPONENTES REACT
                     |
              +------+------+
              |             |
              v             v
         Estado local    Estado global
          useState       AppStore
                             |
                             v
                       Context API
                       useReducer
              |
              v
       Servicios frontend
              |
              v
           Fetch API
              |
              v
         API de NestJS
              |
              v
          PostgreSQL
```

El diagrama representa una organización conceptual; los componentes pueden consultar servicios de manera directa y mantener estados locales independientes.

### 2.3 Criterio de elección

La elección se fundamenta en la necesidad de combinar:

- Desarrollo basado en componentes.
- Reutilización de elementos visuales.
- Estado compartido simple.
- Separación entre vistas y llamadas HTTP.
- Navegación organizada por roles.
- Compatibilidad con TypeScript.
- Desarrollo progresivo de funcionalidades.
- Baja complejidad inicial de infraestructura frontend.

Se consideró que React ofrecía un equilibrio adecuado entre flexibilidad, reutilización y facilidad de integración con la API NestJS.

## 3. Alternativas consideradas para el frontend

Se analizaron cuatro opciones principales: React, Angular, Vue y Svelte.

### 3.1 Alternativa A — React con TypeScript (seleccionada)

React es una biblioteca para construir interfaces de usuario mediante componentes.

Permite definir vistas que se actualizan cuando cambia su estado y combinar componentes pequeños para construir pantallas más complejas.

**Ventajas:**

- Modelo de programación basado en componentes.
- Reutilización de elementos visuales.
- Integración directa con TypeScript.
- Amplia disponibilidad de herramientas y bibliotecas.
- Manejo de estado mediante Hooks.
- Posibilidad de incorporar React Router.
- Compatibilidad con distintas estrategias de organización.
- Facilidad para integrar servicios HTTP.
- Permite construir tanto el portal del socio como la consola administrativa.
- Favorece la separación entre componentes visuales y lógica de aplicación.

**Desventajas:**

- React no establece por sí solo una estructura completa de proyecto.
- Es necesario seleccionar herramientas para navegación, compilación y otros aspectos.
- Un uso inadecuado del estado puede provocar renderizados innecesarios.
- La distribución de responsabilidades depende de las convenciones adoptadas por el equipo.
- Las aplicaciones grandes pueden necesitar estrategias adicionales para administrar datos remotos.

**Evaluación:**

Se consideró una alternativa adecuada por su flexibilidad y capacidad de construir interfaces complejas a partir de componentes reutilizables.

Además, permite incorporar únicamente las herramientas necesarias, evitando una estructura excesiva para el alcance inicial del proyecto.

### 3.2 Alternativa B — Angular

Angular es un framework frontend que proporciona una solución más estructurada para construir aplicaciones web.

Incluye mecanismos integrados para navegación, inyección de dependencias, formularios y organización de componentes.

**Ventajas:**

- Arquitectura fuertemente estructurada.
- Integración con TypeScript.
- Herramientas de navegación.
- Sistema de inyección de dependencias.
- Convenciones claras para aplicaciones grandes.
- Herramientas de formularios y validación.
- Ecosistema orientado a aplicaciones empresariales.

**Desventajas para este proyecto:**

- Mayor cantidad de conceptos iniciales.
- Curva de aprendizaje más pronunciada en determinados aspectos.
- Estructura y convenciones que podrían resultar excesivas para algunas pantallas.
- Mayor esfuerzo inicial de configuración y adaptación del equipo.

**Motivo de descarte:**

Angular era una alternativa técnicamente válida para FitZone Sports.

Sin embargo, se priorizó una solución con menor cantidad de conceptos obligatorios al inicio y mayor libertad para organizar los componentes según las funcionalidades.

React permitió adoptar una estructura progresiva, incorporando herramientas específicas a medida que avanzaba el desarrollo.

### 3.3 Alternativa C — Vue

Vue es un framework progresivo para construir interfaces web mediante componentes reactivos.

**Ventajas:**

- Sintaxis accesible.
- Sistema de reactividad integrado.
- Componentes reutilizables.
- Herramientas para navegación y estado.
- Compatibilidad con TypeScript.
- Posibilidad de adoptar progresivamente distintas herramientas.

**Desventajas para este proyecto:**

- Requería adoptar un modelo de componentes diferente del seleccionado.
- Su integración implicaba utilizar convenciones y bibliotecas específicas del ecosistema Vue.
- No proporcionaba una ventaja decisiva frente a React para las necesidades identificadas.
- El equipo tendría que mantener una única estrategia de componentes basada en la tecnología seleccionada.

**Motivo de descarte:**

Se consideró que React ofrecía las funcionalidades necesarias para el proyecto y permitía mantener una arquitectura de componentes acorde con la organización propuesta.

Vue continuaba siendo una opción viable, pero no se identificó una necesidad que justificara preferirlo frente a React.

### 3.4 Alternativa D — Svelte

Svelte permite construir interfaces reactivas utilizando componentes que se compilan a código JavaScript.

**Ventajas:**

- Modelo de componentes reactivos.
- Posibilidad de generar aplicaciones livianas.
- Menor cantidad de abstracciones ejecutadas en el navegador para determinadas tareas.
- Sintaxis concisa.
- Compatibilidad con herramientas modernas de frontend.

**Desventajas para este proyecto:**

- Requería adoptar convenciones distintas para componentes y reactividad.
- La organización del estado y la navegación debía diseñarse para ese ecosistema.
- Se necesitaba evaluar su integración con las herramientas previstas.
- No ofrecía un beneficio suficiente para justificar cambiar la arquitectura elegida.

**Motivo de descarte:**

Se priorizó React por su ecosistema, su modelo de composición y su adecuación a los componentes que el equipo necesitaba construir.

## 5. Elección de Vite

Además de la biblioteca de interfaz, fue necesario seleccionar una herramienta que facilitara el desarrollo local y la construcción de la aplicación.

Se eligió **Vite**.

### 5.1 Responsabilidades

Vite se utiliza para:

- Ejecutar el servidor de desarrollo.
- Procesar los módulos del frontend.
- Actualizar las vistas durante el desarrollo.
- Compilar los recursos para su distribución.
- Configurar el proxy hacia el backend.
- Integrar plugins utilizados por React.

### 5.2 Configuración del proyecto

El archivo:

`frontend/vite.config.ts`

contiene la configuración del entorno de desarrollo.

La aplicación utiliza el plugin de React, una configuración asociada al compilador de React y el plugin `basic-ssl`.

También define un proxy para las solicitudes dirigidas a `/backend`.

Fragmento representativo:

```typescript id="wn7v6q"
server: {
  host: true,
  proxy: {
    "/backend": {
      target: "http://localhost:3000",
      changeOrigin: true,
      rewrite: (path) =>
        path.replace(/^\/backend/, ""),
    },
  },
}
```

Este mecanismo permite que el frontend realice solicitudes utilizando un prefijo común y que Vite las redirija hacia la API durante el desarrollo.

### 5.3 Alternativas consideradas

**Webpack:** herramienta flexible y ampliamente utilizada, pero con una configuración que podía exigir más trabajo inicial para este proyecto.

**Create React App:** alternativa históricamente utilizada para iniciar aplicaciones React, pero que no se consideró conveniente frente al entorno moderno seleccionado.

**Vite:** proporcionaba las funcionalidades necesarias para desarrollo y compilación con una configuración relativamente directa.

### 5.4 Consecuencias

La aplicación depende de una configuración específica de Vite para el entorno local.

El proxy de desarrollo no debe confundirse con la configuración de publicación: en la construcción para producción, las solicitudes son gestionadas por el servidor que publica la aplicación, en este caso Nginx.

## 6. Librería propia de componentes reutilizables

Uno de los principales objetivos del frontend fue evitar la duplicación de elementos visuales y mantener una interfaz coherente.

Para resolverlo, se decidió construir una **librería de componentes propios**.

Estos componentes se encuentran en:

`frontend/src/components/`

La organización se inspira en **Atomic Design**, utilizando tres niveles principales:

- Átomos.
- Moléculas.
- Organismos.

La aplicación también contiene pantallas completas y layouts que combinan estos componentes.

### 6.1 Organización

```text id="jk8lgi"
frontend/src/components/
│
├── atoms/
│   ├── Badge.tsx
│   ├── Button.tsx
│   ├── Input.tsx
│   ├── Spinner.tsx
│   └── index.ts
│
├── molecules/
│   ├── AlertMessage.tsx
│   ├── Card.tsx
│   ├── FormField.tsx
│   └── index.ts
│
├── organisms/
│   ├── AdminInscripcionClase.tsx
│   ├── GrillaHoraria.tsx
│   ├── Navbar.tsx
│   ├── RequireAuth.tsx
│   ├── TablaDatos.tsx
│   └── index.ts
│
└── index.ts
```

El archivo `components/index.ts` permite exportar los componentes mediante un punto de entrada común.

### 6.2 Átomos

Los átomos representan componentes de interfaz relativamente simples.

**Button:** permite presentar botones con variantes visuales y estados de carga.

**Input:** centraliza campos de entrada.

**Badge:** muestra etiquetas de estado.

**Spinner:** representa operaciones de carga.

Ejemplo del componente `Button`:

```typescript id="05mq4k"
export type ButtonVariant =
  | "primary"
  | "secondary"
  | "danger"
  | "ghost";
```

La aplicación puede utilizar el mismo componente con distintos estilos según la operación.

Esto reduce la necesidad de repetir estructuras HTML y estilos en cada pantalla.

### 6.3 Moléculas

Las moléculas combinan elementos simples para resolver necesidades más completas.

**FormField:** reúne etiqueta, campo de entrada y mensajes de validación.

**Card:** organiza secciones de contenido.

**AlertMessage:** muestra mensajes de error, éxito, advertencia e información.

Ejemplo conceptual de reutilización:

```tsx id="yeo404"
<FormField label="Nombre" required>
  <Input placeholder="Ingresá el nombre" />
</FormField>
```

La ventaja es que diferentes formularios pueden mantener el mismo estilo y comportamiento básico.

### 6.4 Organismos

Los organismos representan componentes más complejos.

**Navbar:** navegación principal del portal.

**RequireAuth:** protección de rutas administrativas.

**TablaDatos:** presentación genérica de información tabular.

**GrillaHoraria:** selección visual de turnos deportivos.

**AdminInscripcionClase:** inscripción administrativa a clases.

Estos componentes reúnen varios elementos visuales y determinadas interacciones.

### 6.5 Ejemplo: GrillaHoraria

El componente `GrillaHoraria` recibe las franjas disponibles y permite seleccionar un horario.

El contrato incluye:

```typescript id="al0znh"
export interface GrillaHorariaProps {
  franjas: FranjaHorariaItem[];
  horaSeleccionada: number | null;
  onSelectHora: (franja: FranjaHorariaItem) => void;
}
```

La grilla muestra:

- Hora de inicio y finalización.
- Precio.
- Estado de disponibilidad.
- Recargos y descuentos.
- Turno seleccionado.

Los turnos ocupados o en mantenimiento aparecen deshabilitados.

Esta organización permite separar la presentación de los horarios de las operaciones de consulta y creación de reservas.

### 6.6 Ejemplo: TablaDatos

`TablaDatos<T>` permite mostrar colecciones de diferentes entidades utilizando una estructura común.

Recibe:

- Definición de columnas.
- Filas.
- Función para identificar cada fila.
- Estado de carga.
- Mensaje para listados vacíos.

La utilización de genéricos TypeScript permite reutilizar el componente con diferentes tipos de registros.

### 6.7 Ventajas de Atomic Design

**Reutilización:** los componentes pueden utilizarse en distintas pantallas.

**Consistencia visual:** los estilos y estados se mantienen más uniformes.

**Mantenimiento:** una corrección en un componente compartido puede beneficiar a varias vistas.

**Separación de responsabilidades:** los componentes pequeños se concentran en funciones concretas.

**Extensibilidad:** nuevas pantallas pueden construirse combinando componentes existentes.

**Trabajo en equipo:** diferentes integrantes pueden desarrollar componentes y vistas sin repetir todas las estructuras.

## 7. Alternativas consideradas para la librería de componentes

Además de la estructura elegida, se evaluaron enfoques alternativos para construir la interfaz.

### 7.1 Alternativa A — Componentes propios y Atomic Design (seleccionada)

Consiste en construir una biblioteca interna de elementos reutilizables organizados por complejidad.

**Ventajas:**

- Control sobre estilos y comportamiento.
- Adaptación al diseño de FitZone Sports.
- Evita depender de una biblioteca visual extensa.
- Facilita reutilizar los mismos componentes.
- Permite aprender y aplicar composición de interfaces.
- Favorece la consistencia entre las pantallas.

**Desventajas:**

- Requiere desarrollar y mantener componentes propios.
- Se necesita verificar accesibilidad y comportamiento.
- Puede aumentar el trabajo inicial.
- Los componentes complejos requieren pruebas específicas.
- Una implementación incompleta puede generar inconsistencias.

**Evaluación:**

Se consideró apropiada para el alcance académico porque permite demostrar una estructura de componentes reutilizables y mantener control sobre la identidad visual.

### 7.2 Alternativa B — Material UI

Material UI proporciona componentes React previamente desarrollados y estilizados.

**Ventajas:**

- Amplio catálogo de componentes.
- Reducción del tiempo de implementación inicial.
- Patrones visuales establecidos.
- Funcionalidades comunes disponibles.
- Herramientas de personalización.

**Desventajas para este proyecto:**

- Introduce una dependencia de biblioteca visual.
- La personalización puede requerir adaptar su sistema de estilos.
- Algunos componentes podrían resultar innecesarios.
- El equipo perdería parte del control directo sobre la implementación visual.

**Motivo de descarte:**

Se priorizó desarrollar componentes propios para mantener una identidad visual específica y demostrar la organización de la interfaz.

### 7.3 Alternativa C — Bootstrap

Bootstrap ofrece componentes y utilidades CSS reutilizables.

**Ventajas:**

- Desarrollo rápido de interfaces.
- Sistema de grillas responsivas.
- Componentes y estilos conocidos.
- Documentación amplia.

**Desventajas para este proyecto:**

- La personalización visual requiere modificar estilos establecidos.
- Puede generar dependencias de clases CSS específicas.
- No reemplaza por sí mismo la organización de componentes React.
- Puede producir interfaces visualmente similares a otras aplicaciones si no se personaliza.

**Motivo de descarte:**

Se decidió mantener un sistema visual propio y organizar los componentes directamente dentro de React.

### 7.4 Alternativa D — Componentes independientes en cada pantalla

Consiste en implementar cada vista con sus propios botones, formularios y estructuras.

**Ventajas:**

- Menor organización inicial.
- Flexibilidad para resolver pantallas aisladas.
- Puede resultar rápida durante un prototipo inicial.

**Desventajas:**

- Duplica código.
- Dificulta las correcciones globales.
- Produce diferencias visuales.
- Incrementa el costo de mantenimiento.
- Complica reutilizar funcionalidades.

**Motivo de descarte:**

No ofrecía una estructura adecuada para una aplicación con numerosas pantallas administrativas y de socios.

## 8. Gestión de estado global

La interfaz necesita administrar información que no pertenece exclusivamente a una pantalla.

Por ejemplo:

- Usuario autenticado.
- Token de sesión.
- Estado de carga de la sesión.
- Sede seleccionada.
- Estado de conectividad.

Si cada componente mantuviera copias independientes de estos datos, podrían aparecer inconsistencias.

Para resolver este problema se decidió utilizar **React Context API y `useReducer`**.

### 8.1 Estructura implementada

La implementación se encuentra en:

`frontend/src/store/AppStore.tsx`

El estado principal está definido mediante:

```typescript id="txfpgv"
export interface AppState {
  usuario: UsuarioSesion | null;
  token: string | null;
  cargandoSesion: boolean;
  sedeSeleccionadaId: number | null;
  online: boolean;
}
```

Esta estructura contiene información compartida que puede ser utilizada por diferentes componentes de la aplicación.

### 8.2 Context API

Context API permite distribuir información a los componentes descendientes sin tener que pasarla manualmente por cada nivel de propiedades.

El proyecto utiliza un contexto denominado:

```typescript id="5q0r7o"
const AppStoreContext =
  createContext<AppStoreValue | null>(null);
```

Los componentes pueden recuperar la información mediante el hook `useAppStore()`.

### 8.3 useReducer

`useReducer` centraliza las modificaciones del estado mediante acciones.

El proyecto utiliza acciones como:

```typescript id="lw0r9t"
type AppAction =
  | { type: "SET_CARGANDO_SESION"; payload: boolean }
  | {
      type: "SET_SESION";
      payload: {
        usuario: UsuarioSesion | null;
        token: string | null;
      };
    }
  | { type: "CERRAR_SESION" }
  | { type: "SET_SEDE"; payload: number | null }
  | { type: "SET_ONLINE"; payload: boolean };
```

Cada acción representa una modificación concreta del estado compartido.

### 8.4 Ejemplo de actualización

Cuando un usuario selecciona una sede, el store ejecuta una acción:

```typescript id="4omqsd"
dispatch({
  type: "SET_SEDE",
  payload: sedeId,
});
```

El reducer produce el nuevo estado:

```typescript id="d0x6f2"
case "SET_SEDE":
  return {
    ...state,
    sedeSeleccionadaId: action.payload,
  };
```

Esta organización permite mantener las actualizaciones centralizadas y facilita comprender por qué cambia la información.

### 8.5 Proveedor global

El archivo `frontend/src/main.tsx` envuelve la aplicación con el proveedor:

```tsx id="9hmfv7"
<React.StrictMode>
  <AppStoreProvider>
    <App />
  </AppStoreProvider>
</React.StrictMode>
```

Esto permite que las pantallas descendientes utilicen el estado compartido.

### 8.6 Hook personalizado

El proyecto ofrece:

```typescript id="12i8am"
export function useAppStore(): AppStoreValue {
  const ctx = useContext(AppStoreContext);

  if (!ctx) {
    throw new Error(
      "useAppStore debe utilizarse dentro de <AppStoreProvider>"
    );
  }

  return ctx;
}
```

El hook proporciona una interfaz común para acceder al estado y ejecutar acciones.

## 9. Alternativas consideradas para el estado global

La elección de Context API y `useReducer` se fundamenta en las necesidades reales de la aplicación.

Se consideraron alternativas como Redux Toolkit, Zustand y el uso exclusivo de estados locales.

### 9.1 Alternativa A — Context API y useReducer (seleccionada)

**Ventajas:**

- Funcionalidades incluidas en React.
- No requiere incorporar otra biblioteca de estado.
- Permite centralizar información compartida.
- Utiliza acciones explícitas.
- Facilita el tipado mediante TypeScript.
- Es suficiente para un conjunto relativamente reducido de variables globales.
- Mantiene una curva de aprendizaje adecuada para el equipo.

**Desventajas:**

- Una actualización del contexto puede provocar renderizados en múltiples consumidores.
- No incluye automáticamente herramientas específicas para caché de datos remotos.
- Los contextos grandes pueden volverse difíciles de mantener.
- No proporciona por sí mismo el mismo conjunto de herramientas de depuración que algunas bibliotecas especializadas.

**Evaluación:**

Se consideró adecuada porque el estado global de FitZone Sports contiene principalmente información de sesión, sede y conectividad.

Los datos específicos de cada pantalla se mantienen en estados locales o se recuperan mediante servicios HTTP.

### 9.2 Alternativa B — Redux Toolkit

Redux Toolkit proporciona herramientas para administrar estado compartido mediante un store centralizado.

**Ventajas:**

- Estructura explícita para acciones y cambios de estado.
- Herramientas de depuración.
- Organización apropiada para estados complejos.
- Posibilidad de incorporar RTK Query para manejar datos remotos.
- Convenciones consolidadas.

**Desventajas para este proyecto:**

- Introduce una dependencia adicional.
- Requiere configurar y mantener slices y otros mecanismos.
- Puede incrementar el código y la estructura inicial.
- Su complejidad no resultaba necesaria para las variables globales identificadas.

**Motivo de descarte:**

El estado compartido era suficientemente reducido como para administrarlo mediante herramientas integradas de React.

No se identificó una necesidad que justificara incorporar Redux desde el comienzo.

### 9.3 Alternativa C — Zustand

Zustand ofrece una biblioteca ligera para manejar estado compartido mediante stores.

**Ventajas:**

- API relativamente sencilla.
- Menor configuración inicial que otras herramientas.
- Posibilidad de seleccionar partes específicas del estado.
- Buena integración con React y TypeScript.
- Útil para compartir información entre componentes.

**Desventajas para este proyecto:**

- Introduce una dependencia externa.
- Requiere adoptar convenciones adicionales.
- El equipo tendría que mantener otra tecnología de estado.
- No ofrecía una ventaja decisiva para el tamaño del estado global definido.

**Motivo de descarte:**

Se priorizó utilizar Context API y `useReducer` porque ya cubrían las necesidades principales sin incorporar una biblioteca adicional.

### 9.4 Alternativa D — useState exclusivamente

Consiste en mantener toda la información mediante estados locales de los componentes.

**Ventajas:**

- Implementación sencilla.
- No requiere un store global.
- Resulta apropiada para formularios y componentes aislados.
- Facilita mantener cerca el estado de la interfaz que lo utiliza.

**Desventajas:**

- Puede requerir pasar propiedades entre numerosos componentes.
- Produce duplicación de datos compartidos.
- Dificulta sincronizar información de sesión.
- Complica compartir la sede seleccionada entre distintas pantallas.
- Puede generar inconsistencias entre componentes.

**Motivo de descarte:**

No resultaba conveniente para administrar la autenticación y otros datos compartidos por toda la aplicación.

Sin embargo, **`useState` continúa utilizándose para la información local de las vistas**, como formularios, mensajes y estados de carga.

## 10. Comparación de gestión de estado

| Criterio | Context + useReducer | Redux Toolkit | Zustand | useState local |
|---|---|---|---|---|
| Dependencia adicional | **No** | Sí | Sí | No |
| Estado compartido | **Sí** | Sí | Sí | Limitado |
| Acciones explícitas | **Sí** | Sí | Según implementación | No necesariamente |
| Configuración inicial | **Baja** | Media | Baja | Mínima |
| Herramientas especializadas | Limitadas | Amplias | Según integración | Limitadas |
| Adecuación a FitZone Sports | **Alta** | Media-alta | Alta | Parcial |

**Resultado:** se seleccionó Context API con `useReducer`, manteniendo los estados locales para las funcionalidades que no necesitan ser compartidas.

## 11. Separación entre estado global y estado local

La decisión establece una separación entre diferentes clases de información.

### 11.1 Estado global

Se utiliza cuando múltiples pantallas necesitan acceder a la misma información.

Ejemplos:

- Sesión autenticada.
- Usuario actual.
- Sede seleccionada.
- Estado de conectividad.

### 11.2 Estado local

Se utiliza cuando la información pertenece principalmente a un componente.

Ejemplos:

- Texto ingresado en un formulario.
- Modal abierto o cerrado.
- Fila seleccionada.
- Estado de carga de una consulta.
- Mensaje de error de una operación.
- Resultado de una búsqueda.
- Cámara QR activa.

### 11.3 Ventajas de la separación

Esta organización evita concentrar todos los datos de la aplicación dentro del store.

También permite que cada pantalla mantenga la información necesaria para su funcionamiento sin generar dependencias globales innecesarias.

### 11.4 Información remota

Los listados de clases, usuarios, canchas y pagos se consultan mediante servicios HTTP.

No se implementó una biblioteca general de caché de consultas remotas como TanStack Query.

Por lo tanto, los componentes deben administrar explícitamente sus estados de carga, error y actualización cuando consultan el backend.

Esta decisión simplifica las dependencias, aunque puede generar cierta repetición en la lógica de obtención de datos.

## 14. Comunicación con el backend

La aplicación React consume una API REST implementada mediante NestJS.

Para concentrar las solicitudes HTTP, el proyecto incorpora servicios dentro de:

`frontend/src/services/`

### 14.1 Organización de servicios

Entre los archivos disponibles se encuentran:

- `apiClient.ts`
- `authService.ts`
- `usuariosService.ts`
- `sedesService.ts`
- `clasesService.ts`
- `canchasService.ts`
- `membresiasService.ts`
- `pagosService.ts`
- `pagosAdminService.ts`
- `planesService.ts`
- `controlAccesoService.ts`
- `reservasAdminService.ts`
- `permissions.ts`

Cada archivo agrupa operaciones relacionadas con una funcionalidad.

### 14.2 Cliente HTTP común

El proyecto implementa `apiRequest<T>` dentro de `apiClient.ts`.

Su firma principal es:

```typescript id="mdm3xm"
export async function apiRequest<T>(
  path: string,
  options: RequestOptions = {},
): Promise<T>
```

Esta función:

1. Construye la URL con el prefijo `/backend`.
2. Recupera el token de autenticación.
3. Agrega el encabezado `Authorization` si existe un token.
4. Envía el cuerpo en formato JSON cuando corresponde.
5. Comprueba la respuesta HTTP.
6. Extrae los mensajes de error.
7. Devuelve un resultado tipado.

### 14.3 Manejo de errores

La clase `ApiError` representa errores HTTP con su código de estado.

Permite diferenciar respuestas como:

- `401 Unauthorized`.
- `403 Forbidden`.
- `404 Not Found`.
- `409 Conflict`.

Esta diferenciación facilita presentar mensajes adecuados al usuario.

### 14.4 Descarga de comprobantes

La función `apiRequestBlob` permite descargar archivos binarios, como comprobantes PDF.

### 14.5 Ventajas de la separación

- Reduce la repetición de solicitudes.
- Facilita actualizar rutas de la API.
- Centraliza parte del tratamiento de errores.
- Mejora la legibilidad de las vistas.
- Permite reutilizar operaciones desde diferentes componentes.
- Facilita conectar progresivamente pantallas que inicialmente utilizaban datos locales.

### 14.6 Limitación identificada

Aunque existe un cliente HTTP común, algunos servicios todavía realizan solicitudes `fetch` directamente.

Por ejemplo, `sedesService.ts` implementa consultas propias.

Esto significa que la centralización de comunicación HTTP es parcial.

Una mejora futura sería unificar las operaciones para mantener un comportamiento consistente en autenticación y tratamiento de errores.

## 16. Integración con el control de acceso offline

El frontend también cumple una función importante en el requisito RNF-01.

La aplicación necesita detectar cambios de conectividad y permitir operaciones locales en el terminal de recepción.

### 16.1 Estado de conexión

El store global contiene:

```typescript id="qbd2ze"
online: boolean;
```

El proveedor escucha los eventos del navegador:

```typescript id="ja4p55"
window.addEventListener("online", onOnline);
window.addEventListener("offline", onOffline);
```

Cuando ocurre un cambio, se actualiza el estado compartido.

Esto permite que los componentes conozcan el estado de conectividad informado por el navegador.

### 16.2 Terminal de recepción

El componente:

`frontend/src/admin/AdminControlAcceso.tsx`

utiliza el estado global de conexión junto con servicios específicos de control de acceso.

Cuando detecta un problema de red, puede recurrir al snapshot local de socios.

Los ingresos autorizados provisionalmente se agregan a una cola persistente.

Cuando se recupera la conexión, la aplicación intenta sincronizar los eventos.

### 16.3 Generación y presentación de QR

El componente:

`frontend/src/portal/MiPaseQR.tsx`

utiliza la biblioteca `qrcode` para representar visualmente los tokens emitidos por el backend.

Los códigos se actualizan conforme al mecanismo de rotación implementado.

### 16.4 Alcance de la decisión

React y Context API facilitan distribuir el estado de conectividad, pero no garantizan por sí solos el funcionamiento offline.

Las reglas de validación, la copia local y la sincronización se implementan mediante servicios específicos.

Las decisiones relacionadas se documentan en:

- ADR-003 — Estrategia offline.
- ADR-007 — Sincronización de terminales.

## 18. Riesgos y medidas de mitigación

### 18.1 Crecimiento excesivo del store global

**Riesgo:** incorporar toda la información de la aplicación dentro de Context API.

**Mitigación:** mantener en el store solamente los datos compartidos y utilizar estado local para información específica de las vistas.

### 18.2 Duplicación de componentes

**Riesgo:** crear diferentes botones, formularios o tablas para operaciones equivalentes.

**Mitigación:** reutilizar la librería de componentes y mantener actualizado el catálogo.

### 18.3 Renderizados innecesarios

**Riesgo:** que una modificación del estado global actualice componentes que no necesitan esa información.

**Mitigación:** separar responsabilidades, evaluar la división de contextos cuando crezca el estado y aplicar optimizaciones donde exista una necesidad comprobada.

### 18.4 Inconsistencia de datos remotos

**Riesgo:** que una pantalla muestre información desactualizada después de una modificación en el backend.

**Mitigación:** actualizar los datos tras las operaciones, manejar los estados de carga y establecer criterios claros de refresco.

### 18.5 Fallos de autenticación

**Riesgo:** que una ruta protegida se muestre basándose únicamente en la existencia de un token.

**Mitigación:** validar la sesión y los permisos reales mediante el backend.

### 18.6 Manejo incorrecto de roles

**Riesgo:** que un usuario acceda a una funcionalidad administrativa que no le corresponde.

**Mitigación:** mantener controles de interfaz coherentes y reforzar la autorización en los endpoints de NestJS.

### 18.7 Pérdida de estado persistido

**Riesgo:** que el navegador elimine información almacenada localmente.

**Mitigación:** tratar el almacenamiento local como un mecanismo auxiliar, no como la fuente definitiva de datos del sistema.

### 18.8 Errores de integración

**Riesgo:** que los contratos del frontend y del backend utilicen estructuras diferentes.

**Mitigación:** mantener actualizada la documentación OpenAPI, revisar los tipos TypeScript y ejecutar pruebas de integración.

## 22. Evolución futura de la decisión

La arquitectura seleccionada permite incorporar nuevas pantallas utilizando componentes y servicios existentes.

Si FitZone Sports creciera significativamente, podrían evaluarse mejoras adicionales.

### 22.1 División de contextos

Separar la sesión, los permisos y la conectividad en contextos específicos cuando el volumen del estado compartido lo justifique.

### 22.2 Biblioteca de consultas remotas

Evaluar herramientas como TanStack Query para administrar caché, invalidación y actualización de datos del backend.

### 22.3 Ampliación del sistema de diseño

Incorporar tokens visuales, documentación de componentes y criterios uniformes de accesibilidad.

### 22.4 Pruebas de componentes

Agregar pruebas automatizadas de interacciones críticas de los formularios, las tablas y las grillas.

### 22.5 Accesibilidad

Revisar navegación mediante teclado, etiquetas semánticas y estados accesibles en los componentes.

### 22.6 Optimización del frontend

Evaluar carga diferida de rutas, reducción del tamaño de los bundles y mejoras sobre componentes de alto costo de renderizado.

### 22.7 Centralización de servicios HTTP

Unificar las solicitudes actualmente dispersas y mantener una política consistente de manejo de errores y autenticación.

### 22.8 Seguridad del almacenamiento de sesión

Evaluar mecanismos de protección más adecuados para un despliegue productivo y reforzar las medidas contra XSS.

Estas mejoras constituyen posibles evoluciones y no se declaran implementadas por el presente ADR.

Si una modificación futura reemplazara React o cambiara sustancialmente la arquitectura de estado, debería documentarse mediante un nuevo registro de decisión.

---

## 23. Conclusión

Se decidió implementar el frontend de FitZone Sports utilizando **React con TypeScript**, Vite como herramienta de desarrollo y React Router como mecanismo de navegación.

La elección de React responde a la necesidad de construir interfaces dinámicas para diferentes perfiles, reutilizar componentes y mantener separadas las responsabilidades de presentación y comunicación con el backend.

Frente a alternativas como Angular, Vue y Svelte, React ofrecía una combinación adecuada de flexibilidad, composición de componentes y compatibilidad con la arquitectura prevista.

Para organizar la interfaz se adoptó una **librería de componentes propia inspirada en Atomic Design**, con elementos agrupados en átomos, moléculas y organismos.

Esta decisión permite reducir duplicaciones y mantener criterios visuales comunes entre el portal de socios y la consola administrativa.

En cuanto al estado compartido, se seleccionó **Context API junto con `useReducer`**, debido a que las necesidades globales se concentran principalmente en sesión, usuario, sede seleccionada y conectividad.

La utilización de estados locales complementa esta estrategia para los formularios, listados y demás funcionalidades específicas de cada pantalla.

También se decidió organizar gran parte de la comunicación HTTP mediante servicios TypeScript, facilitando la integración progresiva con la API NestJS.

Las alternativas Redux Toolkit y Zustand resultaban técnicamente viables, pero se consideró innecesario incorporar una biblioteca adicional para el tamaño inicial del estado compartido.

La decisión presenta compromisos, como la necesidad de mantener una biblioteca visual propia, la administración manual de datos remotos y el cuidado requerido para evitar dependencias innecesarias entre componentes.

Sin embargo, sus beneficios resultan adecuados para el alcance del Trabajo Integrador Final.

**Decisión final: mantener React con TypeScript y Vite para la interfaz web, organizar los elementos mediante componentes propios reutilizables inspirados en Atomic Design y utilizar Context API con `useReducer` para administrar el estado global, complementado con estado local y servicios HTTP especializados.**
