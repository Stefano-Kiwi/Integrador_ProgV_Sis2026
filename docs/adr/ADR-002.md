# ADR-002 — Adopción de PostgreSQL como base de datos relacional

**Estado:** Aceptado  
**Fecha de registro:** 19 de noviembre de 2026  
**Proyecto:** FitZone Sports — Trabajo Integrador Final  
**Equipo:** 12  
**Unidad temática:** Unidad I — Arquitectura de Software y Persistencia  
**Requisitos relacionados:** RN-01, RN-02, RN-03, RNF-03 y RNF-04

---

## 1. Contexto

FitZone Sports es una plataforma destinada a administrar las operaciones de una cadena de gimnasios y complejos deportivos distribuidos en múltiples sedes.

El sistema gestiona información relacionada con usuarios, roles, sedes, membresías, clases grupales, canchas deportivas, reservas, control de acceso y pagos simulados.

Estas funcionalidades presentan relaciones entre sí y requieren mantener la información consistente durante su funcionamiento.

Por ejemplo, una reserva de cancha relaciona a un usuario con una instalación deportiva, una fecha y un horario determinado. La operación debe verificar que la cancha exista, que se encuentre habilitada y que el turno solicitado no esté ocupado por otra reserva activa.

Asimismo, el control de acceso debe impedir que un socio mantenga ingresos abiertos simultáneamente en diferentes sedes, conforme a la regla de negocio **RN-01**.

Estas características generan necesidades específicas de persistencia:

- Mantener relaciones entre diferentes entidades.
- Evitar la duplicación de información.
- Garantizar la integridad referencial.
- Ejecutar operaciones transaccionales.
- Controlar solicitudes concurrentes.
- Permitir consultas eficientes sobre grandes cantidades de registros.
- Mantener un historial consistente de reservas, accesos y pagos.
- Facilitar las modificaciones del esquema durante el desarrollo.
- Permitir incorporar nuevas sedes sin rediseñar la base de datos.

Por estas razones, durante el diseño arquitectónico fue necesario seleccionar un motor de base de datos que ofreciera garantías de integridad y capacidades adecuadas para operaciones transaccionales.

También se requería una tecnología que permitiera integrar la persistencia con el backend desarrollado en NestJS y TypeScript.

---

## 2. Decisión

Se decidió utilizar **PostgreSQL 18 como sistema de gestión de bases de datos relacionales**, complementado con **Prisma ORM** para facilitar el acceso a la información desde NestJS.

La base de datos se organiza mediante tablas relacionadas, claves primarias, claves foráneas, restricciones de unicidad, índices y tipos enumerados.

La elección se fundamenta principalmente en tres necesidades:

1. Mantener la consistencia de los datos mediante relaciones y transacciones.
2. Garantizar que las reservas y los accesos respeten las reglas de concurrencia.
3. Permitir consultas eficientes y una evolución controlada del modelo de datos.

### 2.1 Uso de PostgreSQL

PostgreSQL almacena la información principal de FitZone Sports y aplica restricciones directamente sobre los datos.

Estas restricciones resultan fundamentales porque una validación realizada únicamente en el backend puede ser insuficiente cuando existen solicitudes simultáneas.

El motor permite utilizar:

- Transacciones con propiedades ACID.
- Claves primarias y foráneas.
- Restricciones `UNIQUE`.
- Restricciones `CHECK`.
- Índices compuestos.
- Índices únicos parciales.
- Tipos de datos temporales y decimales.
- Consultas SQL con relaciones entre tablas.

De esta manera, las reglas críticas no dependen exclusivamente de comprobaciones implementadas en memoria.

### 2.2 Uso de Prisma ORM

Prisma permite representar las entidades de PostgreSQL mediante modelos definidos en el archivo:

`backend/prisma/schema.prisma`

A partir de estos modelos se genera un cliente tipado que utilizan los repositorios de NestJS.

Se eligió Prisma porque permite:

- Definir entidades y relaciones de manera declarativa.
- Generar tipos compatibles con TypeScript.
- Reducir la escritura repetitiva de consultas SQL comunes.
- Administrar migraciones del modelo de datos.
- Facilitar operaciones CRUD.
- Utilizar transacciones.
- Mantener una separación entre servicios de negocio y operaciones de persistencia.

Sin embargo, Prisma no reemplaza todas las capacidades de PostgreSQL.

En particular, la implementación utiliza migraciones SQL para definir determinados índices únicos parciales que no se representan directamente en la versión de Prisma utilizada por el proyecto.

Por lo tanto, la decisión adoptada no consiste en depender exclusivamente del ORM, sino en **combinar Prisma con las capacidades nativas de PostgreSQL** cuando las reglas de negocio lo requieren.

## 3. Alternativas consideradas

Se analizaron cuatro alternativas principales para la persistencia de datos: PostgreSQL, MySQL/MariaDB, MongoDB y SQLite.

### 3.1 Alternativa A — PostgreSQL (seleccionada)

PostgreSQL es un sistema de gestión de bases de datos relacionales de código abierto que ofrece soporte para transacciones, integridad referencial, consultas complejas e índices avanzados.

**Ventajas:**

- Soporte de transacciones ACID.
- Integridad referencial mediante claves foráneas.
- Índices compuestos y únicos parciales.
- Herramientas para analizar y optimizar consultas.
- Compatibilidad con Prisma ORM.
- Buen soporte para concurrencia.
- Capacidad de gestionar relaciones entre múltiples entidades.
- Disponibilidad de imágenes oficiales para Docker.
- Posibilidad de incorporar nuevas sedes mediante registros, sin modificar el esquema.

**Desventajas:**

- Requiere administrar y configurar un servidor de base de datos.
- Necesita una estrategia de respaldo y restauración.
- Los índices y las consultas deben diseñarse correctamente para evitar problemas de rendimiento.
- Las migraciones avanzadas pueden requerir SQL manual.
- Su administración demanda conocimientos específicos de bases de datos relacionales.

**Evaluación:**

Se consideró la alternativa más adecuada porque FitZone Sports necesita garantizar operaciones transaccionales sobre datos altamente relacionados.

Además, los índices únicos parciales resultan especialmente útiles para implementar las reglas de negocio de reservas e ingresos.

### 3.2 Alternativa B — MySQL / MariaDB

MySQL y MariaDB son motores relacionales ampliamente utilizados en aplicaciones web.

**Ventajas:**

- Soporte de bases de datos relacionales.
- Transacciones mediante motores adecuados, como InnoDB.
- Uso de claves primarias y foráneas.
- Integración con herramientas ORM.
- Amplia documentación y disponibilidad.
- Herramientas de administración conocidas.

**Desventajas para este proyecto:**

- Existen diferencias respecto de PostgreSQL en las funcionalidades avanzadas de indexación.
- La implementación de unicidad condicionada puede requerir estructuras o técnicas alternativas.
- Sería necesario adaptar las migraciones y determinadas consultas.
- Algunas reglas de concurrencia necesitarían un diseño diferente.

**Motivo de descarte:**

Aunque MySQL y MariaDB podían resolver gran parte de las necesidades del sistema, PostgreSQL ofrecía una solución más directa para las restricciones de unicidad parciales utilizadas en FitZone Sports.

La elección no implica que MySQL sea incapaz de garantizar la integridad de las reservas, sino que PostgreSQL proporcionaba herramientas más convenientes para el diseño seleccionado.

### 3.3 Alternativa C — MongoDB

MongoDB es una base de datos orientada a documentos que almacena información mediante estructuras similares a JSON.

**Ventajas:**

- Flexibilidad en la estructura de documentos.
- Facilidad para representar determinadas estructuras anidadas.
- Posibilidades de escalado distribuido.
- Integración con aplicaciones JavaScript y TypeScript.
- Menor rigidez del esquema para ciertos casos de uso.

**Desventajas para este proyecto:**

- El dominio de FitZone Sports contiene numerosas relaciones entre entidades.
- Se necesitan consultas que vinculan usuarios, reservas, membresías, canchas y sedes.
- Sería necesario decidir cuidadosamente qué información incorporar dentro de documentos y qué información referenciar.
- La integridad entre documentos requeriría mecanismos adicionales.
- La implementación de determinadas operaciones transaccionales sería diferente.

**Motivo de descarte:**

El modelo de negocio presenta relaciones claramente estructuradas y restricciones de integridad que se expresan naturalmente mediante un modelo relacional.

Se consideró que PostgreSQL permitiría representar estas dependencias de forma más directa y mantener una mayor consistencia estructural.

Esto no significa que MongoDB carezca de transacciones o mecanismos de integridad, sino que su modelo documental no fue considerado el más adecuado para este caso.

### 3.4 Alternativa D — SQLite

SQLite es un motor relacional liviano que utiliza archivos locales para almacenar la base de datos.

**Ventajas:**

- Instalación y configuración sencillas.
- No requiere administrar un servidor separado.
- Bajo consumo de recursos.
- Adecuado para prototipos y aplicaciones pequeñas.
- Facilita determinados escenarios de desarrollo local.

**Desventajas para este proyecto:**

- Su modelo de concurrencia de escrituras es más limitado que el de un servidor PostgreSQL.
- No ofrece la misma infraestructura de conexiones y administración para múltiples clientes remotos.
- Resulta menos apropiado para centralizar una plataforma multi-sede con operaciones simultáneas frecuentes.
- Exigiría considerar una estrategia distinta para el acceso concurrente de múltiples terminales y servicios.

**Motivo de descarte:**

FitZone Sports necesita una base de datos centralizada a la que accede una API utilizada por múltiples usuarios y sedes.

Se decidió utilizar PostgreSQL para contar con un servidor dedicado y herramientas apropiadas para el procesamiento transaccional concurrente.

## 4. Comparación de alternativas

| Criterio | PostgreSQL | MySQL / MariaDB | MongoDB | SQLite |
|---|---|---|---|---|
| Modelo principal | Relacional | Relacional | Documental | Relacional |
| Transacciones ACID | Sí | Sí, con motor adecuado | Sí | Sí |
| Claves foráneas tradicionales | Sí | Sí, con motor adecuado | No de la misma forma | Sí |
| Índices únicos parciales | Soporte nativo | Requiere alternativas según motor | Índices parciales con características propias | Sí |
| Consultas relacionales complejas | Alta adecuación | Alta adecuación | Requiere diseño documental específico | Adecuada, según escala |
| Integración con Prisma | Sí | Sí | Sí | Sí |
| Servidor centralizado | Sí | Sí | Sí | No, motor embebido |
| Adecuación a FitZone Sports | **Alta** | Alta | Media | Media-baja |

Los valores de adecuación son una evaluación cualitativa basada en las necesidades del proyecto, no una comparación de rendimiento experimental entre motores.

**Resultado de la evaluación:** PostgreSQL fue seleccionado por su combinación de integridad relacional, transacciones, índices avanzados y compatibilidad con Prisma.

## 5. Diseño del modelo relacional

El modelo de FitZone Sports se encuentra definido en:

`backend/prisma/schema.prisma`

La migración inicial contiene **17 tablas principales**.

Entre ellas se encuentran:

| Entidad | Función |
|---|---|
| `rol` | Define los roles de los usuarios |
| `sede` | Registra las sucursales deportivas |
| `usuario` | Almacena usuarios y sus relaciones con roles y sedes |
| `credencial_qr` | Información vinculada a credenciales QR |
| `plan_membresia` | Planes comerciales disponibles |
| `membresia` | Contratación y estados de membresías |
| `acceso` | Ingresos y egresos de usuarios |
| `tipo_clase` | Catálogo de disciplinas grupales |
| `instructor` | Instructores registrados |
| `clase` | Clases programadas |
| `reserva_clase` | Reservas de clases |
| `lista_espera_clase` | Usuarios en espera por cupos |
| `tipo_cancha` | Catálogo de disciplinas deportivas |
| `cancha` | Instalaciones deportivas |
| `reserva_cancha` | Turnos reservados |
| `pago` | Operaciones de pago simuladas |
| `comprobante` | Comprobantes asociados a pagos |

Estas entidades se relacionan mediante claves foráneas.

Por ejemplo:

- Un usuario tiene un rol.
- Un usuario puede tener una sede base.
- Una sede tiene múltiples canchas y clases.
- Una cancha pertenece a un tipo de cancha.
- Una reserva de cancha pertenece a una cancha y a un usuario.
- Una clase pertenece a una sede y a un instructor.
- Una membresía relaciona a un usuario con un plan.
- Un pago puede corresponder a una membresía o a una reserva de cancha.

El diseño relacional permite evitar duplicaciones innecesarias y mantener reglas consistentes entre los módulos.

### 5.1 Ejemplo de relación entre usuarios y sedes

El modelo `usuario` contiene la propiedad:

```prisma id="9w4ngh"
sede_base_id Int?
```

La relación con `sede` está definida mediante Prisma.

Este campo permite identificar la sede asociada al usuario.

La relación también resulta importante para implementar las restricciones de acceso de los usuarios con rol Gerente.

### 5.2 Ejemplo de restricción de unicidad

El modelo `cancha` define:

```prisma id="24pqcu"
@@unique([sede_id, nombre])
```

Esto impide registrar dos canchas con el mismo nombre dentro de una misma sede.

Dos sedes diferentes pueden utilizar nombres equivalentes sin entrar en conflicto.

### 5.3 Tipos monetarios

Los importes se almacenan mediante tipos decimales:

```prisma id="0e8xdg"
costo_hora Decimal @db.Decimal(10, 2)
```

Esta decisión permite almacenar valores monetarios con precisión decimal definida, evitando depender exclusivamente de la representación binaria de números de coma flotante.

En el modelo también se utilizan campos decimales para los precios de planes, descuentos, recargos, penalidades y pagos.

## 6. Integridad transaccional y control de concurrencia

Uno de los principales motivos para seleccionar PostgreSQL fue la necesidad de garantizar consistencia en operaciones concurrentes.

FitZone Sports debe cumplir dos reglas especialmente importantes:

**RN-01:** un usuario no puede mantener ingresos activos simultáneamente en sedes diferentes.

**RN-02:** no pueden existir dos reservas activas para la misma cancha, fecha y horario.

Para implementar estas reglas, el sistema utiliza índices únicos parciales definidos directamente en PostgreSQL.

### 6.1 Prevención de sobreventa de canchas — RN-02

Cuando varios usuarios intentan reservar el mismo turno simultáneamente, una validación previa de disponibilidad no es suficiente.

Dos solicitudes pueden consultar el mismo turno antes de que alguna de ellas registre su reserva.

Por esta razón, se utiliza el siguiente índice:

```sql id="jmbuoz"
CREATE UNIQUE INDEX "ux_reserva_cancha_slot"
ON "reserva_cancha"(
    "cancha_id",
    "fecha",
    "hora_inicio"
)
WHERE "estado" <> 'CANCELADA';
```

La restricción garantiza que exista como máximo una reserva no cancelada para una misma cancha, fecha y horario.

Las reservas con estado `CANCELADA` no quedan sujetas a esa restricción y, por lo tanto, permiten reutilizar el turno.

### Funcionamiento esperado

Supongamos que doce usuarios intentan reservar la misma cancha para el mismo día y horario.

Aunque las doce solicitudes lleguen prácticamente al mismo tiempo, PostgreSQL debe permitir solamente una reserva activa para ese turno.

Las restantes operaciones deben fallar por conflicto de unicidad.

En el backend, los errores de unicidad conocidos de Prisma pueden traducirse a respuestas HTTP `409 Conflict`.

Esta decisión complementa la validación previa de disponibilidad y evita que una condición de carrera genere reservas duplicadas.

### 6.2 Prevención de ingresos simultáneos — RN-01

El sistema también implementa:

```sql id="26j2eq"
CREATE UNIQUE INDEX "ux_acceso_activo_por_usuario"
ON "acceso"("usuario_id")
WHERE "egreso_at" IS NULL;
```

Esta restricción impide registrar dos accesos abiertos para un mismo usuario.

Mientras el campo `egreso_at` permanezca en `NULL`, se considera que el ingreso sigue activo.

Una vez registrado el egreso, el usuario puede iniciar otro ingreso conforme a las demás reglas.

Esto ayuda a impedir que una misma membresía sea utilizada simultáneamente en dos sedes.

### 6.3 Restricciones sobre clases y listas de espera

La migración también define:

```sql id="m6c86b"
CREATE UNIQUE INDEX "ux_reserva_clase_activa"
ON "reserva_clase"("usuario_id", "clase_id")
WHERE "estado" = 'CONFIRMADA';
```

Este índice impide que un usuario tenga dos reservas confirmadas para una misma clase.

Además, incorpora:

```sql id="j6kzeh"
CREATE UNIQUE INDEX "ux_lista_espera_activa"
ON "lista_espera_clase"("usuario_id", "clase_id")
WHERE "estado" = 'EN_ESPERA';
```

Esta segunda restricción evita que un usuario mantenga dos entradas activas de espera para la misma clase.

### 6.4 Transacciones ACID

PostgreSQL ofrece transacciones con propiedades ACID:

**Atomicidad:** las operaciones incluidas en una transacción se confirman o revierten como una unidad.

**Consistencia:** las modificaciones deben respetar las restricciones de integridad declaradas.

**Aislamiento:** las transacciones concurrentes interactúan de acuerdo con el nivel de aislamiento configurado.

**Durabilidad:** una vez confirmado un cambio, el motor utiliza sus mecanismos de persistencia para conservarlo frente a fallos contemplados por su diseño.

En el proyecto, Prisma permite agrupar operaciones mediante `$transaction`.

Por ejemplo, el proceso de cancelación de una reserva de clase y la asignación de su cupo a un usuario en lista de espera necesita coordinar distintas modificaciones.

La utilización de transacciones contribuye a mantener el sistema consistente si alguna de ellas falla.

Es importante aclarar que **una transacción por sí sola no impide todas las condiciones de carrera**.

La garantía de unicidad de turnos se apoya específicamente en el índice único parcial de PostgreSQL.

## 7. Índices y rendimiento de consultas — RNF-03

Además de garantizar integridad, PostgreSQL se utiliza para optimizar las consultas frecuentes.

La grilla de disponibilidad de canchas requiere buscar reservas de acuerdo con:

- Identificador de cancha.
- Fecha.
- Hora de inicio.

Para facilitar este tipo de consulta se creó el índice:

```sql id="sl9ybm"
CREATE INDEX "ix_reserva_cancha_disponibilidad"
ON "reserva_cancha"(
    "cancha_id",
    "fecha",
    "hora_inicio"
);
```

El índice permite que PostgreSQL considere un acceso indexado cuando las condiciones de consulta y el plan de ejecución lo justifican.

### 7.1 Beneficio esperado

Sin índices apropiados, ciertas consultas pueden requerir examinar una cantidad mayor de registros.

Mediante una estructura de búsqueda sobre los campos utilizados con mayor frecuencia, es posible reducir el trabajo necesario para localizar reservas específicas.

La eficacia real depende de factores como:

- Volumen de datos.
- Distribución de valores.
- Selectividad de los filtros.
- Estadísticas del optimizador.
- Cantidad de registros activos.
- Recursos disponibles en el servidor.

### 7.2 Medición

PostgreSQL dispone de:

```sql id="nqv7nm"
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM reserva_cancha
WHERE cancha_id = 1
  AND fecha = DATE '2026-11-20'
  AND hora_inicio = 19;
```

Este procedimiento permite inspeccionar el plan de ejecución y los recursos utilizados por la consulta.

El proyecto documenta una medición de **0,068 ms** en la evidencia del requisito RNF-03.

Ese valor debe interpretarse como resultado de una ejecución y un entorno determinados, no como garantía de respuesta constante para cualquier volumen de información.

La evidencia se encuentra en:

`docs/rnf/RNF-03.md`

## 8. Integración con NestJS y Prisma ORM

### 8.1 Organización del acceso a datos

El backend utiliza la siguiente estructura conceptual:

```text id="f0x3j2"
        Controlador NestJS
                |
                v
         Servicio de negocio
                |
                v
             Repository
                |
                v
           PrismaService
                |
                v
            PostgreSQL
```

Los servicios de negocio no necesitan construir manualmente todas las sentencias SQL.

En su lugar, utilizan repositorios que encapsulan las operaciones de Prisma.

### 8.2 PrismaService

El archivo:

`backend/src/prisma/prisma.service.ts`

define una clase que extiende `PrismaClient`.

Esta clase implementa los mecanismos de conexión y desconexión vinculados al ciclo de vida del módulo NestJS:

```typescript id="n1wq3a"
@Injectable()
export class PrismaService
  extends PrismaClient
  implements OnModuleInit, OnModuleDestroy
{
  async onModuleInit() {
    await this.$connect();
  }

  async onModuleDestroy() {
    await this.$disconnect();
  }
}
```

Su función es centralizar el cliente Prisma que utilizan los repositorios.

### 8.3 Conexión mediante variables de entorno

La base de datos se configura mediante:

```prisma id="4d6z6i"
datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}
```

Esto permite utilizar distintas conexiones según el entorno sin modificar el esquema Prisma.

Las credenciales reales deben proporcionarse mediante variables de entorno o mecanismos seguros de configuración.

No corresponde incorporar contraseñas productivas al repositorio.

### 8.4 Migraciones

Las migraciones se almacenan en:

`backend/prisma/migrations/`

Las principales son:

- `0_init`: estructura relacional inicial.
- `20261118000000_indices_parciales_y_disponibilidad`: índices de integridad y rendimiento.
- `20261118010000_reserva_cancha_cumplida_y_penalidad`: evolución de estados y penalidades de reservas deportivas.
- `20261118020000_reserva_clase_penalidad`: modificaciones relacionadas con penalidades de clases.

Esta estructura permite reproducir las modificaciones del modelo de datos de forma controlada.

El comando utilizado para aplicar migraciones ya creadas es:

```bash id="o9vye1"
cd backend
npm run db:migrate
```

La generación del cliente Prisma se realiza mediante:

```bash id="9mck1g"
npx prisma generate
```

Las migraciones SQL especiales deben conservarse incluso cuando también existan definiciones equivalentes o relacionadas dentro de `schema.prisma`.

## 9. Consecuencias de la decisión

### 9.1 Consecuencias positivas

**Integridad de los datos**

Las claves foráneas y las restricciones reducen el riesgo de registrar relaciones inválidas o información inconsistente.

**Control de concurrencia**

Los índices únicos parciales permiten proteger reglas críticas incluso frente a solicitudes simultáneas.

**Mantenimiento del modelo**

Prisma ofrece una representación centralizada del esquema y herramientas para administrar cambios.

**Compatibilidad con TypeScript**

El cliente Prisma generado permite trabajar con consultas y resultados tipados.

**Optimización de consultas**

PostgreSQL ofrece índices y herramientas para inspeccionar el rendimiento.

**Escalabilidad funcional**

La incorporación de nuevas sedes se realiza mediante datos relacionados, sin necesitar crear nuevas tablas por sucursal.

**Reproducibilidad**

El proyecto puede utilizar PostgreSQL dentro de Docker y aplicar migraciones para reconstruir una base de desarrollo.

### 9.2 Consecuencias negativas

**Administración adicional**

Se necesita mantener PostgreSQL, administrar conexiones y establecer procedimientos de respaldo y recuperación.

**Dependencia tecnológica**

El proyecto utiliza funcionalidades específicas de PostgreSQL, especialmente los índices parciales.

Migrar a otro motor requeriría adaptar estas reglas.

**Complejidad de las migraciones**

Algunos cambios necesitan SQL manual además de las herramientas estándar de Prisma.

**Conocimientos técnicos**

Los desarrolladores deben comprender las relaciones, los índices, las transacciones y los errores de integridad.

**Costo de consultas incorrectas**

Un diseño inadecuado de consultas o índices puede degradar el rendimiento a medida que crece el volumen de datos.

**Base de datos compartida**

Todos los módulos dependen de una misma instancia lógica de persistencia, lo que exige planificar su disponibilidad y evitar dependencias innecesarias.

## 10. Relación con los requisitos del proyecto

### RN-01 — Prohibición de ingresos simultáneos

Se utiliza un índice único parcial que impide registrar más de un acceso abierto por usuario.

### RN-02 — Prevención de sobreventa

Se utiliza un índice único parcial que permite una única reserva no cancelada por cancha, fecha y horario.

### RN-03 — Control de membresías y mora

El modelo relacional permite consultar el estado de la membresía del usuario y relacionarlo con las operaciones de acceso y reserva.

### RNF-03 — Rendimiento

Se incorporan índices sobre los campos más utilizados en las consultas de disponibilidad.

Los planes de ejecución pueden analizarse mediante `EXPLAIN ANALYZE`.

### RNF-04 — Incorporación de nuevas sedes

El diseño contempla una entidad `sede` relacionada con usuarios, accesos, clases y canchas.

Agregar una sucursal no requiere modificar la estructura básica de las tablas ni reiniciar el servidor exclusivamente por ese registro.

La posibilidad de escalar la capacidad total del sistema sigue dependiendo de la infraestructura y de las pruebas realizadas.

## 12. Evolución futura de la decisión

La utilización de PostgreSQL permite mantener una base relacional centralizada durante la etapa actual del proyecto.

Si la cantidad de sedes, usuarios y reservas aumentara considerablemente, podrían evaluarse medidas adicionales como:

1. Optimización de consultas mediante índices y análisis de ejecución.
2. Configuración y monitoreo del pool de conexiones.
3. Incorporación de réplicas de lectura, si la carga lo justifica.
4. Estrategias de particionamiento para tablas con grandes volúmenes históricos.
5. Mantenimiento y archivado de registros antiguos conforme a las necesidades de negocio.
6. Monitoreo de bloqueos, transacciones y tiempos de respuesta.
7. Automatización de respaldos y verificación periódica de restauraciones.

Estas medidas representan **posibilidades de evolución**, no funcionalidades que se declaran implementadas actualmente.

La decisión de migrar a otro motor debería quedar registrada en un nuevo ADR, acompañado por una evaluación de costos, riesgos y mecanismos para conservar la integridad de los datos.

## 13. Conclusión

Se adoptó **PostgreSQL como motor de base de datos relacional**, complementado con Prisma ORM, porque ofrece las capacidades necesarias para garantizar la integridad de información y administrar operaciones transaccionales dentro de FitZone Sports.

La selección resulta especialmente importante por las reglas de negocio asociadas a la reserva de canchas y al control de accesos.

Los índices únicos parciales permiten trasladar determinadas garantías de consistencia directamente a PostgreSQL, evitando depender exclusivamente de validaciones realizadas en el backend.

La utilización de Prisma facilita el desarrollo con NestJS y TypeScript, mientras que las migraciones SQL permiten aprovechar capacidades avanzadas del motor cuando el ORM no las representa directamente.

Frente a las alternativas consideradas, PostgreSQL proporciona un equilibrio favorable entre **consistencia, rendimiento, capacidad de crecimiento, soporte transaccional y facilidad de integración**.

Esta decisión complementa la arquitectura de monolito modular seleccionada en el ADR-001 y establece las bases de persistencia para los diferentes módulos funcionales.

**Decisión final: mantener PostgreSQL como sistema de gestión de bases de datos relacionales de FitZone Sports, utilizando Prisma ORM y migraciones SQL específicas para garantizar las reglas críticas de integridad y concurrencia.**
