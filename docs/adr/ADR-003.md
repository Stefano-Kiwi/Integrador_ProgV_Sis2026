# ADR-003 — Estrategia de funcionamiento offline del control de acceso

**Estado:** Aceptado  
**Fecha de registro:** 19 de noviembre de 2026  
**Proyecto:** FitZone Sports — Trabajo Integrador Final  
**Equipo:** 12  
**Unidad temática:** Arquitectura de Software — Disponibilidad y tolerancia a fallos  
**Requisitos relacionados:** RNF-01, RF-03, RF-04, RF-05 y RN-01  
**Decisión complementaria:** ADR-007 — Sincronización del terminal de sede

---

## 1. Contexto

FitZone Sports es una plataforma de gestión de gimnasios y complejos deportivos que permite a los socios utilizar sus membresías en distintas sedes de la cadena.

Uno de los procesos más importantes del sistema es el **control de acceso a las instalaciones**, mediante el cual el personal de recepción verifica la identidad y el estado de la membresía de cada socio.

En condiciones normales, el usuario presenta un código QR dinámico desde su dispositivo móvil. El terminal de recepción lee el código, se comunica con el servidor central y solicita la validación correspondiente.

El backend comprueba la autenticidad del código, su vencimiento, el estado de la membresía y la existencia de ingresos activos. Si se cumplen las condiciones, registra el ingreso.

Sin embargo, este procedimiento presenta una dependencia importante: **la disponibilidad de la conexión entre el terminal de sede y el servidor central**.

Una interrupción de Internet podría impedir el ingreso de socios, aunque sus membresías se encuentren activas.

Esto genera un problema operativo porque el control de acceso constituye una actividad permanente de las instalaciones.

La indisponibilidad del servidor central no debería obligar automáticamente a detener toda la recepción de usuarios.

### 1.1 Problema identificado

El sistema debe responder a las siguientes situaciones:

- Pérdida temporal de conectividad a Internet.
- Interrupción de la comunicación con la API.
- Latencia excesiva o falta de respuesta del servidor.
- Imposibilidad de consultar las membresías en tiempo real.
- Necesidad de registrar ingresos mientras la base de datos central no está disponible para el terminal.
- Recuperación posterior de la conexión.
- Posibles conflictos entre operaciones locales y el estado actualizado de la base de datos.

Estas situaciones requieren una estrategia que permita continuar con determinadas operaciones, pero también que preserve la coherencia del sistema central.

### 1.2 Requisito no funcional asociado

El requisito **RNF-01** establece la necesidad de disponer de mecanismos de continuidad operativa para el control de acceso cuando se pierde la conexión principal.

La documentación del proyecto también establece una meta de disponibilidad del 99,5 %.

Para atender este requisito se consideró necesario diseñar una solución capaz de:

1. Conservar localmente información relevante de los socios.
2. Consultar esa información sin conexión.
3. Registrar temporalmente los ingresos realizados.
4. Recuperar los registros pendientes cuando vuelva la conectividad.
5. Detectar operaciones repetidas y conflictos.
6. Mantener la trazabilidad de lo ocurrido durante la interrupción.

La solución debía integrarse con la arquitectura existente de NestJS, React, TypeScript y PostgreSQL, sin introducir una infraestructura distribuida desproporcionada para el alcance del proyecto.

## 2. Decisión

Se decidió implementar una **estrategia de operación offline basada en snapshots locales de socios activos y una cola persistente de ingresos pendientes de sincronización**.

La aplicación utiliza un modelo de funcionamiento híbrido:

**Modo online:** el terminal consulta al servidor central y recibe una respuesta de autorización definitiva.

**Modo offline:** el terminal consulta una copia local previamente descargada y registra provisionalmente el ingreso para su posterior reconciliación con el servidor.

El mecanismo combina:

- Un backend NestJS encargado de proporcionar los datos de referencia.
- Un terminal web desarrollado con React.
- Almacenamiento local mediante `localStorage`.
- Un snapshot de socios con membresía activa.
- Una cola de ingresos registrados sin conexión.
- Un endpoint de sincronización por lotes.
- Validación posterior de los eventos en el backend.

Se decidió mantener PostgreSQL como **fuente de verdad central**.

Los registros locales no sustituyen permanentemente la base de datos; representan operaciones provisionales que deben confirmarse o identificarse como conflictivas al recuperar la conectividad.

### 2.1 Principio arquitectónico

La decisión se basa en separar dos necesidades:

**Continuidad operativa:** el personal de recepción debe poder seguir realizando determinadas validaciones durante una interrupción de red.

**Consistencia definitiva:** la base de datos central debe conservar la responsabilidad de confirmar los ingresos y aplicar las reglas de negocio globales.

Esta separación permite ofrecer un funcionamiento degradado sin abandonar el modelo centralizado de información.

### 2.2 Arquitectura propuesta e implementada

```text
                 SOCIO
                   |
                   v
             CÓDIGO QR
                   |
                   v
        TERMINAL DE RECEPCIÓN
              React / Web
                   |
             ¿Hay conexión?
                /       \
              Sí         No
              |          |
              v          v
          API NestJS   Snapshot local
              |          |
              v          v
        Validación     Validación
         central        provisoria
              |          |

```

El diagrama representa la arquitectura funcional.

En la implementación actual, el frontend primero intenta realizar la validación online. Si detecta una falla de conectividad, utiliza el snapshot local.

Los errores de negocio enviados por la API, como una membresía inactiva o un ingreso duplicado, no se tratan como una autorización para recurrir al modo offline.

## 3. Alternativas consideradas

Para resolver la necesidad de continuidad operativa se consideraron cuatro alternativas principales.

### 3.1 Alternativa A — Validación exclusivamente online

Consiste en exigir que cada lectura de QR sea validada directamente por el servidor central.

En este modelo, el terminal no conserva información suficiente para autorizar ingresos sin conexión.

**Ventajas:**

- Siempre utiliza la información disponible en la base de datos central.
- Simplifica la administración de estados.
- Evita almacenar datos de socios en los terminales.
- No requiere implementar procesos de sincronización.
- Las reglas globales se comprueban antes de registrar cada ingreso.
- Reduce las diferencias entre información local y central.

**Desventajas:**

- Depende completamente de la conectividad.
- Una caída de Internet puede detener los ingresos.
- La disponibilidad percibida por cada sede depende también de su proveedor de conexión.
- El personal no dispone de una alternativa automatizada ante una interrupción.
- Una caída prolongada puede producir demoras operativas y acumulación de socios en recepción.

**Motivo de descarte:**

No satisface el objetivo principal del RNF-01.

Aunque ofrece una validación centralizada consistente, genera una dependencia operativa excesiva de la conectividad.

### 3.2 Alternativa B — Snapshot local y cola de sincronización (seleccionada)

Consiste en descargar previamente una copia de los socios habilitados y utilizarla cuando el servidor central no se encuentra disponible.

Los ingresos realizados en ese estado se almacenan localmente hasta que puedan transmitirse al backend.

**Ventajas:**

- Permite continuar determinadas operaciones durante una caída de conexión.
- No requiere mantener una segunda base de datos PostgreSQL en cada sede.
- Puede implementarse dentro de la aplicación React existente.
- Reutiliza los endpoints de control de acceso de NestJS.
- La sincronización permite recuperar los registros acumulados.
- Facilita una experiencia de recepción similar en modo online y offline.
- Reduce la complejidad de infraestructura para el alcance académico.

**Desventajas:**

- Los datos locales pueden quedar desactualizados.
- La autorización provisional no equivale a la confirmación definitiva.
- Existen posibles conflictos al recuperar la conexión.
- Se almacenan datos personales en el dispositivo.
- El almacenamiento del navegador tiene limitaciones de capacidad, seguridad y persistencia.
- Se requiere una política clara de actualización y eliminación de snapshots.
- La validación de códigos QR sin conexión plantea desafíos criptográficos adicionales.

**Evaluación:**

Se seleccionó esta alternativa porque ofrece un equilibrio adecuado entre continuidad operativa y complejidad técnica.

Además, permite aprovechar la arquitectura web existente sin desplegar servidores independientes en cada sucursal.

### 3.3 Alternativa C — Base de datos local por sede con replicación

Consiste en implementar una base de datos local en cada sucursal, que mantenga información sobre usuarios, membresías e ingresos.

Cada sede podría disponer de un servicio propio para procesar las operaciones mientras se encuentre desconectada.

Posteriormente, las bases locales se sincronizarían con el servidor central.

**Ventajas:**

- Mayor independencia de cada sede.
- Posibilidad de manejar más operaciones locales.
- Consultas sin necesidad de conectividad externa.
- Mayor capacidad para almacenar información histórica.
- Mejor control sobre transacciones locales si se utiliza un motor apropiado.

**Desventajas:**

- Requiere mantener infraestructura adicional en todas las sedes.
- Aumenta los costos de instalación, actualización y soporte.
- Introduce problemas complejos de replicación.
- Es necesario definir políticas de resolución de conflictos.
- Puede haber diferencias entre el estado de distintas sucursales.
- La seguridad y protección de datos deben administrarse en múltiples ubicaciones.
- Requiere monitoreo, respaldo y recuperación local.

**Motivo de descarte:**

El proyecto no necesitaba incorporar una arquitectura distribuida completa para lograr una continuidad básica del control de acceso.

La complejidad de mantener una base de datos por sede se consideró excesiva para las necesidades y recursos actuales.

### 3.4 Alternativa D — Registro manual de ingresos

Consiste en permitir que el personal registre los ingresos manualmente, por ejemplo, utilizando planillas o formularios físicos cuando se interrumpe el servicio.

Al recuperar la conexión, los datos deberían cargarse en la aplicación.

**Ventajas:**

- No requiere una implementación tecnológica compleja.
- Puede utilizarse como último recurso.
- Permite continuar registrando información básica.
- No necesita que el navegador conserve datos de socios.

**Desventajas:**

- Mayor riesgo de errores humanos.
- No permite verificar automáticamente todas las condiciones.
- La información puede resultar ilegible o incompleta.
- La carga posterior requiere trabajo adicional.
- Puede generar registros duplicados.
- Es difícil garantizar un orden y una trazabilidad precisos.
- No ofrece la misma experiencia operativa que una validación automatizada.

**Motivo de descarte:**

Aunque podría utilizarse como medida de contingencia excepcional, no se consideró apropiada como estrategia principal.

FitZone Sports busca automatizar el control de accesos y conservar registros estructurados que puedan sincronizarse posteriormente.

## 4. Comparación de alternativas

| Criterio | Solo online | Snapshot + cola | Base local por sede | Registro manual |
|---|---|---|---|---|
| Funciona sin conexión | No | **Parcialmente** | Sí | Sí |
| Complejidad inicial | Baja | Media | Alta | Baja |
| Infraestructura adicional | No | No | Sí | No |
| Información central actualizada | Sí | No siempre | No siempre | No |
| Sincronización posterior | No aplica | Sí | Sí | Manual |
| Consistencia inmediata global | Alta | No garantizada | No garantizada | No garantizada |
| Automatización | Alta | Alta | Alta | Baja |
| Adecuación al proyecto | Baja | **Alta** | Media | Baja |

La comparación representa una evaluación cualitativa de alternativas.

El funcionamiento offline de la alternativa seleccionada se considera parcial porque depende de disponer previamente de un snapshot y de una credencial QR todavía válida.

**Resultado de la evaluación:** se eligió la estrategia de snapshot y cola local porque permite mantener un nivel de continuidad operativa sin introducir una infraestructura distribuida compleja.

## 5. Funcionamiento de la estrategia seleccionada

### 5.1 Descarga del snapshot de socios

Cuando el terminal dispone de conexión, puede solicitar una copia de los socios habilitados mediante el endpoint:

```http
GET /acceso/sedes/:sedeId/snapshot
```

El backend consulta las membresías con estado `ACTIVO` y construye una respuesta con la información necesaria para identificar a los socios.

El snapshot contiene datos como:

- Identificador del socio.
- DNI.
- Nombre.
- Apellido.
- Estado de la membresía.
- Fecha de finalización.
- Identificador de la sede.
- Fecha de generación.

El conjunto de socios incluye membresías activas de la red porque FitZone Sports permite el acceso multi-sede.

No se almacenan las contraseñas de los usuarios dentro del snapshot.

### 5.2 Almacenamiento local

El frontend utiliza `localStorage` para conservar el snapshot.

La clave se construye utilizando el identificador de la sede:

```typescript
const snapshotKey = (sedeId: number) =>
  `fitzone_snapshot_sede_${sedeId}`;
```

Esto permite mantener copias diferenciadas para distintos terminales o sedes seleccionadas dentro del navegador.

La función `descargarSnapshotSede` obtiene los datos desde la API y los conserva en el almacenamiento local.

Si se interrumpe la conexión, `leerSnapshotLocal` intenta recuperar la última copia disponible.

### 5.3 Generación del código QR

El socio obtiene un código QR dinámico desde el backend mediante:

```http
GET /acceso/qr
```

El QR contiene un token compuesto por un payload codificado y una firma HMAC-SHA256.

El payload identifica al usuario e incluye información temporal:

```typescript
interface QrTokenPayload {
  userId: number;
  win: number;
  iat: number;
  exp: number;
}
```

La validez prevista del código es de 60 segundos.

Esto significa que no se utiliza una credencial estática permanente.

La decisión de utilizar códigos rotativos busca reducir el riesgo de reutilización de credenciales capturadas previamente.

### 5.4 Validación online

En condiciones normales, el terminal envía el QR y la sede al backend:

```http
POST /acceso/validar
```

El servidor:

1. Verifica el formato del token.
2. Comprueba su firma HMAC-SHA256.
3. Verifica el vencimiento.
4. Comprueba que la sede exista.
5. Consulta la membresía del usuario.
6. Comprueba que no tenga otro ingreso activo.
7. Registra el ingreso en PostgreSQL.
8. Devuelve la autorización correspondiente.

Este es el flujo que ofrece las garantías completas de validación central.

### 5.5 Activación del modo offline

Si no hay conexión o se produce un error de red, el terminal utiliza el mecanismo local.

El servicio encargado es:

`frontend/src/services/controlAccesoService.ts`

La función principal es:

```typescript
validarAccesoOffline(qr, sedeId)
```

Esta función:

1. Decodifica el contenido del token.
2. Comprueba que tenga la estructura esperada.
3. Verifica que el tiempo de expiración no haya transcurrido.
4. Recupera el snapshot local.
5. Busca el identificador del socio.
6. Comprueba que la membresía figure como `ACTIVO`.
7. Construye un registro de ingreso pendiente.
8. Guarda el registro en la cola local.
9. Devuelve una autorización provisional al terminal.

Si no existe un snapshot para la sede o el socio no figura como activo, se rechaza la validación local.

### 5.6 Registro provisional de ingresos

Los ingresos generados en modo offline se representan mediante el siguiente contrato:

```typescript
interface IngresoOfflineItem {
  userId: number;
  sedeId: number;
  timestamp: string;
  qrToken: string;
}
```

Estos datos se almacenan en una cola persistente del navegador.

La clave utilizada es:

```typescript
const COLA_OFFLINE_KEY =
  "fitzone_cola_accesos_offline";
```

El registro contiene la información necesaria para que el backend pueda analizar posteriormente el ingreso.

La cola permite conservar los eventos mientras el navegador mantenga su almacenamiento.

### 5.7 Recuperación de conectividad

Cuando el sistema vuelve a estar online, el frontend intenta enviar los registros pendientes.

El endpoint utilizado es:

```http
POST /acceso/sincronizar
```

La solicitud contiene un conjunto de eventos:

```json
{
  "ingresos": [
    {
      "userId": 15,
      "sedeId": 2,
      "timestamp": "2026-11-19T14:30:00.000Z",
      "qrToken": "<TOKEN_QR>"
    }
  ]
}
```

El servidor analiza cada evento y devuelve información sobre las operaciones aceptadas y los conflictos encontrados.

La implementación de referencia intenta sincronizar al recuperar la conexión y realiza comprobaciones periódicas cada 30 segundos mientras existe conectividad.

La definición detallada de la reconciliación y sus conflictos corresponde al **ADR-007**.

## 6. Manejo de conflictos y consistencia

La estrategia offline introduce una diferencia importante entre los estados local y central.

Durante una interrupción de red, el terminal no puede garantizar que la información almacenada coincida con la situación actual de PostgreSQL.

### 6.1 Membresías modificadas

Una membresía puede haber vencido o sido suspendida después de que el terminal descargó su snapshot.

El terminal podría encontrar al socio como activo en la copia local aunque el servidor central ya haya actualizado su estado.

En ese caso, el ingreso local sería provisional y podría resultar rechazado durante la sincronización.

### 6.2 Ingresos simultáneos

La regla RN-01 impide que un usuario tenga ingresos abiertos en dos sedes al mismo tiempo.

En modo online, PostgreSQL garantiza esta restricción mediante un índice único parcial.

En modo offline, un terminal desconectado no conoce necesariamente los ingresos que se produjeron en otras sedes.

Por lo tanto, **la prevención global de ingresos simultáneos no puede garantizarse completamente mientras el terminal está aislado**.

El conflicto debe detectarse al sincronizar.

### 6.3 Registros duplicados

Una solicitud de sincronización puede repetirse debido a un problema de red.

El backend implementa una comprobación para identificar eventos ya registrados utilizando:

- Usuario.
- Sede.
- Marca temporal del ingreso.

Cuando encuentra un registro equivalente, lo informa como duplicado sin volver a crearlo.

### 6.4 Conflictos de sincronización

Los eventos pueden rechazarse por diferentes motivos:

- Firma QR inválida.
- QR correspondiente a otro usuario.
- Membresía inactiva.
- Existencia de un ingreso abierto.
- Incompatibilidad con una restricción de PostgreSQL.

El backend diferencia las operaciones aceptadas de las conflictivas para que el terminal pueda mostrar el resultado al operador.

### 6.5 Confirmación definitiva

La autorización local no equivale necesariamente a un ingreso confirmado en la base de datos.

La fuente de verdad sigue siendo PostgreSQL.

El registro se considera definitivamente incorporado al sistema central cuando el backend lo procesa y acepta.

## 7. Consideraciones de seguridad

La utilización de información local requiere analizar riesgos específicos.

### 7.1 Protección de datos personales

Los snapshots incluyen información identificatoria de los socios.

Aunque no contienen contraseñas, datos como el DNI y el estado de membresía deben considerarse información personal.

El terminal debería utilizarse en dispositivos controlados por la organización.

Además, se recomienda restringir el acceso físico y lógico al navegador donde se almacena la información.

### 7.2 Almacenamiento del navegador

`localStorage` facilita la implementación y conserva los datos entre recargas de la página.

Sin embargo, tiene limitaciones:

- La información no se cifra automáticamente a nivel de aplicación.
- El almacenamiento puede ser eliminado por el usuario o el navegador.
- Un script malicioso ejecutado dentro del mismo origen podría acceder a los datos.
- No ofrece las mismas garantías transaccionales que una base de datos dedicada.
- La disponibilidad de los datos depende del dispositivo y del perfil del navegador.

Por estos motivos, se considera una solución adecuada para el alcance académico, pero requiere medidas adicionales de protección para su utilización en un entorno productivo.

### 7.3 Autenticidad de códigos QR

El backend genera los tokens utilizando HMAC-SHA256.

En condiciones normales, también verifica su firma antes de autorizar un ingreso.

**Limitación de la implementación actual:**

La función offline del frontend decodifica el payload del token y comprueba su expiración, pero **no verifica criptográficamente la firma HMAC en el propio navegador**.

La firma se comprueba posteriormente cuando el evento llega al backend.

Por lo tanto, durante el período de desconexión existe un riesgo de aceptación provisional de un token cuyo contenido haya sido manipulado.

Esta limitación debe documentarse expresamente y no presentarse como una validación offline criptográficamente equivalente a la online.

### 7.4 Mejora de seguridad recomendada

Una evolución de esta estrategia debería permitir que el terminal compruebe localmente la autenticidad de las credenciales sin exponer secretos del servidor.

Una posibilidad sería utilizar firmas digitales asimétricas:

- El servidor firma las credenciales mediante una clave privada.
- El terminal dispone de una clave pública para verificarlas.
- La clave privada nunca necesita distribuirse a las sucursales.

Este mecanismo permitiría fortalecer las validaciones offline.

Se trata de una **mejora futura propuesta**, no de una funcionalidad implementada en el código de referencia.

### 7.5 Vigencia de los datos locales

La implementación actual conserva el snapshot descargado, pero no impone una caducidad automática que obligue a rechazar copias antiguas.

Esto representa un riesgo porque una membresía puede cambiar de estado durante una desconexión prolongada.

Se recomienda establecer una política de antigüedad máxima del snapshot y actualizarlo periódicamente.

## 8. Consecuencias de la decisión

### 8.1 Consecuencias positivas

**Mayor continuidad operativa**

El terminal puede continuar realizando determinadas validaciones cuando se pierde la conexión.

**Menor dependencia de la red**

No todas las operaciones necesitan una consulta inmediata al backend.

**Integración con la arquitectura existente**

Se reutilizan React, NestJS y PostgreSQL, sin crear servidores locales adicionales.

**Registro estructurado de eventos**

Los ingresos pendientes se almacenan con información suficiente para su procesamiento posterior.

**Recuperación del estado central**

La sincronización permite enviar los eventos acumulados cuando vuelve la conexión.

**Trazabilidad**

El backend puede diferenciar ingresos aceptados, duplicados y conflictivos.

**Mantenimiento simplificado**

El mecanismo se implementa mediante servicios del frontend y endpoints específicos del módulo Acceso.

### 8.2 Consecuencias negativas

**Consistencia eventual**

El estado local puede diferir del estado central mientras no existe conectividad.

**Riesgo de autorizaciones provisionales incorrectas**

Una membresía puede encontrarse desactualizada o existir un ingreso activo en otra sede.

**Dependencia del snapshot previo**

Si no se descargó una copia local, el terminal no puede utilizar el mecanismo offline.

**Dependencia de credenciales válidas**

El QR dinámico vence cada 60 segundos. Si el socio necesita generar una nueva credencial mientras el backend está inaccesible, el mecanismo actual puede no permitirlo.

**Limitaciones del almacenamiento**

Los datos del navegador pueden perderse o ser modificados.

**Mayor complejidad de pruebas**

Es necesario evaluar tanto el flujo online como las transiciones hacia el modo offline y la recuperación de la conexión.

**Seguridad local incompleta**

La verificación de firma HMAC no está implementada en el navegador.

**Gestión de conflictos**

Al recuperar la conexión pueden aparecer operaciones que no satisfagan las reglas centrales y necesiten intervención operativa.

## 9. Relación con los requisitos

### RNF-01 — Disponibilidad y operación offline

La estrategia busca mantener el control de acceso durante interrupciones temporales mediante snapshots y registro local de ingresos.

El mecanismo implementado aporta continuidad parcial, pero **no certifica por sí mismo el cumplimiento de una disponibilidad del 99,5 %**.

Para acreditar esa meta sería necesario disponer de mediciones de disponibilidad en un período representativo.

### RF-03 — Acceso multi-sede

El snapshot incluye socios activos de la red.

Esto permite que el terminal pueda identificar socios cuya sede base sea diferente de la sede donde intentan ingresar.

La validación definitiva de las reglas globales se efectúa en el backend.

### RF-04 — Código QR dinámico

El sistema emite códigos rotativos con validez de 60 segundos y firma HMAC-SHA256.

La validación offline debe considerar la expiración temporal de la credencial.

### RF-05 — Control de aforo

Los ingresos offline pueden reflejarse provisionalmente en la información visual del terminal.

Sin embargo, el aforo central no incorpora esos eventos hasta la sincronización.

Por lo tanto, durante una desconexión puede existir una diferencia entre la ocupación física y la información registrada en PostgreSQL.

### RN-01 — Prohibición de ingresos simultáneos

La comprobación global de ingresos abiertos depende del estado central.

El modo offline no puede garantizar completamente esta regla entre múltiples sedes desconectadas.

Los conflictos correspondientes deben identificarse y resolverse al recuperar la conexión.

## 11. Evolución futura de la decisión

La estrategia implementada cubre una necesidad de continuidad básica para los terminales de recepción.

Sin embargo, existen posibles mejoras que permitirían fortalecerla.

### 11.1 Verificación criptográfica local

Incorporar credenciales verificables mediante claves públicas, evitando que la autorización provisional dependa únicamente del contenido decodificado del QR.

### 11.2 Caducidad de snapshots

Establecer una antigüedad máxima y rechazar las copias que superen ese límite.

### 11.3 Almacenamiento local más robusto

Evaluar IndexedDB para almacenar registros estructurados y facilitar el tratamiento de colas de mayor volumen.

### 11.4 Protección de datos

Definir una política de acceso, retención y eliminación de los datos personales conservados en terminales.

### 11.5 Auditoría y conflictos

Incorporar un historial persistente de conflictos de sincronización para su resolución administrativa posterior.

### 11.6 Gestión de credenciales durante desconexiones prolongadas

Evaluar un mecanismo que permita contar con credenciales válidas durante una interrupción más larga sin comprometer la seguridad de la identificación.

### 11.7 Pruebas de contingencia

Ampliar las pruebas para comprobar:

- Interrupción de red durante una validación.
- Ausencia del snapshot.
- Snapshot desactualizado.
- Token QR vencido.
- Repetición de eventos.
- Pérdida del almacenamiento local.
- Recuperación después de una desconexión prolongada.
- Conflictos de ingreso en dos sedes.
- Fallos parciales durante la sincronización.

Estas mejoras no forman parte de la decisión implementada inicialmente. De adoptarse un cambio arquitectónico relevante, debería registrarse mediante un ADR posterior.

## 12. Conclusión

Se adoptó una **estrategia de funcionamiento offline basada en snapshots locales de socios y una cola persistente de ingresos pendientes** para reducir la dependencia del control de acceso respecto de la conectividad con el servidor central.

Frente a las alternativas consideradas, esta solución ofrece un equilibrio entre continuidad operativa, reutilización de la infraestructura existente y complejidad de implementación.

La alternativa de validación exclusivamente online fue descartada por no responder adecuadamente al requisito RNF-01.

La implementación de una base de datos local por sede ofrecía mayores posibilidades de independencia, pero incorporaba una complejidad de infraestructura y sincronización que no se consideró necesaria para el alcance actual.

El registro manual, aunque podría utilizarse como contingencia excepcional, no cumplía los objetivos de automatización y trazabilidad.

La solución seleccionada conserva a **PostgreSQL como fuente de verdad central**, mientras que los terminales utilizan información previamente descargada para sostener operaciones provisionales.

Esta arquitectura permite mantener cierto grado de funcionamiento cuando se pierde la conectividad, pero acepta consecuencias como la consistencia eventual, la necesidad de resolver conflictos y la existencia de limitaciones de seguridad en la validación local.

Por ese motivo, el diseño debe entenderse como una solución de **operación degradada**, no como una garantía de que todas las validaciones offline ofrecen exactamente las mismas condiciones que el modo online.

La sincronización y reconciliación de eventos se documentan por separado en el ADR-007.

**Decisión final: mantener una estrategia de continuidad offline mediante snapshots locales de socios activos, almacenamiento temporal de ingresos y posterior sincronización con el servidor central, reconociendo sus limitaciones y conservando PostgreSQL como fuente definitiva de información.**
