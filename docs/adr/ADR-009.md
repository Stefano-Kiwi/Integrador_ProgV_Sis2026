## 1. Contexto

FitZone Sports es una plataforma de gestión deportiva destinada a una cadena de gimnasios y complejos deportivos con múltiples sedes.

La solución está compuesta por una aplicación frontend desarrollada con React y TypeScript, una API backend implementada con NestJS y Prisma ORM, y una base de datos PostgreSQL.

Durante el desarrollo, el equipo necesitaba disponer de un procedimiento para ejecutar estos componentes de manera integrada y reproducible.

La instalación manual de todas las dependencias en cada computadora podía generar diferencias entre los entornos de los integrantes.

Por ejemplo, una versión distinta de Node.js, una configuración incorrecta de PostgreSQL o la ausencia de una migración podían impedir que una funcionalidad se ejecutara correctamente.

Además, la plataforma debía poder ser evaluada por la cátedra, por lo que resultaba importante disponer de instrucciones claras para preparar y ejecutar el sistema.

### 1.1 Problema identificado

Una aplicación compuesta por varios procesos necesita coordinar correctamente:

- La instalación de dependencias.
- Las versiones de herramientas.
- La configuración de variables de entorno.
- La conexión entre frontend y backend.
- La comunicación con PostgreSQL.
- Las migraciones del esquema.
- La carga de datos de demostración.
- La persistencia de información.
- La exposición de puertos.
- El inicio y apagado de servicios.
- La actualización del código.
- La recuperación ante errores de despliegue.

Sin una estrategia definida, cada integrante podría ejecutar la aplicación de una manera diferente.

Esto dificultaría reproducir errores, realizar pruebas integradas y presentar una versión estable.

### 1.2 Problema de la reversión

Además de ejecutar una versión nueva, era necesario considerar qué sucedería si una actualización introdujera errores.

Por ejemplo:

1. El equipo publica una modificación del backend.
2. La aplicación comienza a presentar fallas.
3. Se necesita recuperar una versión previamente validada.
4. La versión nueva pudo haber modificado también el esquema de PostgreSQL.
5. La reversión del código no garantiza que la base de datos vuelva automáticamente a su estado anterior.

Por lo tanto, la estrategia debía distinguir entre:

**Reversión de aplicación:** recuperar los artefactos correspondientes a una versión estable.

**Reversión de base de datos:** recuperar o adaptar el esquema y los datos cuando una migración resulte incompatible.

Ambas operaciones presentan riesgos diferentes y no deben confundirse.

### 1.3 Restricciones del proyecto

La solución debía:

1. Ser compatible con la arquitectura de monolito modular.
2. Permitir ejecutar PostgreSQL, NestJS y React.
3. Reducir las diferencias entre entornos.
4. Facilitar la evaluación académica.
5. Mantener persistentes los datos de PostgreSQL.
6. Permitir aplicar migraciones versionadas.
7. Proporcionar un procedimiento identificable de actualización.
8. Evitar eliminar datos al reiniciar contenedores.
9. Aprovechar GitHub para controlar versiones.
10. Integrarse con las verificaciones automatizadas de GitHub Actions.
11. Mantener una complejidad de infraestructura razonable para el equipo.

## 2. Alternativas consideradas

Se evaluaron distintas estrategias para instalar, ejecutar y actualizar FitZone Sports.

### 2.1 Alternativa A — Instalación manual de todos los componentes

Consiste en instalar Node.js, PostgreSQL y las demás herramientas directamente en cada computadora.

El frontend y backend se iniciarían mediante comandos npm, mientras que PostgreSQL funcionaría como un servicio instalado en el sistema operativo.

**Ventajas:**

- No requiere utilizar contenedores.
- Permite ejecutar y depurar los procesos directamente.
- Facilita trabajar con herramientas ya instaladas.
- Puede ser suficiente para desarrollos pequeños.
- Evita depender de Docker Desktop.

**Desventajas:**

- Cada integrante debe configurar su entorno.
- Pueden aparecer incompatibilidades de versiones.
- Es necesario administrar PostgreSQL manualmente.
- Las variables de entorno y los puertos pueden diferir.
- La instalación resulta menos reproducible.
- El evaluador necesita realizar más pasos.
- La recuperación de una instalación defectuosa puede ser más compleja.

**Motivo de descarte:**

Se consideró insuficiente como única estrategia de ejecución.

Aunque el desarrollo manual continúa siendo posible, se necesitaba un mecanismo más uniforme para levantar el sistema integrado.

### 2.2 Alternativa B — Máquinas virtuales completas

Consiste en preparar una máquina virtual con el sistema operativo, las dependencias y todos los componentes de FitZone Sports.

**Ventajas:**

- Permite controlar gran parte del entorno de ejecución.
- Aísla la aplicación respecto del sistema anfitrión.
- Puede reproducir instalaciones completas.
- Facilita conservar una imagen de referencia.

**Desventajas:**

- Mayor consumo de almacenamiento y memoria.
- Distribución de imágenes más pesada.
- Mantenimiento del sistema operativo invitado.
- Actualizaciones potencialmente más lentas.
- Mayor complejidad para distribuir cambios pequeños.
- Menor comodidad para separar los servicios.

**Motivo de descarte:**

El proyecto no necesitaba virtualizar un sistema operativo completo para cada componente.

Se priorizó una alternativa más liviana que permitiera separar procesos mediante contenedores.

### 2.3 Alternativa C — Docker y Docker Compose (seleccionada)

Consiste en empaquetar los componentes de la aplicación mediante imágenes Docker y definir su ejecución utilizando archivos Docker Compose.

**Ventajas:**

- Permite definir entornos reproducibles.
- Reduce diferencias entre equipos.
- Facilita iniciar varios servicios.
- Aísla procesos y dependencias.
- Permite reconstruir las imágenes cuando cambia el código.
- Facilita distribuir configuraciones de desarrollo.
- Permite utilizar volúmenes persistentes.
- Se integra con las herramientas de Node.js y PostgreSQL.
- No requiere un orquestador distribuido.
- Resulta adecuado para demostraciones locales.

**Desventajas:**

- Requiere instalar Docker y Compose.
- Consume recursos adicionales.
- Necesita administrar redes, puertos y volúmenes.
- Las imágenes deben actualizarse y protegerse.
- Compose no garantiza alta disponibilidad.
- El despliegue no es automáticamente reversible.
- La base de datos necesita procedimientos propios de respaldo.
- Una configuración insegura puede exponer servicios o credenciales.

**Evaluación:**

Se consideró la opción más apropiada por su equilibrio entre reproducibilidad, aislamiento y simplicidad operativa.

### 2.4 Alternativa D — Kubernetes

Kubernetes permite administrar aplicaciones contenerizadas mediante recursos de orquestación.

**Ventajas:**

- Escalado de servicios.
- Gestión declarativa.
- Reinicio y reemplazo de instancias.
- Posibilidad de realizar actualizaciones progresivas.
- Integración con sistemas de monitoreo.
- Mecanismos de despliegue adecuados para infraestructuras distribuidas.

**Desventajas para FitZone Sports:**

- Mayor complejidad de instalación.
- Necesidad de aprender y mantener recursos de Kubernetes.
- Requiere una infraestructura de ejecución apropiada.
- Aumenta el esfuerzo de configuración.
- Puede resultar excesivo para un equipo pequeño.
- La administración de almacenamiento persistente introduce requisitos adicionales.
- Las migraciones de base de datos siguen necesitando un procedimiento independiente.

**Motivo de descarte:**

La aplicación se desarrolla como un monolito modular y no requiere inicialmente una infraestructura de orquestación distribuida.

Se consideró que Kubernetes incorporaría una complejidad que no se justificaba para el alcance del Trabajo Integrador Final.

## 3. Comparación de alternativas

| Criterio | Instalación manual | Máquina virtual | Docker Compose | Kubernetes |
|---|---|---|---|---|

**Resultado:** se seleccionó Docker Compose como estrategia de ejecución y despliegue local, complementado por control de versiones Git y verificaciones automatizadas.

## 4. Decisión

Se decidió **contenerizar los componentes de FitZone Sports mediante Docker y utilizar Docker Compose para administrar su ejecución**, conservando PostgreSQL en un volumen persistente y utilizando Git para identificar versiones del código.

Se adoptó una estrategia de despliegue local con tres componentes lógicos:

1. Base de datos PostgreSQL.
2. Backend NestJS.
3. Frontend React compilado y publicado mediante Nginx.

El despliegue se complementa con GitHub Actions para verificar que los cambios puedan compilarse y superar las pruebas definidas.

La reversión de aplicación se plantea mediante la recuperación de una revisión estable y la reconstrucción o restauración de sus imágenes.

La reversión del esquema de base de datos requiere una evaluación independiente de compatibilidad y, cuando corresponda, una restauración o migración compensatoria.

### 4.1 Alcance de la decisión

La arquitectura está implementada mediante Dockerfiles y archivos Compose.

Sin embargo, **en el commit revisado no existe un archivo `docker-compose.yml` o `compose.yml` único en la raíz del repositorio**.

La configuración está separada entre:

- `backend/docker-compose.yml`
- `frontend/docker-compose.yml`
- `backend/database/docker-compose.yml`

El primero define PostgreSQL y backend.

El segundo define frontend.

El tercero proporciona una configuración adicional de PostgreSQL para determinados usos de desarrollo.

Por lo tanto, la decisión de Docker Compose está implementada, pero la orquestación de los tres componentes desde un único archivo raíz sigue siendo una mejora pendiente.

La solución funciona mediante contenedores separados según sus responsabilidades.

```text id="et5m5s"
                          |
                 HTTP / HTTPS local
                          |
                          v
                FRONTEND - NGINX
                React compilado
                 Puertos 80/443
```

## 6. Contenerización del backend

El backend utiliza el archivo:

`backend/Dockerfile`

### 6.1 Imagen base

La imagen utilizada es:

```dockerfile id="9Qdo11"
FROM node:22-slim
```

Se decidió utilizar una imagen de Node.js compatible con el backend NestJS.

### 6.2 Preparación del entorno

El Dockerfile establece:

```dockerfile id="d1gkcm"
WORKDIR /app
```

También instala dependencias del sistema necesarias para Prisma y las conexiones seguras.

### 6.3 Instalación de dependencias

La imagen copia primero los archivos de dependencias:

```dockerfile id="0o0ttc"
COPY package*.json ./
RUN npm ci
```

El uso de `npm ci` permite instalar las dependencias conforme al lockfile del proyecto.

Esta elección favorece la reproducibilidad respecto de una instalación que pudiera actualizar libremente las versiones.

### 6.4 Generación de Prisma

El Dockerfile incorpora el esquema de Prisma y ejecuta:

```dockerfile id="y5a5uj"
COPY prisma ./prisma/
RUN npx prisma generate
```

Esto prepara el cliente de acceso a PostgreSQL.

### 6.5 Compilación

Posteriormente, copia el código fuente y construye la aplicación:

```dockerfile id="k94191"
COPY . .
RUN npm run build
```

El backend queda preparado para ejecutarse con Node.js.

### 6.6 Inicio

El Dockerfile utiliza:

```dockerfile id="hycgol"
ENTRYPOINT ["./docker-entrypoint.sh"]
CMD ["node", "dist/main.js"]
```

El entrypoint ejecuta la preparación de base de datos antes de iniciar el servidor.

### 6.7 Consecuencia de esta organización

El backend no necesita instalar las herramientas de desarrollo directamente en el equipo donde se ejecuta el contenedor.

Sin embargo, la imagen utiliza una etapa única y contiene dependencias instaladas mediante `npm ci`, incluidas las necesarias para compilar.

Una futura optimización podría separar las etapas de construcción y ejecución para reducir la superficie y el tamaño de la imagen final.

## 7. Contenerización del frontend

El frontend utiliza:

`frontend/Dockerfile`

Se implementó una construcción de múltiples etapas.

### 7.1 Primera etapa — Compilación

Se utiliza:

```dockerfile id="bcxblj"
FROM node:20-alpine AS build
```

La primera etapa instala las dependencias y ejecuta:

```dockerfile id="83lp55"
RUN npm install
RUN npm run build
```

La aplicación React se compila mediante TypeScript y Vite.

Los archivos resultantes se almacenan en el directorio `dist`.

### 7.2 Segunda etapa — Publicación mediante Nginx

La segunda etapa utiliza:

```dockerfile id="5i57fu"
FROM nginx:alpine
```

La imagen copia los archivos compilados al directorio público de Nginx:

```dockerfile id="c4dlbe"
COPY --from=build /app/dist /usr/share/nginx/html
```

Esta separación permite que la aplicación final sea servida por Nginx sin necesitar ejecutar el servidor de desarrollo Vite.

### 7.3 Ventajas

- Se separa la compilación del servicio de archivos estáticos.
- Nginx puede servir los recursos generados por React.
- Se evita depender del servidor de desarrollo de Vite durante la publicación.
- Los archivos estáticos pueden utilizar mecanismos de caché.
- Se permite configurar un proxy hacia el backend.

### 7.4 Reproducibilidad

A diferencia del backend, el Dockerfile del frontend utiliza `npm install` en lugar de `npm ci`.

Esto introduce una diferencia en la estrategia de instalación.

Para lograr una construcción más predecible, se recomienda utilizar `npm ci` también en la etapa de frontend, siempre que el lockfile esté correctamente actualizado.

Esta modificación se considera una mejora pendiente.

## 8. Nginx y comunicación entre componentes

El frontend utiliza:

`frontend/nginx.conf`

Nginx tiene tres responsabilidades principales:

1. Publicar la aplicación React compilada.
2. Permitir la navegación entre rutas de una SPA.
3. Redirigir determinadas solicitudes al backend.

### 8.1 Navegación React Router

La configuración incluye:

```nginx id="gd02hp"
location / {
    try_files $uri $uri/ /index.html;
}
```

Esta regla permite que rutas como `/admin` o `/profile` carguen la aplicación React correctamente al ingresar directamente mediante el navegador.

### 8.2 Publicación de recursos estáticos

Los archivos del directorio `/assets/` utilizan encabezados de caché.

Esto permite aprovechar el almacenamiento del navegador para recursos generados por Vite.

### 8.3 Proxy hacia NestJS

La configuración contiene:

```nginx id="vlhn1e"
location /backend/ {
    proxy_pass http://host.docker.internal:3000/;
}
```

El frontend realiza solicitudes con el prefijo `/backend`.

Nginx las redirige al backend publicado en el puerto 3000 del anfitrión.

### 8.4 Consecuencia técnica

El frontend y backend pueden iniciarse mediante Compose independientes.

No obstante, esta configuración está acoplada a la disponibilidad del puerto 3000 en el anfitrión y a la resolución de `host.docker.internal`.

Una futura configuración Compose única podría simplificar la comunicación utilizando el nombre del servicio `backend` dentro de una red Docker compartida.

## 9. Servicios definidos en Docker Compose

### 9.1 PostgreSQL

El archivo `backend/docker-compose.yml` define:

```yaml id="bg4yw3"
postgres:
  image: postgres:18-alpine
  container_name: fitzone_postgres
  restart: unless-stopped
```

El servicio utiliza PostgreSQL 18.

También configura:

- Usuario y contraseña.
- Nombre de la base.
- Puerto 5432.
- Volumen persistente.
- Comprobación de salud.

### 9.2 Healthcheck de PostgreSQL

La configuración utiliza:

```yaml id="ny43mv"
healthcheck:
  test:
    - CMD-SHELL
    - pg_isready -U postgres -d fitzone_sports
  interval: 5s
  timeout: 5s
  retries: 5
  start_period: 10s
```

Este mecanismo permite comprobar que PostgreSQL esté aceptando conexiones.

### 9.3 Dependencia del backend

El backend declara:

```yaml id="uy072p"
depends_on:
  postgres:
    condition: service_healthy
```

Esto evita iniciar el servicio de aplicación antes de que PostgreSQL supere la comprobación de salud inicial.

### 9.4 Backend

El servicio publica el puerto:

```yaml id="mkx2iq"
ports:
  - "3000:3000"
```

La variable `DATABASE_URL` utiliza el nombre de servicio `postgres` para establecer la conexión interna.

### 9.5 Frontend

El archivo `frontend/docker-compose.yml` define un contenedor Nginx que publica:

```yaml id="sh833n"
ports:
  - "5173:80"
  - "5174:443"
```

Por lo tanto:

| Componente | Dirección local |
|---|---|
| Frontend HTTP | `http://localhost:5173` |
| Frontend HTTPS | `https://localhost:5174` |
| Backend NestJS | `http://localhost:3000` |
| Swagger | `http://localhost:3000/api` |
| PostgreSQL desde el anfitrión | `localhost:5432` |

**Observación:** el manual de instalación menciona el puerto HTTPS 5443, pero el Compose del frontend revisado publica 5174.

Antes de la entrega se debe unificar la configuración y la documentación.

## 10. Persistencia de PostgreSQL

Uno de los aspectos más importantes del despliegue es conservar la información de la base de datos.

### 10.1 Volumen persistente

El servicio PostgreSQL utiliza:

```yaml id="6wqrkl"
volumes:
  - postgres_data:/var/lib/postgresql
```

El volumen permite conservar los datos aunque se destruya o recree el contenedor, siempre que no se elimine expresamente el volumen.

### 10.2 Diferencia entre detener y eliminar datos

El comando:

```bash id="zygdvj"
docker compose down
```

detiene y elimina los contenedores y la red del proyecto Compose, pero normalmente conserva los volúmenes nombrados.

En cambio:

```bash id="ga8mbd"
docker compose down -v
```

también elimina los volúmenes administrados por ese proyecto Compose.

### 10.3 Riesgo

Eliminar el volumen de PostgreSQL puede provocar la pérdida de la base de datos local.

Por lo tanto, `down -v` debe reservarse exclusivamente para entornos descartables en los que se haya decidido reiniciar los datos.

**No debe utilizarse como procedimiento habitual de reversión.**

### 10.4 Persistencia no equivale a respaldo

Aunque el volumen conserve los datos, esto no significa que exista una copia recuperable ante corrupción, eliminación accidental o fallas del almacenamiento.

La estrategia requiere distinguir entre:

- Persistencia mediante volumen.
- Respaldo mediante exportación de datos.
- Restauración controlada.
- Reversión de migraciones.

## 11. Migraciones y preparación automática

El backend utiliza Prisma para administrar el esquema de PostgreSQL.

Las migraciones se encuentran en:

`backend/prisma/migrations/`

### 11.1 Preparación de la base

El archivo:

`backend/docker-entrypoint.sh`

ejecuta:

```bash id="gs2jjn"
npx prisma migrate deploy
```

Este comando aplica las migraciones pendientes que ya fueron versionadas en el repositorio.

### 11.2 Reintentos de conexión

El script contiene un mecanismo de hasta quince intentos para aplicar migraciones.

Si el proceso no consigue completar esa operación después de los intentos permitidos, termina con un error.

Esto evita iniciar NestJS normalmente cuando no fue posible preparar la base.

### 11.3 Datos semilla

Después de las migraciones, el script ejecuta:

```bash id="3lnju5"
npm run seed
```

Este comando carga los datos de demostración definidos por el proyecto.

### 11.4 Inicio del servidor

Finalmente se ejecuta:

```bash id="k2yqxq"
exec "$@"
```

Esto inicia el proceso principal del contenedor.

### 11.5 Consecuencia de la decisión

La preparación automatizada simplifica el entorno académico porque evita aplicar manualmente las migraciones al iniciar una instalación nueva.

Sin embargo, **el seed se ejecuta en cada inicio del backend**.

Esto constituye una limitación importante: la rutina utiliza cuentas y credenciales de demostración, por lo que no debe ejecutarse de esa manera sobre información productiva.

Una futura configuración de producción deberá separar las migraciones y los datos iniciales de prueba.

## 12. Variables de entorno y configuración

La aplicación utiliza variables de entorno para configurar componentes como la base de datos, los tokens de autenticación y el servidor.

### 12.1 Variables principales

| Variable | Responsabilidad |
|---|---|
| `PORT` | Puerto interno del backend |
| `DATABASE_URL` | Cadena de conexión PostgreSQL |
| `JWT_SECRET` | Firma de tokens de autenticación |
| `QR_SECRET` | Firma y validación de códigos QR |
| `POSTGRES_USER` | Usuario de PostgreSQL |
| `POSTGRES_PASSWORD` | Contraseña de PostgreSQL |
| `POSTGRES_DB` | Nombre de la base de datos |

### 12.2 Archivos de referencia

El repositorio contiene:

- `backend/.env.example`
- `frontend/.env.example`

Estos archivos ayudan a identificar parámetros utilizados por los componentes.

### 12.3 Limitación del Compose actual

El Compose de backend revisado define directamente valores de desarrollo para la contraseña de PostgreSQL y el secreto JWT.

Aunque existe `backend/.env.example`, eso no significa que el archivo Compose cargue automáticamente sus valores.

Por lo tanto, debe evitarse afirmar que la configuración actual ya separa correctamente todos los secretos mediante variables externas.

### 12.4 Recomendaciones de seguridad

Para un despliegue real sería necesario:

- Eliminar credenciales de ejemplo.
- Utilizar secretos aleatorios.
- Evitar publicar credenciales dentro del repositorio.
- No registrar secretos en logs.
- Limitar el acceso al servidor de base de datos.
- Utilizar canales cifrados cuando corresponda.
- Mantener configuraciones diferenciadas por ambiente.

## 13. Procedimiento de instalación local

La configuración existente utiliza archivos Compose separados.

El siguiente procedimiento corresponde al entorno de desarrollo y demostración.

### 13.1 Requisitos previos

Se necesita:

- Git.
- Docker Engine o Docker Desktop.
- Docker Compose.
- Puertos disponibles.
- Acceso al repositorio.
- Recursos suficientes para descargar y construir las imágenes.

### 13.2 Clonar el repositorio

```bash id="5qn9r5"
git clone https://github.com/Stefano-Kiwi/Integrador_ProgV_Sis2026.git
cd Integrador_ProgV_Sis2026
```

### 13.3 Iniciar PostgreSQL y backend

Desde la raíz:

```bash id="wss8dj"
docker compose -f backend/docker-compose.yml up --build -d
```

Este comando utiliza el archivo Compose que define PostgreSQL y NestJS.

### 13.4 Comprobar servicios

```bash id="xrxk86"
docker compose -f backend/docker-compose.yml ps
```

Para revisar los registros:

```bash id="kj71fx"
docker compose -f backend/docker-compose.yml logs --tail=100
```

### 13.5 Iniciar frontend

Desde la raíz:

```bash id="h3k0x7"
docker compose -f frontend/docker-compose.yml up --build -d
```

### 13.6 Comprobar frontend

```bash id="8mc5sk"
docker compose -f frontend/docker-compose.yml ps
```

## 15. Estrategia de actualización

- Haya superado las pruebas.
- Disponga de las migraciones necesarias.
- Tenga documentación coherente.

- Referencia de la versión o tag, si existe.
- Identificación de las imágenes utilizadas.

## 16. Procedimiento de reversión de la aplicación

La reversión busca recuperar una versión anterior cuando una actualización provoca problemas.

### 16.1 Principio de reversión

La estrategia establece que el código de aplicación debe poder asociarse con una revisión identificable de Git.

Sin embargo, el repositorio **no incorpora un comando o workflow automatizado de rollback**.

Por lo tanto, el procedimiento de reversión se documenta como una operación manual y controlada.

### 16.2 Condiciones previas

Antes de iniciar una reversión debe comprobarse:

- Qué versión está ejecutándose.
- Qué versión se pretende recuperar.
- Si existen modificaciones locales sin guardar.
- Qué migraciones fueron aplicadas.
- Si el esquema actual es compatible con el código anterior.
- Si existe un respaldo verificado.
- Qué servicios deben detenerse.

### 16.3 Caso A — Cambio exclusivo de aplicación

Supongamos que una versión introduce un error de presentación o una regresión en un servicio, pero no modifica el esquema de PostgreSQL.

En un entorno controlado, el procedimiento puede consistir en recuperar el commit previamente validado y reconstruir las imágenes.

Ejemplo conceptual:

```bash id="zj0vda"
# Identificar la versión actualmente desplegada
git rev-parse HEAD

# Recuperar una revisión anterior previamente validada
git switch --detach <SHA_ESTABLE_VERIFICADO>

# Reconstruir backend
docker compose -f backend/docker-compose.yml up --build -d

# Reconstruir frontend
docker compose -f frontend/docker-compose.yml up --build -d
```

`<SHA_ESTABLE_VERIFICADO>` representa una revisión real seleccionada por el equipo; no debe reemplazarse por un valor arbitrario.

### 16.4 Advertencia sobre el procedimiento

Los comandos anteriores son una guía de recuperación para un entorno controlado, no un mecanismo de rollback transaccional.

Se debe confirmar primero que las imágenes anteriores puedan funcionar con el esquema PostgreSQL actual.

Además, el entrypoint del backend ejecuta migraciones y seed al iniciarse, por lo que reconstruir una versión anterior no es una acción inocua para una base con información persistida.

### 16.5 Validación posterior

Después de recuperar la versión estable deben comprobarse:

- Inicio correcto de backend.
- Conectividad con PostgreSQL.
- Ejecución del frontend.
- Autenticación.
- Consultas principales.
- Ausencia de errores relevantes.
- Integridad de los datos.

Si el problema continúa, la reversión no debe considerarse completada.

## 17. Reversión de migraciones de PostgreSQL

La reversión del esquema presenta más riesgos que la reversión de archivos de aplicación.

### 17.1 Problema

Una actualización puede modificar tablas, campos, restricciones o tipos de datos.

Si se intenta iniciar una versión anterior del backend contra un esquema incompatible, la aplicación puede fallar.

### 17.2 Prisma Migrate

El proyecto utiliza migraciones versionadas.

El comando:

```bash id="krkcw6"
npx prisma migrate deploy
```

aplica migraciones pendientes.

Sin embargo, **no constituye un mecanismo de reversión automática**.

El repositorio no contiene scripts `down.sql` que permitan revertir automáticamente todas las modificaciones.

### 17.3 Estrategia de reversión

Cuando una migración resulta incompatible, se establece el siguiente procedimiento:

1. Detener temporalmente las escrituras.
2. Identificar la migración problemática.
3. Comprobar el estado del esquema.
4. Conservar un respaldo del estado actual.
5. Identificar si existe un respaldo anterior válido.
6. Evaluar la restauración en una instancia aislada.
7. Comprobar la compatibilidad del código anterior.
8. Restaurar o aplicar una migración compensatoria aprobada.
9. Verificar integridad y funcionamiento.
10. Registrar la intervención.

### 17.4 Migración fallida

Si una migración quedó incompleta, debe inspeccionarse el esquema real y determinar qué cambios llegaron a aplicarse.

Prisma permite registrar la resolución de determinadas migraciones mediante:

```bash id="3w9cqz"
npx prisma migrate resolve --rolled-back NOMBRE_MIGRACION
```

Este comando **no deshace por sí mismo las modificaciones SQL que hayan ocurrido**.

Debe utilizarse solamente después de comprobar y resolver el estado real de la base.

### 17.5 Migración aplicada

Si una migración ya fue aplicada correctamente, no corresponde marcarla arbitrariamente como revertida.

Las opciones deben evaluarse según el caso:

- Restauración de un respaldo anterior.
- Migración compensatoria hacia adelante.
- Adaptación temporal de la aplicación.
- Procedimiento manual revisado para modificar el esquema.

### 17.6 Prohibición de reinicio destructivo

No debe utilizarse:

```bash id="5o5qch"
npx prisma migrate reset
```

como procedimiento de recuperación de una base productiva.

Ese comando puede eliminar y recrear la base.

Tampoco debe utilizarse `docker compose down -v` para intentar corregir una migración.

### 17.7 Consecuencia arquitectónica

La reversión del código y la reversión del esquema son operaciones independientes.

Por ese motivo, una estrategia de despliegue confiable requiere diseñar migraciones compatibles o contar con respaldos verificables.

## 18. Respaldo y restauración

PostgreSQL almacena los datos en un volumen persistente, pero también necesita mecanismos de respaldo.

### 18.1 Objetivo

Los respaldos permiten recuperar información ante:

- Eliminación accidental.
- Corrupción de datos.
- Fallos de almacenamiento.
- Migraciones incorrectas.
- Errores administrativos.
- Necesidad de volver a un estado anterior.

### 18.2 Herramienta seleccionada

PostgreSQL dispone de `pg_dump` para exportar una base de datos.

El siguiente ejemplo corresponde a la instancia de desarrollo y debe adaptarse al entorno correspondiente.

Ejemplo desde una terminal compatible con Bash, ubicado en la raíz del repositorio:

```bash id="bm9dp1"
docker compose -f backend/docker-compose.yml exec -T postgres \
  pg_dump -U postgres -d fitzone_sports > backup-fitzone.sql
```

En Windows PowerShell debe utilizarse un procedimiento de redirección que preserve correctamente la codificación del archivo generado; el manual de instalación documenta una variante mediante `cmd /c`.

### 18.3 Conservación del respaldo

La copia debe:

- Guardarse fuera del contenedor.
- Protegerse frente a accesos no autorizados.
- Identificarse mediante fecha y versión.
- Conservarse según una política de retención.
- Verificarse antes de utilizarse para una recuperación.

### 18.4 Restauración

La restauración debe realizarse primero en una instancia aislada.

El procedimiento necesita verificar:

- Integridad del archivo.
- Compatibilidad de versiones.
- Esquema recuperado.
- Datos disponibles.
- Historial de migraciones.
- Funcionamiento del backend.
- Ausencia de errores en recorridos críticos.

### 18.5 Limitación actual

El repositorio documenta cómo realizar respaldos y restauraciones, pero no implementa una programación automática de copias ni demuestra una política productiva de retención.

Por lo tanto, se considera un **procedimiento operativo definido**, no un sistema completo de recuperación automática.

## 20. Diferencias entre desarrollo y producción

La decisión de utilizar Docker no implica que el despliegue actual sea automáticamente seguro para producción.

### 20.1 Entorno actual

La configuración revisada está orientada principalmente al desarrollo y la demostración académica.

Entre sus características se encuentran:

- PostgreSQL publicado en el puerto 5432.
- Credenciales de desarrollo definidas en Compose.
- Secretos de ejemplo.
- Certificado HTTPS autofirmado.
- Ejecución automática de seed al iniciar backend.
- Docker Compose separados.
- Ausencia de despliegue progresivo.
- Ausencia de réplicas de aplicación.
- Monitoreo limitado.

### 20.2 Riesgos productivos

Utilizar esta configuración sin modificaciones podría exponer información o provocar comportamientos no deseados.

En particular, el seed de demostración puede crear o modificar cuentas de prueba.

El HTTPS autofirmado tampoco sustituye a un certificado válido para un servicio publicado.

### 20.3 Requisitos para una evolución productiva

Una versión preparada para producción debería:

1. Retirar el seed automático de demostración.
2. Utilizar credenciales y secretos seguros.
3. Proteger PostgreSQL en una red privada.
4. Configurar TLS con certificados válidos.
5. Definir respaldos automatizados.
6. Incorporar healthchecks del backend y frontend.
7. Implementar registros y métricas.
8. Fijar versiones o digests de las imágenes.
9. Definir un procedimiento de actualización probado.
10. Validar la restauración y reversión antes de desplegar.

Estas medidas constituyen requisitos de evolución y **no se declaran implementadas en la configuración actual**.

## 21. Relación con la escalabilidad — RNF-04

La estrategia seleccionada facilita empaquetar los componentes y trasladarlos entre entornos compatibles con Docker.

Esto representa una ventaja para el crecimiento del sistema.

### 21.1 Incorporación de nuevas sedes

Las sucursales se administran como entidades en PostgreSQL.

Por lo tanto, registrar una nueva sede no requiere crear un backend independiente.

La arquitectura modular permite mantener una única API que administra los recursos asociados con todas las sedes.

### 21.2 Escalado del backend

Los contenedores proporcionan una base para considerar la ejecución de distintas instancias de la aplicación.

Sin embargo, la configuración Compose actual publica una única instancia de NestJS.

No implementa balanceo de carga ni despliegue horizontal automático.

### 21.3 Persistencia centralizada

PostgreSQL continúa siendo un punto central para mantener la consistencia de las operaciones.

Si se incorporaran varias instancias del backend, todas deberían respetar las restricciones de integridad de la misma base.

### 21.4 Limitación

La posibilidad técnica de ejecutar contenedores adicionales no garantiza rendimiento ni alta disponibilidad.

Para acreditar escalabilidad sería necesario medir el comportamiento bajo distintas cargas y diseñar una infraestructura apropiada.

## 22. Consecuencias de la decisión

### 22.1 Consecuencias positivas

**Reproducibilidad**

Los Dockerfiles permiten definir las dependencias necesarias para cada componente.

**Aislamiento**

Frontend, backend y PostgreSQL se ejecutan en contenedores separados.

**Facilidad de demostración**

El equipo puede proporcionar un procedimiento de instalación basado en Docker.

**Menor dependencia del equipo anfitrión**

No es necesario instalar manualmente todos los servicios para ejecutar la versión contenerizada.

**Persistencia**

PostgreSQL utiliza un volumen nombrado que permite conservar la información entre recreaciones normales de contenedores.

**Preparación automática**

El backend aplica migraciones y ejecuta datos semilla al iniciarse.

**Separación de presentación y API**

El frontend se publica mediante Nginx y consume el backend mediante un proxy.

**Control de versiones**

Git permite identificar revisiones de código y asociarlas con resultados de integración continua.

**Verificación previa**

GitHub Actions comprueba compilación, lint, cobertura y escenarios de integración.

**Extensibilidad**

La contenerización facilita estudiar una futura migración hacia una infraestructura más avanzada.

### 22.2 Consecuencias negativas

**Dependencia de Docker**

Los usuarios del entorno contenerizado necesitan disponer de Docker y Compose.

**Consumo de recursos**

La ejecución de varios contenedores requiere memoria, CPU y almacenamiento.

**Complejidad de redes**

La separación actual de Compose obliga a utilizar el anfitrión como punto de comunicación entre frontend y backend.

**Configuración distribuida**

Existen diferentes archivos Compose que deben mantenerse coherentes.

**Despliegue no atómico**

La actualización de backend y frontend se realiza mediante operaciones independientes.

**Interrupciones durante actualización**

Compose no proporciona automáticamente una estrategia de despliegue sin tiempo de inactividad.

**Seguridad de desarrollo**

La configuración actual incorpora credenciales y características apropiadas solo para demostración.

**Dependencia de migraciones**

Las versiones del backend deben ser compatibles con el esquema PostgreSQL.

**Reversión manual**

No existe una automatización de rollback.

**Necesidad de respaldos**

La persistencia mediante volúmenes no reemplaza la recuperación ante fallas.

### 22.3 Deuda técnica asumida

La decisión deja pendientes las siguientes mejoras:

- Crear un Compose único en la raíz.
- Corregir las diferencias entre puertos documentados y configurados.
- Incorporar healthchecks de aplicación.
- Retirar el seed automático de cualquier entorno productivo.
- Externalizar los secretos de desarrollo.
- Implementar respaldos verificables y periódicos.
- Fijar versiones o digests de imágenes.
- Automatizar la publicación de imágenes versionadas.
- Establecer un procedimiento de rollback ensayado.
- Incorporar monitoreo y alertas.
- Verificar la construcción Docker dentro del pipeline.
- Documentar y probar un despliegue productivo separado.

Construir y probar las imágenes Docker dentro de GitHub Actions para detectar diferencias entre compilaciones npm y las imágenes finales.

### 26.10 Alta disponibilidad

Evaluar balanceo de carga, réplicas y procedimientos de recuperación ante fallos solamente si el crecimiento de la plataforma lo requiere.

Estas mejoras no se consideran implementadas por el presente ADR.

Si el equipo reemplazara Docker Compose por otro mecanismo de orquestación o modificara sustancialmente su estrategia de despliegue, debería registrar un nuevo ADR.

---

## 27. Conclusión

Se decidió utilizar **Docker y Docker Compose para la ejecución contenerizada de FitZone Sports**, organizando sus componentes en servicios diferenciados para frontend, backend y PostgreSQL.

La elección responde a la necesidad de disponer de un entorno reproducible, reducir diferencias entre equipos y simplificar la instalación de las dependencias necesarias.

Frente a la instalación manual, las máquinas virtuales completas y Kubernetes, Docker Compose ofrecía un equilibrio más conveniente entre aislamiento, complejidad y facilidad de uso para el alcance académico.

La implementación utiliza imágenes Node.js para construir el backend y frontend, Nginx para publicar la aplicación React y PostgreSQL para conservar la información.

La persistencia se administra mediante un volumen Docker, mientras que Prisma permite aplicar migraciones versionadas.

GitHub Actions complementa la estrategia mediante pruebas y verificaciones de compilación previas a la selección de una versión.

Respecto de la reversión, se estableció que la aplicación debe asociarse con una revisión de Git identificable y que la recuperación de una versión anterior debe realizarse de manera controlada.

No obstante, la reversión de código no implica automáticamente revertir el esquema de PostgreSQL.

Cuando existen migraciones incompatibles, es necesario utilizar respaldos o migraciones compensatorias, verificando la integridad de los datos.

La solución presenta limitaciones reconocidas: los archivos Compose están separados, el despliegue no es progresivo, algunas configuraciones son exclusivas de desarrollo, el seed se ejecuta al iniciar y no existe una automatización de rollback.

Estas limitaciones no invalidan la elección de Docker Compose para el Trabajo Integrador Final, pero establecen condiciones que deben resolverse antes de una utilización productiva.

**Decisión final: mantener Docker y Docker Compose como estrategia de contenerización y despliegue local de FitZone Sports, utilizar GitHub Actions para las verificaciones previas, conservar PostgreSQL mediante almacenamiento persistente y documentar una reversión controlada de aplicación y base de datos, reconociendo que el rollback automático y el despliegue productivo seguro constituyen mejoras pendientes.**
